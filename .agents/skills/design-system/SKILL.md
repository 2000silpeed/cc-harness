# 디자인 시스템 적용

## 새로 작성하거나 다른 프로젝트에 재사용할 때

- `docs/design-system/authoring-guide.md`를 먼저 읽는다. 다른 저장소에서 작업할 때는 이 스킬을 제공한 저장소의 가이드 경로를 먼저 확인한다. 필요한 문서가 없으면 추측하지 말고 요청한다.
- 대상 프로젝트의 지침·참고 자료·기능 범위·기존 디자인·스타일 도구를 조사한다. 기존 규칙을 덮어쓰지 않는다.
- 가이드의 입력 조사 → design.md → 공통 문서 → 교차 검토 → 대상별 검사 연결 순서로 진행한다. 관찰·제안·승인·미정을 구분하고 필요한 질문만 하나씩 한다.
- 다른 프로젝트의 색상·사례·검사기를 새 제품의 기준으로 복사하지 않는다. 실제 이식에는 기준 원본·대상·스타일 방식·명령을 함께 조정한다.
- README와 흐름 화면의 상태를 함께 갱신한다. 문서 작성·사용자 승인·구현·수동 검사·훅 실제 발화를 구분해서 보고한다.

## 현재 저장소의 기준을 적용할 때

1. 프로젝트 AGENTS.md와 변경 대상의 실제 코드를 읽는다. 기존 인터뷰와 승인 상태는 요청 없이 변경하지 않는다.
2. 대상 기능의 design.md를 먼저 읽는다. 실제 대상 경로와 승인된 기준을 확인한다. 다른 앱까지 승인된 디자인으로 확대하지 않는다.
3. 대상에 존재하는 디자인 시스템의 colors.md, typography.md, spacing.md, components.md를 읽는다. 없으면 필요한 기준부터 준비한다. 기존 값을 재사용하고 새 값이 필요하면 이유를 제시한다. 통과를 위해 검사 기준을 무작정 완화하지 않는다.
4. 승인된 범위만 구현한다. 참고 이미지가 없으면 이미지 분석 결과를 만들어내지 않는다. 없는 hover/disabled/error 상태를 이미 구현된 것으로 기록하지 않는다.
5. 대상에 구성된 디자인 검사 명령과 지원 파일·정적 분석 한계를 확인하고 관련 검사를 실행한다. 검사기가 없으면 대상 기술에 맞는 최소 검사 계획과 미검증 범위를 기록한다. 이 하네스의 배포가 제품 검사기·패키지·훅을 설치했다고 가정하지 않는다.
6. 화면을 바꿨다면 실제 브라우저에서 반응형·상태·키보드 포커스를 확인한다. 정적 검사와 시각 검증 결과를 구분해 보고한다.

훅은 검사를 실행할 뿐 자동 수정이나 변경 취소를 하지 않는다. 사용법과 신뢰 승인 절차는 `docs/methods/design-system.md`를 따른다.
