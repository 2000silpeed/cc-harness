# 아이디어를 실행 가능한 이슈로

현재 게이트의 절만 읽는다. 절은 지정 제목부터 다음 같은/상위 수준 제목 직전까지 선택한다.

- G1: `docs/methods/requirements-interview.md`의 `## 결정의 원칙`, `## 인터뷰 실행`, `## 검증과 인계`; `docs/methods/planning.md`의 `## 단계 1: 요구사항 인터뷰 계약`.
- G2·G3: planning의 `## 단계 2: PRD와 기술 결정`.
- G4: planning의 `## 단계 3: 수직 슬라이스와 AC`.
- 외부 등록 요청이 있을 때만 planning의 `## GitHub·프로젝트 보드 등록 계약`.
- 작성할 때만 `docs/harness/templates.md`의 대응 제목(`## 원문·인터뷰·요구사항`, `## PRD와 ADR`, `## 이슈`).

다음 단계 자료를 미리 읽지 않는다. 이전 단계는 승인 버전·미결 항목만 전달한다.

## 게이트 권한과 기록

`docs/harness/lifecycle.md`의 `## 5. 승인과 외부 작업`을 읽고 기본 직접 승인, 결과·구현 승인, 별도로 위임한 게이트 정책을 구분한다. 구현 승인이 없으면 `human-required`다. 명확한 추천 결과에 대한 “승인하고 구현”은 결과와 가역적 로컬 구현·검증의 승인으로 보존한다. 통상적인 후속 G2–G5 판단에 게이트 이름·추가 양식·반복 승인을 요구하지 않으며 필요한 문서와 독립 검토는 수행한다. 명시된 게이트 제한과 STOP을 우선한다.

`policy-delegated` 결정은 위임 정책과 실제 근거를 대조해 기록한다. `auto-with-audit`는 결정자와 분리된 검증자가 범위·기준·증거를 감사한 뒤에만 통과한다. 둘 다 사용자 직접 승인으로 표기하지 않는다. 사용자의 침묵, AI 추천, 검사 통과는 위임이 아니다.

- G1: 제품 목적·사용자 가치가 충돌하거나 의도가 빠졌으면 항상 사용자에게 상향한다.
- G2: 승인 결과에 필요한 통상적인 기술 선택은 이유와 대안을 기록해 판단한다.
- G3: 승인 결과의 경계를 구체화한다. 목적·비용·위험·우선순위를 실질적으로 바꾸는 선택은 확인한다.
- G4: 구현 승인 범위의 이슈 분해·AC·의존성은 `auto-with-audit`와 독립 감사로 확정한다.

외부 쓰기, Git 초기화·브랜치·커밋·push·PR·병합·배포, 유료 호출, 파괴적 작업, 보안·법적 결정은 게이트 위임과 별도다. 사용자가 정확한 대상과 범위를 위임 기록에 포함한 경우에만 해당 권한이 생긴다.

## G1 요구사항

원본 요청을 `spec-original.md`에 보존하고 실제 코드·설정을 확인한다. 앱 소스가 없으면 없다고 밝힌다. 처음 요청의 핵심 동작·사용자 가치가 불명확하면 결과를 좌우하는 질문 하나에 구체적인 추천과 이유를 제시한다. 이후 사용자가 추천 결과를 승인하고 구현을 요청했다면 같은 질문이나 일상적인 기술 선택을 반복 확인하지 않는다. 사용자 결정·실행 승인과 AI 기본값·이유·용어를 `spec-fixed.md`에 구분한다. 낮은 위험의 세부는 제한된 가역적 기본값으로 해결하되 제품 목적·가치·중대한 범위·위험의 공백은 상향한다. **G1은 필요한 동작 정책과 성공 조건의 근거를 갖춘 뒤 통과하며 필수 입력을 “미결”로 두고 통과시키지 않는다.**

UI가 필요하면 design-system으로 `design.md`와 공통 기준을 준비하고 관찰·AI 선택·사용자 결정의 출처를 구분해 검토한다. 구현 승인 범위의 통상적인 디자인 선택은 이유를 기록하고 진행한다. UI가 없으면 이유와 함께 해당 없음으로 둔다.

## G2·G3 PRD와 ADR

유효한 G1 spec, design, 실제 코드를 입력으로 사용한다. 데이터/API/상태/핵심 동작/컴포넌트/기존 패턴/테스트 용이성 기준으로 최소 세 안을 비교한다. 의미 없는 대안을 만들지 않는다. G2는 사용자 선택 또는 구현 승인 범위의 기술 판단 근거로 판정한다. ADR의 Context·Decision·Alternatives·Consequences에 결정 출처를 기록하고 AI 추천이나 정책 판정을 사용자 결정으로 쓰지 않는다. 구체적인 Out of Scope를 제시하고 G3은 사용자 확정 또는 승인 결과의 경계를 지키는 판정 뒤 이슈로 간다.

## G4 이슈

유효한 G2·G3 PRD를 사용자에게 보이는 독립 TDD 수직 슬라이스로 나눈다. AC는 Given–When–Then의 관찰 결과로 쓰고 기반 준비와 사용자 기능, 의존 순서를 구분한다. G4는 사용자 승인을 기본으로 하며, 결과·구현 승인 또는 유효한 `auto-with-audit` 정책이 있으면 분리된 검증자가 목록·AC·의존성과 범위 준수를 감사한 뒤 통과시킨다. **G4 통과는 외부 등록 권한이 아니다.**

정확한 외부 등록 대상과 범위가 별도로 허용되어 있으면 실제 repo/owner/project·인증·중복을 확인하고 결과 URL과 보드 상태를 재조회한다. 부분 실패를 보존하고 재시도에서 중복 생성하지 않는다. 권한/네트워크가 없으면 로컬 `issues.md`만 완료한다.

출력은 spec-original·interview·spec-fixed·prd·issues와 게이트별 모드·결정 출처·근거·감사 결과다. 실제 생성했을 때만 외부 URL을 기록하고 test-scenarios 또는 tdd-loop로 인계한다.
