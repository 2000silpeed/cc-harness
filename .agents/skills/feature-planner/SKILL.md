# 아이디어를 실행 가능한 이슈로

`docs/harness/templates.md`, `docs/methods/requirements-interview.md`, `docs/methods/planning.md`를 읽는다. 세 단계와 네 승인 게이트를 따른다.

## 1. 요구사항 인터뷰

입력: 대상 feature의 spec-original.md와 실제 코드. 원본이 없으면 사용자 요청을 보존한다.
한 번에 하나씩 묻고 판단 질문에는 추천과 이유를 제시한다. 이미 답한 사실은 반복하지 않는다.
확인 영역: 주 사용자, 최소 사용 흐름 세 가지(대상에 맞게), 저장과 기존 구조, 최대/빈값/중복/동시성, 오류 표시, 기존 UI 재사용, 응답 시간·데이터 크기, 다음 기능에 미치는 영향.
같은 의미의 용어를 코드·문서·대화에서 일치시키고 spec-fixed에 용어 정의와 결정 이유를 적는다.
[GATE G1] 사용자가 spec-fixed를 확정한 근거 전에는 설계 결정을 확정하지 않는다. 기술 선택 위임은 요구사항 승인으로 간주하지 않는다.

## 디자인 연결

요구사항상 UI가 필요하면 기존 화면 유무와 관계없이 design-system의 문서 작성 절차로 design.md와 공통 기준을 준비한다. Figma나 참고 화면이 없으면 제안임을 표시하고 사용자 검토를 받으며 관찰 결과를 꾸미지 않는다. UI가 불필요한 기능이면 해당 없음과 이유를 기록한다.

## 2. PRD와 ADR

입력: 확정 spec-fixed·존재하는 design.md·실제 코드.
먼저 개요, 사용자 스토리, 기술 결정(미정), Out of Scope, 용어 정의 뼈대를 만든다.
최소 세 아키텍처 안을 다음 일곱 기준으로 비교한다: 데이터 구조, API 레이어 변경점, 상태관리 변경점, 핵심 동작, 컴포넌트 구조, 기존 패턴 일관성, 테스트 용이성.
[GATE G2] 사용자의 기술안 선택 근거를 기다린다. 의미 없는 대안이나 AI 선택을 사용자 선택으로 기록하지 않는다.
선택을 Context·Decision·Alternatives(각각 거부 이유)·Consequences(장단점 모두)의 ADR로 PRD에 기록한다.
이번에 하지 않을 것을 구체적으로 나열한다.
[GATE G3] 사용자가 Out of Scope를 확정한 뒤 이슈 분해로 진행한다.

## 3. 이슈 분해와 선택적 외부 등록

입력: 승인 PRD와 GitHub 보드 정보(외부 등록할 때).
각 이슈는 독립 TDD가 가능하고 사용자에게 보여줄 동작이 있는 수직 슬라이스로 만든다. API→상태→UI 수평 분할만 하지 않는다.
반나절~하루 크기를 출발 기준으로 너무 크거나 작은 이슈를 조정하고 선행 이슈 결과가 후행 입력이 되도록 순서를 정한다. 역방향 개발을 계획하지 않는다.
AC는 Given–When–Then으로 관찰 가능한 결과를 적는다. 사용자 기능과 필요한 기반 준비 작업은 구분한다.
[GATE G4] 사용자가 목록·수직 슬라이스·AC·의존성을 확인하기 전 등록하지 않는다.
외부 등록 요청이 있으면 실제 repo/owner/project·인증·기존 중복을 확인하고 gh 또는 허용된 도구로 이슈와 보드 항목을 생성한다. Todo 상태가 실제 설정됐는지 조회한다.
이슈만 생성되고 보드 추가가 실패하면 URL과 미완료 상태를 보존한다. 재시도 시 이미 만든 이슈를 중복 생성하지 않는다. 권한/네트워크가 없으면 issues.md를 완료하고 원격 등록은 미실행으로 남긴다.

출력: spec-original·interview·spec-fixed·prd·issues와 승인 근거, 실제 등록했을 때만 URL·보드 상태. 이후 test-scenarios 또는 tdd-loop로 인계한다.
