# PM 프로그램 관리 도구 · 인터뷰와 회고

상태: D29로 [spec-fixed.md](spec-fixed.md)의 합의 요구사항 확정(G1 승인). 기술안 선택 대기. 아래 과거 미승인 표시는 당시 기록이다.

질문은 한 번에 하나씩 진행했다. 아래의 질문은 요지이며, 따옴표 안의 사용자 답변은 대화에 나온 표현이다. 짧은 동의 답변은 그 직전에 제시한 제안과 함께 해석한다.

## 2. 과제 체크포인트

### AI 추천과 사용자의 결정이 달랐던 질문

**Q5의 진행 상태가 달랐다.**

- AI 추천: 개발 대기 → 개발 중 → 개발 완료 → 이관 완료.
- 사용자 결정: 개발 대기 → 개발 중 → 개발 완료 → **테스트 완료** → 이관 완료.
- 의미: “개발이 끝남”과 “테스트까지 끝남”을 PM이 구분해야 한다는 업무 요구가 반영됐다. 단순히 AI의 안을 그대로 채택한 것은 아니다.
- 다른 질문에서 사용자가 추천에 반대했다고 꾸며 기록하지 않는다.

### 인터뷰에서 드러난 누락과 엣지 케이스

| 상황                                             | 인터뷰에서 정리한 대응                      | 근거                                                        |
| ------------------------------------------------ | ------------------------------------------- | ----------------------------------------------------------- |

| 개발 예정일이 정해지지 않음                      | 등록 허용, 일정 미정 표시, 개발 막대 미표시 | Q7                                                          |

사용자가 인터뷰 전 미처 생각하지 못했다고 직접 확인한 부분은 **예정일 누락**이다. 다른 항목은 인터뷰에서 다룬 예외이며, 사용자가 이전에 몰랐다고 단정하지 않는다.

### 다시 진행한다면 바꿀 접근

아래는 인터뷰 과정에 대한 **AI의 회고 제안**이며, 사용자가 직접 말한 소감이 아니다.

1. 실제 관리 목록의 예시 1~3개를 먼저 받는다. 이번에도 LE / ZGWLEJ10000 예시가 나온 뒤에야 “프로그램”의 관리 단위와 날짜 의미가 구체화됐다.
2. 단일 프로젝트·PM 직접 운영·PC 한 대라는 범위를 먼저 확정한다. 이번에는 프로젝트 수와 사용 환경을 Q8~Q9에서 확인했다.
3. 이미 명확한 운영 전제를 반복 확인하기보다 중복, 날짜 누락, 테스트 실패 같은 결과가 달라지는 질문을 우선한다. Q10의 “당연하지”라는 답변 뒤에는 실제 판단이 필요한 예외로 질문을 좁혔다.
4. 예정일과 실적을 처음부터 나눠 필드를 정리한다. 모르는 날짜를 예시 값이나 오늘 날짜로 채우지 않는다.
5. 기능을 더 붙이기보다 “이번에 하지 않을 것”을 조기에 적는다. 다중 프로젝트, 팀 협업, 변경 이력 같은 확장을 막는다.
6. 인터뷰에서 합의한 사실과 문서 작성자가 보완한 제안을 나눈 뒤, 사용자에게 최종 정의서를 확인받는다.

## 3. 완료와 미완료의 구분

### 후속 사용 환경 확인

- D33: 모듈·담당자·진행 상태 필터 제안에 사용자가 “승인하고 나머진 기본적인 내용이라 추천안대로 승인할게”라고 답했다. 기본 동작 추가 질문을 반복하지 않고 spec-fixed.md의 D33 표에 위임으로 선택한 추천안을 명시했다. 검색·필터 결합, 확인 후 삭제, Excel 신규 일괄 추가·전체 검증, JSON 백업 등은 개별 응답이 아닌 이 위임에 근거한다. 유료 서비스·외부 등록·구현·이슈 목록 승인으로 확대하지 않는다.

- D32: 검색창 하나에서 모듈·프로그램명·담당자·변경 유형을 통합 검색하고 일부 글자로도 찾는 제안에 사용자가 “좋습니다”라고 답했다. 검색창을 여러 개 두지 않고 주요 정보를 찾게 하려는 제안이다.

- D29: D01–D28의 합의 사항을 요약하고 요구사항 확정 후 기술안 선택으로 넘어갈지 물었으며 사용자가 “좋습니다.”라고 답했다. G1만 승인됐으며 G2·G3·G4 및 구현·외부 등록은 별도다.

- D28: 두 탭의 동시 수정에 따른 덮어쓰기를 막기 위해 한 탭에서만 편집을 허용하고 다른 탭에는 안내하는 제안에 사용자가 “좋습니다”라고 답했다. 잠금 구현과 종료 후 인계 방식은 기술 설계 사항이다.

- D27: 실제 완료일이 예정일과 달라도 그대로 저장하고 예정일을 자동 변경하지 않는 제안에 사용자가 “네 당연히 다를수 있지”라고 답했다. 계획과 실적의 차이를 허용하며 P02의 자동 보정 금지를 확정했다.

- D26: 모듈·프로그램명을 대문자로 통일해 le와 LE를 같은 값으로 처리하는 제안에 사용자가 “네!”라고 답했다. 초기 P01의 대소문자 유지 제안을 변경했다. 앞뒤 공백 제거 후 대문자로 통일한 값을 저장·중복 비교에 사용한다.

- D25: 모듈·프로그램명 앞뒤의 불필요한 공백을 저장할 때 제거해 공백만 다른 중복 등록을 막는 제안에 사용자가 “당연 승인”이라고 답했다. 내부 공백과 대소문자 처리는 이번 질문에 포함하지 않았다.

- D24: 상태를 개발 완료로 바꿔도 오늘 날짜를 자동 입력하지 않고 실제 완료일을 PM이 직접 입력하는 제안에 사용자가 “네”라고 답했다. 상태 정리일과 실제 완료일이 다를 수 있다는 것이 AI 추천 이유다.

- D23: 개발 일정 미정이어도 이관 예정일이 있으면 간트에 이관 날짜 표식만 표시하는 제안에 사용자가 “승인”했다. 개발 기간을 추정하지 않고 알려진 이관 계획을 보여주기 위한 규칙이다.

- D22: 개발 완료에서 개발 중으로 되돌려도 실제 완료일을 자동 삭제하지 않고 PM이 직접 수정하는 제안에 사용자가 “네”라고 답했다. 의도치 않은 기록 삭제 방지가 AI 추천 이유다. 날짜 자동 입력이나 이관 단독 표식에 대한 승인으로 확대하지 않는다.

- D21: “존재하지 않는 날짜나 개발 시작 예정일이 완료 예정일보다 늦은 입력은 막고, 시작·완료가 같은 날인 일정은 허용” 제안에 사용자가 “승인해”라고 답했다. P02의 계획·실적 자동 보정 여부는 이 질문에 포함하지 않았다.

- D20: “저장에 실패하면 성공으로 표시하지 않고, 입력 내용은 유지한 채 오류와 재시도 방법을 안내” 제안에 사용자가 “승인”했다. 미저장 초안의 앱 종료 후 복구까지 합의한 것은 아니다.

- D18: 사전 확인 후 백업 내용으로 현재 목록 전체를 교체하는 복원 방식을 제안했고 사용자가 “승인”했다. 병합 시 중복·충돌 처리를 피하려는 AI 추천이며 사용자 고유의 결정 이유는 별도로 제시되지 않았다.
- D19: 손상·형식 불일치·중복 프로그램이 있는 백업은 복원을 중단하고 기존 데이터를 보존하는 제안에 사용자가 “네”라고 답했다. 저장 실패 안내나 파일 형식까지 승인한 것으로 확대하지 않는다.

D17: “처음 한 번은 인터넷에 연결해 앱을 준비하고, 이후에는 오프라인으로 사용하는 방식도 괜찮나요?”에 사용자가 “그럼요”라고 답했다. 최초 온라인 준비를 허용하며 구체적인 기술안 승인으로 확대하지 않는다.

| --- | --- | --- | --- |

후속 결정 D12: “모듈·프로그램명·진행 상태만 필수, 새 항목은 개발 대기를 기본으로 제시하되 변경 가능, 담당자와 날짜 등은 나중에 입력” 제안에 사용자가 “동의”했다. 일정 확정 전 등록을 허용하기 위한 규칙이다. P01의 공백·대소문자·중복 처리와 나머지 제안 및 전체 문서 승인은 포함하지 않는다. 아래 완료 기록은 최초 인터뷰 시점이며 이후 PRD 초안은 작성됐다.
