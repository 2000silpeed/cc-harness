# PM 프로그램 관리 도구 · 요구사항 정의서

**상태: 요구사항 확정(G1 승인) / 기술안 선택 전**

승인 근거 D29: D01–D28 및 합의 사항 요약을 제시하고 “요구사항을 확정하고 기술안 선택 단계로 넘어갈까요?”라고 물었으며 사용자가 “좋습니다.”라고 답했다. P01–P04는 후속 결정으로 수정·보완된 규칙을 기준으로 확정한다. 아래 개별 기록의 미승인 표시는 각 질문 당시의 이력이며 이 G1 승인으로 대체한다. 기술안·보강 제외 범위(G3)·이슈·구현 승인은 별도다.

## 후속 확정 D12 · 등록 필수 항목

- 사용자 답변: 필수 항목과 기본 상태 질문에 “동의”.
- 모듈·프로그램명·진행 상태만 필수로 한다.
- 새 항목은 개발 대기를 기본값으로 제시하며 PM이 변경할 수 있다.
- 담당자·날짜·변경 유형 등 나머지 항목은 나중에 채울 수 있다.
- 아래 P01 중 공백·대소문자·중복 처리까지 승인한 것은 아니다.

- 최초 입력: [spec-original.md](spec-original.md)
- 질문·답변·추천 차이·회고: [interview.md](interview.md)
- 적용 절차: 프로젝트 `feature-planning-workflow.md`의 단계 1. 이번 산출물은 요구사항 문서이며 앱 구현이 아니다.

## 1. 목적과 사용자

### 최신 확정 D33 · 필터와 기본 동작 일괄 위임

사용자 “승인하고 나머진 기본적인 내용이라 추천안대로 승인할게”를 근거로 모듈·담당자·진행 상태 필터를 확정하고, 아래 기본 동작을 AI 추천안으로 정했다. 각 세부 항목에 개별 답변을 받은 것은 아니다. 기존 범위 안의 동작 결정이며 외부 게시·유료 서비스·구현 또는 이슈 목록 승인이 아니다. 앞선 미정 기록 중 아래와 겹치는 항목은 이 결정을 우선한다.

| 영역 | 위임에 따라 채택한 기본 동작 | 이유 |
| --- | --- | --- |
| 검색 | 앞뒤 공백 제거, 대소문자 무시, 입력 전체를 부분 문자열로 네 필드 중 하나 이상에서 찾는다. 빈 검색은 전체 표시 | 여러 검색어 문법 없이 예측 가능하게 검색 |
| 필터 | 모듈·담당자·진행 상태는 각각 단일 선택, 기본은 전체. 담당자는 미지정 선택 제공. 서로 다른 필터와 검색은 AND로 결합 | 선택한 조건을 모두 만족하는 목록 표시 |
| 결과 | 목록과 간트에 동일 결과·순서를 적용. 결과 수와 조건 초기화 제공. 0건은 안내만 표시하고 원본은 보존 | 대응 행 불일치와 데이터 삭제 오인 방지 |
| 삭제 | 한 행씩 식별 정보를 보여주고 확인 후 영구 삭제. 취소하면 유지. 확인창에 백업 없이는 복구할 수 없음을 안내하며 휴지통·일괄 삭제는 이번에 제외 | 작은 도구의 삭제 범위를 명확히 제한 |
| Excel 업로드 | .xlsx 템플릿 다운로드·업로드 제공. 관리 필드와 같은 고정 열 이름을 사용하며 임의 열 매핑은 제외. 적용 전 미리보기·행 수·행/필드별 오류 표시 | 기존 Excel을 템플릿에 맞춰 안전하게 가져오기 |
| 업로드 충돌 | 앞뒤 공백 제거·대문자 통일 후 파일 내부 또는 기존 목록과 식별 키가 겹치면 오류. 기존 행을 덮어쓰지 않는다 | 중복 등록 정책 일관성 유지 |
| 업로드 적용 | 검증 완료 후 사용자 확인으로 신규 행만 일괄 추가. 오류가 하나라도 있으면 전체 미적용. 취소·저장 실패 시 기존 목록 보존. 빈 파일은 적용하지 않음 | 부분 성공·조용한 덮어쓰기 방지 |
| 업로드 값 | 수동 입력과 같은 필수·날짜 검증. 빈 상태는 개발 대기. 날짜는 템플릿의 YYYY-MM-DD 텍스트 또는 날짜 셀을 날짜 전용 값으로 처리. 수식 셀은 오류로 안내하고 실행하지 않음 | 날짜 시간대 이동과 수식 처리 혼동 방지 |
| 백업 | 버전·내보낸 시각·전체 프로그램 목록을 담는 JSON 파일. 필터 결과와 무관하게 전체 백업. 복원은 기존 확인·교체·검증 규칙 적용 | Excel 신규 추가와 전체 복원 구분 |
| 간트 | 초기에는 오늘이 포함된 월을 표시하고 이전/다음 월·오늘 이동 제공. 검색·필터는 유지하며 날짜가 표시 범위 밖인 행도 목록에서 제거하지 않음 | 범위 이동을 단순화하고 누락 방지 |
| 편집 | 저장 전 취소·다른 행 이동 시 변경이 있으면 폐기 확인. 자동 저장은 하지 않음 | 저장/취소 의미를 명확히 유지 |

기본 검증 데이터는 약 100개다. 최대 용량·업로드 파일 크기 제한·라이브러리·회사 보안 정책·지원 버전은 기술 검증 사항이며 측정 전 성능 보장을 하지 않는다.

### 추가 기능 수락 기준

| ID | Given / When / Then |

| AC14 | Given 네 검색 필드 중 하나에 일치하는 부분 문자열이 있고, When 대소문자와 앞뒤 공백이 다른 검색어를 입력하면, Then 해당 프로그램을 찾는다. |

| AC19 | Given 업로드 적용 중 저장 실패가 발생하고, When 결과를 확인하면, Then 기존 데이터는 보존되며 성공으로 안내하지 않는다. |
| AC20 | Given 검색·필터가 적용돼 있고, When 백업하면, Then 전체 목록이 포함된다. 지원하지 않는 백업 버전의 복원은 거부하고 기존 데이터를 보존한다. |

### 후속 확정 D32 · 통합 검색

사용자 “좋습니다”로 검색창 하나에서 모듈·프로그램명·담당자·변경 유형을 통합 검색하고 일부 글자만 입력해도 찾을 수 있게 하는 규칙을 확정했다. 여러 검색어의 결합 방식·검색 대소문자 처리·필터와의 조합은 별도로 정한다.

### 후속 변경 D30–D31 · 기술 선택과 핵심 기능 추가

- D30: 사용자는 “예쁜 디자인을 원해 C로 간다”라고 답해 React + TypeScript + IndexedDB를 선택했다. 시각 품질은 별도 화면 검증이 필요하다.
- D31: 사용자는 “그 기능들은 다 포함해야지”라고 답해 검색·필터·프로그램 삭제·Excel 업로드를 첫 버전 필수 범위로 지정했다. 기존 AI의 제외 제안을 철회한다.
- D29로 승인된 기존 요구사항은 유지한다. 추가 네 기능의 검색 대상·필터 기준·삭제 복구·Excel 형식과 오류/중복 처리는 후속 질문으로 확정한다. G1은 추가 범위에 한해 보완 중이며 G3은 아직 미확정이다.

### 후속 확정 D28 · 복수 탭 편집 제한

사용자 “좋습니다”로 동일 데이터에 대한 편집은 한 탭에서만 허용하고 다른 탭에는 안내를 표시하도록 확정했다. 동시 수정에 따른 덮어쓰기를 방지하기 위한 규칙이다. 잠금 획득·해제·탭 종료 후 인계 방식은 기술 설계에서 정하며, Chrome과 Edge 사이의 데이터 공유를 뜻하지 않는다.

### 후속 확정 D27 · 계획과 실적의 차이

사용자 “네 당연히 다를수 있지”로 실제 개발 완료일이 개발 완료 예정일과 달라도 그대로 저장하고 예정일을 자동 변경하지 않는 규칙을 확정했다. 지연·조기 완료는 허용하며 날짜 자체의 유효성 검사는 유지한다. P02의 계획·실적 자동 보정 금지는 승인됐다.

### 후속 확정 D26 · 식별 값 대문자 통일

사용자 “네!”로 모듈·프로그램명을 대문자로 통일하도록 확정했다. 저장·중복 비교에는 앞뒤 공백 제거 후 대문자로 변환한 값을 사용하므로 le와 LE는 같은 식별 값이다. 초기 P01의 대소문자 유지 제안을 대체한다. 담당자·변경 유형에는 이 규칙을 적용하지 않는다.

### 후속 확정 D25 · 식별 값 앞뒤 공백

사용자 “당연 승인”으로 모듈·프로그램명은 저장 시 앞뒤 공백을 제거하고, 제거한 값으로 중복을 비교하도록 확정했다. 내부 공백 제거·대소문자 변환까지 승인한 것은 아니다. P01의 앞뒤 공백 처리 미정은 해소됐다.

### 후속 확정 D24 · 실제 완료일 직접 입력

사용자 “네”로 상태를 개발 완료로 바꿔도 오늘 날짜를 자동 입력하지 않고 실제 개발 완료일은 PM이 직접 입력하도록 확정했다. 상태를 정리하는 날과 실제 완료한 날을 구분한다. P03의 해당 자동 입력 금지 규칙은 승인됐다.

### 후속 확정 D23 · 이관 단독 표식

사용자 “승인”으로 개발 일정이 미정이어도 이관 예정일이 있으면 간트에 해당 날짜 표식만 표시하도록 확정했다. 개발 기간을 추정하거나 개발 막대를 만들지 않는다. P03의 이관 단독 표식은 승인됐으며 상태 변경 시 날짜 자동 입력 여부는 별도 미정이다.

### 후속 확정 D22 · 상태 되돌림과 실제 완료일

사용자 “네”로 개발 완료에서 개발 중으로 되돌려도 실제 개발 완료일을 자동 삭제하지 않고, 필요하면 PM이 직접 수정하는 규칙을 확정했다. P03의 해당 날짜 보존 규칙과 AC11은 승인됐다. 상태 변경 시 날짜 자동 입력 여부나 이관 단독 표식까지 이번 답변으로 확정하지 않는다.

### 후속 확정 D21 · 날짜 유효성

사용자 “승인해”로 존재하지 않는 날짜와 개발 시작 예정일이 개발 완료 예정일보다 늦은 입력은 거부하고, 시작·완료 예정일이 같은 날인 일정은 허용하는 규칙을 확정했다. P02 중 날짜 유효성·기간 순서·당일 일정 허용이 승인됐으며, 계획과 실적의 자동 보정 여부까지 이 답변으로 확정하지 않는다.

### 후속 확정 D20 · 저장 실패

사용자 “승인”으로 저장 실패 시 성공으로 표시하지 않고, 입력 내용을 유지하며 오류와 재시도 방법을 안내하는 규칙을 확정했다. P04의 저장 실패 안내는 더 이상 미정이 아니다. 입력 유지가 앱 종료 후 미저장 초안 복구까지 보장한다는 뜻은 아니다.

### 후속 확정 D18–D19 · 백업 복원

- D18: 백업 복원은 현재 목록 전체를 백업 내용으로 교체하며 교체 전에 사용자 확인을 받는다. 사용자 답변 “승인”. 기존 목록과 병합하지 않는다.
- D19: 손상·형식 불일치·중복 프로그램이 있는 백업은 복원을 중단하고 현재 데이터를 그대로 보존한다. 사용자 답변 “네”.
- P04의 위 복원 규칙은 승인됐다. 로컬 저장 실패 안내와 백업 파일 형식·버전 등은 이 답변으로 확정하지 않는다.

### 후속 확정 D13–D16

후속 결정 D17: 최초 한 번 인터넷에 연결해 앱을 준비하고 이후 오프라인으로 사용하는 방식을 허용한다. 사용자 답변 “그럼요”. 아래 D16의 최초 준비 조건 미정은 이 결정으로 해소하며, 구체적인 설치·실행 기술은 아직 선택하지 않았다.

- D13: 동일 모듈+프로그램명 중복 등록을 막고 기존 항목 수정을 안내한다. 사용자 답변 “동의해 이미 이전에 얘기되었던 거야”. 기존 한 행 관리 합의를 재확인한 것이며 공백·대소문자 정규화까지 승인한 것은 아니다.
- D14: 초기 예상 프로그램 수는 약 100개. 최대 개수 제한이나 성능 보장 수치가 아니다.
- D15: Windows의 Chrome을 기본 사용 환경으로 하고 Edge도 지원 대상으로 한다. 버전과 회사 PC 정책은 미확인이다.
- D16: 인터넷이 끊겨도 앱 실행·입력·수정이 가능해야 한다. 최초 설치·준비까지 오프라인이어야 하는지는 아직 확인하지 않았다.

아래 초기 미정 항목 중 위 결정과 겹치는 부분은 이 후속 기록으로 갱신한다. 전체 요구사항 승인과 기술 선택은 여전히 대기 중이다.

PM이 **프로젝트 하나에 속한 프로그램의 담당자, 진행 상태, 개발 일정과 이관 예정일을 목록과 간트 차트로 관리**한다. PM이 직접 등록·수정하고 본인의 PC 한 대에서 사용한다. 계정·협업 서버 없이 작은 관리 도구로 시작한다. (D01, D02, D08, D09)

핵심 질문은 “어떤 프로그램을 누가 맡고 있고, 지금 어느 단계이며, 언제 개발·이관할 예정인가?”이다.

| 이관 예정일        | 이관하기로 계획한 날짜. 이관 완료를 증명하는 날짜가 아님                               |

| 백업·복원          | 데이터를 별도로 보관하고 되불러오는 기능. 자동 클라우드 동기화를 뜻하지 않음           |

| 개발 완료 예정일 | 간트 막대의 끝           | 값 미제공. 사용자가 누락을 확인하고 항목 추가       |

위 표는 인터뷰 예시이며 앱에 저장한 실제 레코드가 아니다. `26년` 표기는 이 인터뷰에서 2026년으로 정리했다. 입력되지 않은 예정일을 실제 완료일로 대신 채우지 않는다. (D03, D04, D06, D07)

테스트 완료는 **상태**로 추가했다. 테스트 완료일이나 실제 이관 완료일 등의 추가 날짜 필드는 현재 합의된 항목에 포함하지 않는다.

## 4. 합의한 기능과 규칙

### F01. 프로그램 목록·등록·수정

- PM이 3절의 항목을 직접 입력하고 목록에서 프로그램별 정보를 확인한다. (D01~D03)
- 한 프로젝트의 프로그램만 다룬다. 프로젝트 생성·선택·전환 화면은 범위에서 제외한다. (D08)
- 동일한 모듈+프로그램명 조합은 한 행만 유지한다. 추가 개발·수정이 생기면 기존 행을 수정하고 변경 건별 이력을 별도 관리하지 않는다. (D11)
- 중복이 발견됐다는 이유로 기존 값을 조용히 덮어쓰는 동작은 합의한 것이 아니다. 중복 입력의 안내·수정 연결 방식은 제안 P01에 구분한다.

### F02. 진행 상태

표시 순서는 다음 5단계다. (D05)

```text
개발 대기 → 개발 중 → 개발 완료 → 테스트 완료 → 이관 완료
```

- PM이 직접 상태를 변경한다. 이 순서는 업무 단계 설명이며 순방향 이동만 강제하는 규칙이 아니다. (D10)
- 개발 완료 뒤 테스트에서 문제가 발견되면 개발 중으로 되돌릴 수 있다. (D10)
- 예정일이 지났다는 이유로 자동 완료 처리하지 않는다. (D10)
- 일정 미정은 위 5단계에 추가되는 여섯 번째 진행 상태가 아니다. (D05, D07)
- 상태를 되돌렸을 때 기존 실제 완료일을 어떻게 다룰지는 제안 P03으로 명시한다.

### F03. 전체 타임스케줄

- 프로그램별 개발 시작 예정일~개발 완료 예정일을 간트 막대로 표시한다. (D06)
- 이관 예정일을 함께 표시해 개발 일정과 이관 계획을 확인할 수 있게 한다. (D06)
- 개발 시작 예정일 또는 개발 완료 예정일이 없으면 등록은 허용하고 목록에 일정 미정을 표시한다. 개발 막대는 그리지 않으며 임의의 날짜로 보완하지 않는다. (D07)
- 일정 미정일 때 이관 예정일만 있는 경우의 표현은 제안 P03으로 구분한다.

### F04. 사용 환경·저장·백업

- PM 본인의 PC 한 대에서 웹브라우저로 사용한다. (D09)
- 입력 데이터를 해당 PC에 저장하고, 다시 열어 이어서 관리할 수 있어야 한다. 로그인·원격 서버·클라우드 동기화는 이번 범위에서 제외한다. (D09)
- 데이터 손실에 대비해 백업과 복원 기능을 제공한다. 파일 형식과 저장 기술은 아직 선택하지 않았다. (D09)
- 복원 시 덮어쓰기 여부와 저장 실패 처리 등은 제안 P04로 구분한다.

## 5. 최소 사용 시나리오

1. **등록 후 전체 일정 확인:** PM이 프로그램을 등록하고 담당자·계획 날짜를 입력한다. 목록과 간트 차트에서 그 프로그램의 개발 기간과 이관 예정일을 확인한다.
2. **개발·테스트 진행 갱신:** PM이 개발 완료, 테스트 완료 등 실제 업무에 맞게 상태를 수정한다. 테스트에서 재개발이 필요하면 개발 중으로 되돌린다.
3. **일정 미정 항목 보완:** PM이 예정일 없이 프로그램을 먼저 등록한다. 나중에 시작·완료 예정일을 입력하면 개발 막대가 표시된다.
4. **다음 작업일에 이어서 관리:** PM이 도구를 다시 열어 이전 데이터를 확인하고 필요할 때 백업한다. 데이터 손실 시 복원 절차를 사용한다.

이는 합의된 요구사항을 사용 흐름으로 정리한 것이며, 이미 구현된 화면의 설명이 아니다.

## 6. 추가 제안 · 최종 검토에서 확인 필요

아래는 인터뷰의 빈틈을 메우기 위한 **AI 제안**이다. 사용자가 아직 개별적으로 답하지 않은 규칙이므로 합의된 사실과 혼동하지 않는다. 승인 전에는 이 규칙에 의존하는 구현을 시작하지 않는다.

| ID  | 제안                                                                                                                                                                                                                                                                                                            | 이유                                                                            |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| P01 | 모듈·프로그램명·진행 상태는 필수. 기본 상태는 개발 대기이며 변경 가능하다. 다른 필드는 추후 입력 가능하다. 식별 값은 앞뒤 공백을 제거하고 대문자로 통일한 뒤 조합을 비교한다(D25·D26). 중복 등록·식별 값 변경으로 충돌하면 저장을 막고 기존 행 수정을 안내한다. | 일정 미정 등록을 유지하면서 빈 식별 값·중복·조용한 덮어쓰기를 방지 |
| P02 | 달력에 없는 날짜와 개발 시작 예정일이 개발 완료 예정일보다 늦은 입력은 거부한다. 시작일과 완료일이 같으면 당일 일정으로 표시한다. 계획과 실적의 불일치는 자동 보정하지 않는다.                                                                                                                                  | 잘못된 기간과 실제 지연·조기 완료를 구분                                        |
| P03 | 상태 변경만으로 날짜를 자동 입력·삭제하지 않는다. 재개발 후 실제 개발 완료일은 PM이 직접 고친다. 개발 막대가 없는 일정 미정 항목도 이관 예정일이 있으면 해당 날짜 표식은 보여준다.                                                                                                                              | 사실인 날짜를 자동으로 잃지 않으면서 미정인 개발 기간과 알려진 이관 날짜를 분리 |
| P04 | 백업은 전체 목록의 시점 복사본으로 취급한다. 복원 전에 기존 데이터 교체를 명시적으로 확인받는다. 손상·형식 불일치·중복 키가 있는 백업은 거부하고 현재 데이터를 보존한다. 로컬 저장 실패는 화면에 알리고 저장 성공으로 표시하지 않는다.                                                                          | 복원 중 조용한 데이터 유실과 저장 실패의 오인을 방지                            |

아직 정하지 않은 기술·규모 사항은 PRD 단계에서 확인한다: 구체적인 브라우저·실행 방식, 완전 오프라인 제공 여부, 저장 기술과 백업 형식, 예상 프로그램 수, 지원해야 할 최대 규모와 허용 응답 시간. 성능 수치나 브라우저 호환성을 임의로 보증하지 않는다.

## 7. 이번 범위에서 하지 않는 것

인터뷰에서 제외한 범위:

- 다중 프로젝트 생성·전환·통합 일정 관리. (D08)
- 다른 PC와의 동기화, 담당자별 계정, 팀 공동 편집, 원격 서버·로그인. (D09)
- 변경 건별 프로그램 행과 변경 이력 관리. (D11)
- 날짜에 따른 자동 상태 완료 처리. (D10)

작은 도구라는 목적을 유지하기 위해 **이번 검토본에 추가하지 않은 기능**:

- 진행률 퍼센트, 추가 상태인 보류·취소, 알림·승인 흐름.
- 프로그램 간 선후행 의존성, 간트 드래그 편집, 인력·비용 분석.
- 사용자 정의 정렬은 아직 범위 밖이다. 검색·필터·프로그램 삭제·Excel 업로드는 D31로 첫 버전에 포함한다. 휴지통 여부는 삭제 정책에서 결정한다.
- SAP·OData 등 외부 시스템 연동. ODATA라는 변경 유형 입력만으로 연동 요구를 추정하지 않는다.

이 목록에 필요한 기능이 있다면 최종 검토에서 범위를 수정한다. 요청되지 않은 기능을 구현자가 임의로 추가하지 않는다.

## 8. 수락 기준

아래 기준은 **구현 후 확인할 동작**이다. 아직 실행한 앱 테스트가 아니다. 제안 ID가 붙은 항목은 해당 제안 승인 후 기준으로 확정한다.

| ID   | Given / When / Then                                                                                                                                          | 근거     |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------- |
| AC01 | Given 등록할 프로그램 정보가 있고, When PM이 저장하면, Then 목록에 모듈·프로그램명·변경 유형·담당자·날짜·상태가 나타난다.                                    | D01~D04  |
| AC02 | Given 같은 모듈+프로그램명 행이 있고, When PM이 추가 변경 내용을 그 행에서 수정하면, Then 행 수는 증가하지 않고 해당 정보가 갱신된다.                        | D11      |
| AC03 | Given 개발 시작 예정일 또는 완료 예정일이 없고, When 프로그램을 등록하면, Then 목록에는 일정 미정으로 남으며 개발 막대와 임의의 보완 날짜는 생성되지 않는다. | D07      |
| AC04 | Given 개발 시작·완료 예정일과 이관 예정일이 있고, When 간트 차트를 확인하면, Then 개발 기간 막대와 이관 예정일을 함께 확인할 수 있다.                        | D06      |
| AC05 | Given 개발 완료인 프로그램이 있고, When PM이 테스트 완료로 바꾸면, Then 목록과 간트의 동일 프로그램을 확인할 때 같은 상태 값이 사용된다.                     | D05, D10 |
| AC06 | Given 개발 완료 뒤 재개발이 필요하고, When PM이 개발 중으로 변경하면, Then 이전 단계로의 변경이 허용된다.                                                    | D10      |
| AC07 | Given 예정일이 지났지만 PM이 상태를 바꾸지 않았고, When 화면을 다시 열면, Then 상태가 자동 완료 처리되지 않는다.                                             | D10      |
| AC08 | Given PC에 저장한 목록이 있고, When 같은 사용 환경에서 도구를 다시 열면, Then 이전 데이터를 이어서 관리할 수 있다.                                           | D09      |
| AC09 | Given 식별 값이 비어 있거나 기존 키와 충돌하고, When 저장을 시도하면, Then 문제를 알리고 중복 행 생성이나 기존 행의 조용한 덮어쓰기는 발생하지 않는다.       | P01      |
