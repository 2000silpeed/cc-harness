# PM Schedule Ledger · 디자인 정의

## 상태와 적용 범위

최신 사용자 검수 결정: 모듈/프로그램과 날짜의 여러 줄 배치가 많은 프로그램을 훑기 어렵다는 피드백에 따라, 사용자가 “동의해”로 한 프로그램=한 행의 조밀한 표를 승인했다. 모듈·프로그램명·담당자·변경 유형·진행 상태·시작 예정·완료 예정·실제 완료·이관 예정의 9개 열, 48px 행, 날짜 YYYY-MM-DD·빈 날짜 —를 사용한다. 미정 날짜의 의미는 접근성 이름으로도 제공한다. 긴 텍스트는 말줄임하고 클릭·키보드로 전체 값 dialog를 열 수 있다. 좁은 화면은 표 내부 가로 스크롤을 사용한다. 아래 기존 여러 줄/가변 행 제안보다 이 결정을 우선하며 저장 데이터·날짜 의미는 변경하지 않는다.

PM-00 최신 상태: 사용자 승인된 C안으로 src/에 빈 장부·등록 준비 안내를 구현했다. P01–P04 및 D33은 요구사항 승인을 받았다. 아래 초기 미선택·미승인·미구현 설명은 최초 디자인 시점의 이력이며 PM-00과 [현재 PRD](prd.md)를 우선한다. 업무 기능과 최종 사용자 디자인 승인은 별도다.

**디자인 검토용 초안.** Design Ontology Harness를 실제 실행한 결과를 PM 업무에 맞게 재정립했다. 컴포넌트 계약 통과는 사용자 디자인 승인이나 앱 기능 테스트 통과가 아니다. [기존 요구사항](spec-fixed.md)의 최종 승인 및 P01–P04 상태는 변경하지 않았다.

- 대상: 단일 프로젝트, PM 개인 PC의 프로그램 목록·등록·수정·5단계 상태·개발 간트·이관 계획·백업/복원.
- 디자인 제안: 밝은 테마, 동일 행 좌표의 장부와 간트, 선택 행에 연결된 편집 패널.
- 미실행: 실제 화면·로컬 저장·브라우저 E2E·배포. 프레임워크와 저장 기술도 미선택.
- 출처: 사용자 Digital Atelier 텍스트, 기존 PM 인터뷰, [저작 입력](ontology/brand_profile.json), [원본 대비 판단](ontology/source-policy.md).
- 컬러 권한: Semantic-os → 체크섬 검증된 Design Ontology Harness Markdown → 생성 토큰 → PM의 명시적 역할 연결. 샘플 색상을 정답으로 복사하지 않는다.

## 1. 방향: 장식보다 대조가 쉬운 작업 장부

The Curated Archive의 차분한 표면감은 유지하되, TIL을 감상하는 공간이 아니라 **어느 프로그램을 누가 맡고 언제 개발·이관하는지 같은 행에서 읽는 공간**으로 바꾼다.

| 샘플                            | 적용                                                           |
| ------------------------------- | -------------------------------------------------------------- |
| 부드러운 최소주의와 tonal depth | 배경·보조 면·선택 문맥의 명도 차이로 유지                      |
| 비대칭 에디토리얼               | 행·열·시간축 정렬로 대체; 장식적 비대칭은 금지                 |
| 56px display와 넓은 여백        | 제목 24px, 기본 데이터 15px, 제안 행 높이 48px                 |
| No-Line                         | 큰 영역은 면으로 구분; 시간축·입력·포커스에는 기능적 경계 허용 |
| Inter exclusively               | 라틴 Inter + 한글 Noto Sans KR 후보; 시스템 대체 폰트 필수     |
| 태그 칩                         | 범위 밖. 5단계 업무 상태의 텍스트 표식으로 대체                |
| Glass/gradient                  | 기본 미채택. 불투명 작업면과 단색 주 액션                      |
| 22.4px 리스트 간격              | 데이터 행에는 강제하지 않음. 명시적인 픽셀 간격 토큰 사용      |

## 2. 첫 화면과 읽는 순서

추가 범위 D31–D33: 작업바에 통합 검색, 모듈·담당자·진행 상태 필터, 조건 초기화·결과 수, Excel 가져오기를 포함한다. 목록과 간트는 같은 결과 집합을 공유한다. 선택 행에는 삭제 확인 진입점을 제공한다. 가져오기 화면은 템플릿 다운로드 → 미리보기·행별 오류 → 적용/취소 흐름이다. 삭제는 식별 정보와 복구 제한을 보여주는 확인창을 사용한다. 세부 동작은 spec-fixed.md D33을 따르며 기존 6개 생성 계약이 이 추가 화면까지 검증한 것은 아니다.

| 영역          | 내용·행동                                            | 배치·스크롤                                                 |
| ------------- | ---------------------------------------------------- | ----------------------------------------------------------- |
| 상단 작업바   | 짧은 제목, 프로그램 등록, 백업, 복원                 | 히어로·KPI·프로젝트 전환 없음                               |
| 프로그램 장부 | 모듈·프로그램명·담당자·변경 유형·상태·계획/실적 날짜 | 의미 있는 열 제목. 모듈·프로그램명 식별 영역 유지           |
| 일정 시간축   | 개발 시작~완료 예정 막대, 이관 예정일                | 장부와 행 순서·높이·세로 스크롤 공유. 가로 시간 이동은 별도 |
| 편집 패널     | 식별·업무·개발 계획·실적·이관 계획, 저장/취소        | 기본 닫힘. 데스크톱 옆 패널, 좁은 화면 전체 폭 dialog 제안  |
| 피드백        | 현재 작업 결과와 오류                                | 필드 인접 오류 + 지속되는 저장 실패 안내. 알림 센터 아님    |

패널의 선택 강조·열 폭·48px 행 높이는 새 디자인 제안이다. 긴 변경 유형으로 높이가 늘어나면 장부와 간트 양쪽에 같은 높이를 적용한다. 독립 스크롤 두 개로 대응 행이 어긋나면 실패다.

## 3. 날짜와 상태의 의미

- 상태는 개발 대기 → 개발 중 → 개발 완료 → 테스트 완료 → 이관 완료. 색이 아니라 한국어 상태명이 기준이며 이전 단계 선택도 허용한다.
- 날짜가 지났다고 자동 완료하거나 진행률을 계산하지 않는다.
- 개발 시작/완료 예정일 중 하나라도 없으면 개발 막대를 그리지 않고 ‘일정 미정’을 표시한다. 여섯 번째 업무 상태가 아니다.
- 실제 개발 완료일은 별도 데이터다. 계획 막대의 끝이나 현재 상태를 대신하지 않는다.
- 이관일은 범례가 있는 다이아몬드와 날짜 문구를 제안한다. 개발 막대가 없는 이관 단독 표식은 P03 승인 전 조건부 시안이다.
- 인터뷰의 LE / ZGWLEJ10000 / 이성운 / 실제 완료 2026-07-10 / 이관 예정 2026-09-06은 출처 있는 예시다. 시작·완료 예정일과 상태를 만들어 채우지 않는다.

## 4. 상태별 계약

| 조건             | 표현·복구                                            | 승인 경계                   |
| ---------------- | ---------------------------------------------------- | --------------------------- |
| 목록 없음        | 등록 안내와 등록 버튼; 가짜 행 없음                  | 합의 기능                   |
| 일정 미정        | 목록 문구, 같은 행 시간 공간 유지, 개발 막대 없음    | 합의 기능                   |
| 긴 값            | 식별 값 복사 가능, 줄바꿈 또는 상세에서 전체 값 확인 | 디자인 제안                 |
| 행 선택          | 양쪽 같은 행의 면 강조와 텍스트/포커스               | 디자인 제안                 |
| 중복·잘못된 날짜 | 입력 인접 오류, 첫 오류로 포커스, 초안 유지          | P01/P02 조건부              |
| 저장 실패        | 성공 메시지 금지, 지속 안내, 재시도                  | P04 조건부                  |
| 복원 요청        | 교체 대상 확인과 취소, 손상 파일 거부                | P04 조건부                  |
| 상태 되돌리기    | 선택 값 갱신, 날짜 부수효과는 별도                   | 날짜 보존 규칙은 P03 조건부 |

향후 구현은 먼저 `ontology/design-system/tokens.css`, 그다음 `runtime-theme.css`를 읽는다. 생성 토큰을 손으로 수정하지 않는다. runtime-theme은 PM의 저작한 역할 연결이며 자동 생성값을 숨기는 패치가 아니다. 원본 기준과 실제 채택값을 [검증 기록](ontology/verification.md)에 구분한다.

`npm run design:check`는 구조도와 PM 검사를 실행한다. PM은 src/app/public의 CSS·HTML·정적 TSX/JSX 스타일을 검사한다. 생성 팔레트 검사는 `node docs/features/pm-program-tracker/ontology/verify-design.mjs`이며 실제 화면 확인과는 구분한다.

## 6. 생성 결과에서 바로 채택하지 않은 것

- 전체 생성 명세의 마케팅·이미지·아이콘 기본 요구는 이 데이터 도구의 새 요구사항이 아니다.
- 자동 생성 dark 토큰은 밝은 테마 승인이나 다크 모드 기능 요구를 뜻하지 않는다. 다크 모드는 별도 검토.
- 자동 서체 설명의 Pretendard 추천보다 입력의 명시적 Inter/Noto Sans KR 계약을 우선한다.
- D31로 검색·필터·삭제·Excel 업로드를 첫 버전에 포함한다. 기존 화면안에는 해당 동작이 아직 반영되지 않았으며 세부 요구사항 확정 후 작업바·목록·가져오기·삭제 상태를 보완한다. 태그·클라우드·KPI·간트 드래그는 추가하지 않는다.
- ‘계약 complete’는 저작 필드가 완성됐다는 뜻이다. P01–P04 사용자 승인으로 승격하지 않는다.

## 7. 다음 검토

3. 승인 후 실제 화면에서 1440/768/390px, 한글·긴 식별자·200% 확대·키보드를 확인한다.
4. 데이터 보존과 복원은 실제 앱의 테스트·E2E로 별도 검증한다.
