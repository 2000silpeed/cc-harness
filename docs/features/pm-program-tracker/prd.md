# PM 프로그램 관리 도구 · PRD

상태: v0.2 기술안 선택 대기. D29의 사용자 “좋습니다.”로 합의 요구사항은 확정(G1)됐다. 기술안·보강 제외 범위·이슈·구현은 아직 승인 전이다. 아래 후속 기록의 미정 표시는 해당 시점의 이력이며 최신 결정과 승인 게이트를 우선한다.

## 1. 개요와 근거

최신 결정 D33: 사용자가 세 필터와 나머지 기본 동작을 추천안에 일괄 위임했다. 검색·필터·삭제·Excel 업로드·백업·간트 탐색의 현재 계약과 AC14–AC20은 [spec-fixed.md](spec-fixed.md)의 D33을 단일 기준으로 읽는다. 이하 해당 미정 기록은 과거 이력이며 반복 질문하지 않는다. G1 추가 범위 보완은 완료했고 C안 선택은 유지한다. 이미 제시한 제외 목록에 휴지통·일괄 삭제·임의 Excel 열 매핑을 제외하는 기본안을 적용했다. 이는 위임에 따른 범위 정리이며 이슈 목록 승인이나 구현 승인은 아니다.

최신 범위 변경 D30–D31: 사용자가 시각 품질을 중시해 C안을 선택했고, 검색·필터·삭제·Excel 업로드를 첫 버전 필수 기능으로 지정했다. 기존 요구사항 승인은 유지하되 추가 기능의 상세와 AC는 보완 중이다. 하단의 과거 미정·게이트 기록보다 이 변경과 ADR 결정을 우선한다. 이슈 분해와 구현은 아직 시작하지 않는다.

PM이 단일 프로젝트의 프로그램을 직접 등록하고 담당자·진행 상태·개발 계획과 실적·이관 계획을 목록과 간트에서 확인하는 개인용 도구다. 첫 버전은 본인 PC의 브라우저에서 데이터를 보존하고 백업·복원한다.

- 요구사항: [spec-fixed.md](spec-fixed.md). D01–D28과 후속 결정으로 보완된 P01–P04를 D29로 확정했다.
- 인터뷰 근거: [interview.md](interview.md), [최초 요청](spec-original.md).
- 화면 제안: [design.md](design.md). 색상·간격·서체·컴포넌트 값은 해당 문서를 참조하고 PRD에 복제하지 않는다.
- 실제 저장소: 협업 스킬·품질 검사·디자인 문서와 토큰이 있다. 앱 소스·API·DB·앱 테스트·빌드는 없다. 기존 앱 컴포넌트 재사용을 전제로 하지 않는다.
- 디자인 훅의 위반 피드백은 실제 확인했지만 이는 제품 구현이나 화면 승인 근거가 아니다.

## 2. 사용자 스토리와 관찰 결과

추가 검색 요구사항 D32: PM은 검색창 하나에 일부 글자를 입력해 모듈·프로그램명·담당자·변경 유형에서 프로그램을 찾는다. 사용자 “좋습니다”로 검색 필드와 부분 검색을 확정했다. D31의 검색 대상 미정은 이 결정으로 해소하며, 여러 검색어·대소문자·필터 조합은 아직 미정이다.

| ID   | 사용자 행동과 목적                                        | 관찰 가능한 결과                                                   | 요구사항 / 수락 기준                    |
| ---- | --------------------------------------------------------- | ------------------------------------------------------------------ | --------------------------------------- |
| US01 | PM이 프로그램과 담당자·일정을 등록한다                    | 새 행에 입력 정보가 나타나고 계획 기간이 있으면 간트에 대응한다    | F01·F03 / AC01·AC04                     |

## 3. 데이터와 동작 계약

관리 필드는 모듈, 프로그램명, 변경 유형, 담당자, 개발 시작 예정일, 개발 완료 예정일, 실제 개발 완료일, 이관 예정일, 진행 상태다. 동일 모듈+프로그램명은 한 행으로 관리한다. 내부 ID 도입 여부는 기술 상세 설계에서 결정한다.

- 상태: 개발 대기 → 개발 중 → 개발 완료 → 테스트 완료 → 이관 완료. 이전 단계로 변경 가능하며 날짜 경과로 완료 처리하지 않는다.
- 간트: 개발 시작 예정일~완료 예정일을 표시한다. 둘 중 하나가 없으면 일정 미정이며 개발 막대를 만들지 않는다.
- 실제 완료일을 예정일 대신 사용하지 않는다. 테스트 완료는 상태이며 추가 날짜 필드가 아니다.
- 인터뷰 예시 LE / ZGWLEJ10000 / 이성운은 자동 초기 데이터가 아니다. 제공되지 않은 예정일·상태를 추정하지 않는다.
- 저장은 PC 브라우저 기반이며 원격 API·로그인은 필요하지 않다. 브라우저 저장과 별도 백업은 구분한다.

### 미승인 보완 규칙

후속 승인 D27: 실제 개발 완료일과 예정일의 차이는 허용하고 예정일을 자동 변경하지 않는다. 유효한 지연·조기 완료는 오류가 아니다. D21과 함께 P02의 날짜 검증·당일 일정·계획/실적 자동 보정 금지가 확정됐다. 이전 P02 미정 표시는 이 후속 결정으로 대체한다.

후속 승인 D26: 모듈·프로그램명은 앞뒤 공백 제거 후 대문자로 통일해 저장·중복 비교한다. 초기 대소문자 유지 제안과 이전 기록의 대소문자 미정 상태를 대체한다. 담당자·변경 유형은 대상이 아니다.

후속 승인 D25: 모듈·프로그램명의 앞뒤 공백을 저장 시 제거하고 정리된 값으로 중복을 비교한다. P01의 해당 공백 처리 미정은 해소됐으며 대소문자 처리는 별도 미정이다.

후속 승인 D24: 개발 완료 상태 변경 시 오늘 날짜를 실제 개발 완료일에 자동 입력하지 않는다. 실제 완료일은 PM이 직접 입력한다. 앞선 기록의 해당 자동 입력 여부 미정은 이 결정으로 해소됐다.

후속 승인 D23: 개발 일정 미정 시에도 이관 예정일의 단독 표식을 표시한다. 개발 막대나 추정 기간은 생성하지 않는다. 아래 P03의 이관 단독 표식 미정 상태는 이 결정으로 해소됐다.

후속 승인 D22: 개발 완료에서 개발 중으로 되돌릴 때 실제 개발 완료일을 보존하고 PM이 직접 수정하도록 확정했다. P03 중 해당 동작과 AC11은 승인됐으며, 날짜 자동 입력·이관 단독 표식은 아직 별도 미정이다.

후속 승인 D21: 존재하지 않는 날짜·개발 시작 예정일이 완료 예정일보다 늦은 입력을 거부하고 당일 일정을 허용한다. 아래 P02 중 해당 날짜 검증은 확정이다. 계획과 실적의 자동 보정 여부는 별도 미정으로 남긴다.

후속 승인 D20: 저장 실패 시 성공 표시 금지, 입력 내용 유지, 오류·재시도 안내를 확정했다. 아래 P04 및 이전 후속 기록의 저장 실패 안내 미정 상태를 대체한다. 앱 종료 후 미저장 초안 복구는 포함하지 않는다. 백업 형식·버전은 여전히 기술 선택 전이다.

후속 승인 D18–D19: P04 중 사전 확인 후 현재 목록 전체 교체와 손상·형식 불일치·중복 프로그램 백업 거부 및 기존 데이터 보존을 확정했다. 아래 P04의 복원 정책은 더 이상 미정이 아니다. 로컬 저장 실패 안내·백업 파일 형식·버전은 아직 미정이다.

후속 승인 D12: P01 중 모듈·프로그램명·진행 상태 필수, 기본 개발 대기(변경 가능), 나머지 필드 추후 입력은 사용자 “동의”로 확정했다. 아래 표의 P01 중 정규화·중복 처리만 미정이며, 전체 요구사항 승인이나 기술안 선택으로 확대하지 않는다.

| 항목 | 초안에만 유지하는 제안                                                              | 결정 전 영향                     |
| ---- | ----------------------------------------------------------------------------------- | -------------------------------- |
| P01  | 식별 값·상태 필수, 기본 개발 대기, 앞뒤 공백 제거 후 대문자 통일, 충돌 시 저장 거부 | D12·D13·D25·D26 반영             |

| P03  | 상태 변경으로 날짜 자동 입력·삭제 금지, 일정 미정에서도 이관 단독 표식              | 편집 부수효과·시간축 표식 미확정 |

전체 문구와 AC09–AC13은 spec-fixed.md를 기준으로 한다. 이 초안에서 제안을 합의로 승격하지 않는다.

## 4. 기술 대안 비교 — 선택 전

세 안 모두 원격 서버 없이 동작하는 웹앱 구상이다. 패키지·버전은 아직 선택하거나 설치하지 않았다. 아래는 설계 비교이며 실측 성능 결과가 아니다.

| 비교 기준         | A. Vanilla JS + localStorage                                       | B. Vanilla JS + IndexedDB                          | C. React + TypeScript + IndexedDB                                                    |
| ----------------- | ------------------------------------------------------------------ | -------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 데이터 구조       | 버전 필드와 전체 프로그램 배열을 JSON 스냅샷으로 저장              | 레코드 저장소와 식별 키 인덱스, 백업용 직렬화 구조 | B와 같은 저장 구조에 타입 정의 추가                                                  |
| API 레이어 변경점 | 기존 API 없음. 로컬 저장 어댑터의 load/save/export/import          | 기존 API 없음. 비동기 저장 어댑터와 트랜잭션       | B의 어댑터를 UI에서 분리해 호출                                                      |
| 상태관리 변경점   | 메모리 목록과 편집 초안을 분리, 저장 후 화면 갱신                  | 비동기 읽기·쓰기 상태와 편집 초안을 직접 관리      | 목록·편집·오류를 컴포넌트 상태/reducer로 관리, 별도 전역 상태 라이브러리는 우선 제외 |
| 핵심 동작         | 작은 목록 전체 저장, 도메인 함수로 수정·간트 데이터 계산           | 레코드 갱신과 전체 복원을 트랜잭션 단위로 설계     | 저장/도메인은 B와 동일, UI 상태 변화에 맞춰 렌더링                                   |
| 컴포넌트 구조     | 작업바·장부/간트·편집 폼을 DOM 모듈로 분리                         | A의 DOM 모듈 + 비동기 저장 피드백                  | 작업바·장부/간트·편집 패널을 선언형 컴포넌트로 구성                                  |
| 기존 패턴 일관성  | 기존 앱 패턴 없음. 현재 JS 도구와 가까우며 새 런타임 의존성 최소   | 기존 앱 패턴 없음. JS 유지, 저장 코드 복잡도 증가  | 기존 앱 패턴 없음. TS·빌드·컴포넌트 검사 설정 추가 필요                              |
| 테스트 용이성     | 순수 함수/저장 어댑터를 분리해 단위 검사, DOM 흐름은 브라우저 검사 | A에 비동기·트랜잭션·스키마 변경 실패 검증 추가     | 타입·컴포넌트 검사 가능, 빌드와 테스트 환경 준비 부담 추가                           |

### 초기 AI 추천: A — 이후 사용자 C 선택

지금까지의 “범위가 크지 않고 PM 혼자 사용”이라는 합의를 기준으로 A를 우선 제안한다. 작은 기능 집합을 적은 도구로 시작할 수 있다. 다만 프로그램 수와 데이터 크기가 미정이므로 성능·용량 적합성은 보장하지 않는다. 전체 JSON 저장, 브라우저 데이터 삭제·저장 실패, 직접 DOM 상태 관리가 부담이다.

레코드별 저장·복원 원자성이 중요하거나 규모가 커지면 B가 후보다. UI 확장 및 타입 기반 유지보수가 우선이면 C를 검토한다. 어느 안도 브라우저 데이터 삭제나 별도 백업 필요성을 없애지 않는다.

### ADR-001: UI 및 로컬 저장 구조

- Context: 신규 앱이며 단일 사용자·단일 프로젝트·로컬 보존·백업/복원이 필요하다. 유지보수 인력·규모·지원 환경은 미정이다.
- Decision: C(React + TypeScript + IndexedDB). 사용자 “예쁜 디자인을 원해 C로 간다”가 선택 근거다. 버전·라이브러리·오프라인 배포 방식은 아직 미선택이다.
- Alternatives: A는 구성 단순성의 이점보다 UI를 구조화하고 다듬는 방향을 우선해 미채택했다. B는 같은 IndexedDB를 쓰지만 직접 DOM을 관리하므로 사용자가 선택한 React 기반 UI 방향과 달라 미채택했다. 이는 선택 근거에 따른 설계 해석이며 React 자체가 미적 품질을 보장한다는 뜻은 아니다.
- Consequences: 공통 컴포넌트·타입으로 화면 일관성과 변경 관리를 도울 수 있다. 대신 빌드·타입·컴포넌트 테스트와 비동기 저장 코드가 추가된다. 기존 PM 검사기의 TSX 지원 확장, 오프라인 실행, 한 탭 편집, 실제 디자인 검증이 필요하다. 자동으로 해결된 것으로 간주하지 않는다.

## 5. Out of Scope — 확정 여부 구분

기존 인터뷰에서 제외한 범위: 다중 프로젝트 전환, 계정·원격 서버·다른 PC 동기화·팀 공동 편집, 변경 건별 이력, 날짜에 따른 자동 완료 처리.

첫 버전 필수 추가 기능(D31): 검색·필터·프로그램 삭제·Excel 업로드. 검색 필드·조합 방식, 필터 기준, 삭제 확인·복구, 업로드 템플릿·열 매핑·중복·오류 처리·미리보기·적용 방식은 아직 미정이다. Excel 업로드는 기존 전체 백업 복원과 다른 기능이며 복원의 전체 교체 정책을 자동 적용하지 않는다. 요구사항과 AC를 보완한 뒤 이슈로 분해한다.

보강 제외 검토 목록: 사용자 정의 정렬, 태그, 진행률·보류/취소 상태·알림/승인 흐름, 간트 드래그·프로그램 의존성, 인력/비용 분석, SAP/OData 연동, 다크 모드. 휴지통 여부는 삭제 정책에서 정한다. 이 목록은 G3에서 사용자 검토가 필요하다. ODATA 신규 개발은 입력 설명이지 연동 요구가 아니다.

## 6. 용어

- 프로그램: 목록의 관리 대상 한 항목. 변경 작업 건과 구분한다.
- 식별 기준: 앞뒤 공백 제거 후 대문자로 통일한 모듈+프로그램명 조합(D25·D26).
- 개발 계획/실적: 시작·완료 예정일과 실제 완료일은 다른 값이다.
- 이관 예정일: 계획 날짜이며 실제 이관 완료를 증명하지 않는다.
- 일정 미정: 계획 기간이 부족한 표시이며 업무 상태가 아니다.
- 백업: 목록을 별도로 보관하는 것. 형식·교체 정책은 아직 미정이다.

전체 용어는 spec-fixed.md §2를 따른다.

## 7. 검증·위험·추가 확인

D28 확정: 동일 데이터의 편집은 한 탭에서만 허용하며 다른 탭에는 안내한다. 아래 복수 탭 정책 미정은 해소됐다. 잠금 획득 경쟁·탭 종료·비정상 종료 후 인계는 기술 설계 및 테스트에 포함한다. 브라우저 간 데이터 공유를 약속하는 요구사항은 아니다.

D17 확정: 최초 온라인 준비 후 오프라인 사용을 허용한다(사용자 “그럼요”). 아래 최초 준비의 인터넷 허용 여부는 해결됐다. 배포·설치 방식과 회사 PC 정책은 별도로 확인한다.

후속 결정 D13–D16: 중복 저장 차단·기존 항목 수정 안내를 재확인했고, 초기 약 100개, Windows Chrome 기본 및 Edge 지원, 인터넷 단절 중 앱 실행·입력·수정 필요를 확인했다. 최대 개수·성능 수치는 미정이다. 기술 A/B/C의 UI·저장 비교와 별개로 오프라인 실행 자원 제공 방식을 설계해야 하며, 브라우저에 데이터를 저장하는 것만으로 앱 오프라인 실행을 충족했다고 보지 않는다. 최초 설치·준비 단계의 인터넷 허용 여부를 다음에 확인한다.

| 미정 항목   | 필요한 결정 / 검증                                                                                               |
| ----------- | ---------------------------------------------------------------------------------------------------------------- |
| 사용 환경   | Windows Chrome 기본·Edge 지원, 오프라인 사용 필요는 확정. 최초 준비·실행/배포 방식·회사 PC 정책·지원 버전은 미정 |
| 데이터 규모 | 초기 약 100개 예상. 최대 프로그램 수·문자열 길이·응답 시간 목표는 미정                                           |
| 복수 탭     | 단일 탭 안내 또는 동시 수정 충돌 처리 정책. 마지막 저장 덮어쓰기를 암묵적으로 채택하지 않음                      |
| 저장/복원   | 저장 기술, 백업 형식·버전, 실패 시 초안과 기존 데이터 보존 동작                                                  |
| 시간축      | 초기 표시 기간·주/월 단위·가로 이동 방식, 일정 전무/범위 밖 이관일 표현                                          |
| 디자인      | 장부+간트 행 대응, 편집 패널, 반응형·포커스·긴 한글/식별자 검토                                                  |
| 테스트 도구 | 기술안 선택 후 단위/브라우저 테스트 기반 선정. 현재 npm run check는 앱 테스트 아님                               |

기능 검증은 요구사항 AC01–AC13을 추적한다. P 조건부 AC는 승인 후 확정한다. 상태 되돌림, 일정 미정, 저장 실패, 손상 백업, 복원 취소와 기존 데이터 보존을 포함한다. 화면 검증은 행 정렬·키보드·확대·반응형을 별도로 수행한다. 이 PRD 작성 중 앱 테스트를 실행한 것은 아니다.
