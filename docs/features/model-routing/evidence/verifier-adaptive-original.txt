# 최종 추가 요구사항: Adaptive Execution & Token Efficiency

앞서 정의한 Model Routing / Escalation, Legacy Adoption, Harness Upgrade 요구사항을 검토하면서 한 단계 상위의 목표를 함께 고려하라.

이번 개선의 궁극적인 목표는 단순히:

> GPT-5.6을 사용하다 어려우면 Astra를 호출한다.

가 아니다.

더 일반적인 목표는:

> **작업의 복잡도와 위험도에 따라 필요한 모델뿐 아니라 개발 프로세스의 깊이 자체를 조절하여, 프로젝트 완성까지의 총 비용·토큰·재작업을 최소화하면서 품질을 유지하는 Adaptive Execution Harness를 만든다.**

이다.

---

## 1. 최적화 대상

단일 요청의 토큰 사용량을 최소화하는 것이 목표가 아니다.

다음 전체 비용을 최적화한다.

```text
Total Project Cost
=
Discovery
+ Planning
+ Context Reconstruction
+ Implementation
+ Testing
+ Verification
+ Reasoning
+ Retry
+ Rework
+ Escalation
```

즉 어떤 단계에서 토큰을 조금 더 사용하더라도 이후의 실패, 재작업, 반복적인 repository 탐색을 크게 줄인다면 전체적으로 더 효율적인 것으로 본다.

반대로 작은 변경에 과도한 planning, subagent 생성, 독립 검증, 전체 테스트, 상위 모델 reasoning을 사용한다면 비효율적인 것으로 본다.

---

# 2. Model Routing보다 상위 개념으로 Adaptive Execution을 검토

다음 구조를 검토하라.

```text
                     TASK
                       │
                       ▼
              Risk / Complexity
                 Assessment
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
         LOW         MEDIUM        HIGH
          │            │            │
          ▼            ▼            ▼
     Lightweight     Standard     Intensive
       Process        Harness       Harness
          │            │            │
          ▼            ▼            ▼
     Default Model Default Model Default Worker
                                    │
                                    ▼
                              Reasoning Model
                               if necessary
```

즉 두 개의 서로 다른 routing을 구분한다.

```text
Process Routing
+
Model Routing
```

### Process Routing

작업에 어느 정도의 개발 절차가 필요한지를 결정한다.

### Model Routing

그 절차 안에서 어떤 capability의 모델을 사용할지를 결정한다.

Model Routing은 가능하면 Adaptive Execution의 하위 기능으로 설계한다.

단, 현재 cc-harness 구조에서 이 추상화가 불필요하게 복잡하다면 억지로 새로운 framework를 만들지 말고 최소한의 contract로 구현한다.

---

# 3. Task Risk / Complexity Classification

작업을 고정된 하나의 workflow로 처리하지 않고 위험도와 복잡도를 평가할 수 있는 최소한의 기준을 설계하라.

초기 가설:

```text
TIER 0 — TRIVIAL

typo
comment
formatting
documentation link
명백한 비동작 문서 수정
```

```text
TIER 1 — SMALL

작은 UI 변경
단일 함수 변경
국소 bug fix
작은 configuration 변경
```

```text
TIER 2 — NORMAL

일반 feature
API 변경
UI flow
DB query
여러 파일에 걸친 일반 구현
```

```text
TIER 3 — COMPLEX

cross-module dependency
architecture uncertainty
복잡한 integration
반복적으로 실패하는 bug
unknown runtime behavior
대규모 refactor
migration
```

```text
TIER 4 — CRITICAL

security-sensitive change
production data
destructive operation
payment/financial correctness
irreversible migration
high-impact infrastructure
```

이 분류는 초기 가설이다.

실제 repository와 기존 cc-harness 철학을 검토하여 더 단순하거나 안전한 분류가 있다면 변경안을 제시하라.

---

# 4. Process Depth

각 Tier마다 동일한 full lifecycle을 기계적으로 반복하지 않는다.

예상 개념:

```text
TIER 0
Default model
+ 최소 검증
```

```text
TIER 1
Default worker
+ targeted test
+ lightweight verification
```

```text
TIER 2
Default worker
+ TDD
+ independent AC verification
```

```text
TIER 3
Default worker
+ bounded retry
+ reasoning escalation
+ independent verification
+ broader regression
```

```text
TIER 4
Strong reasoning
+ strict user gates
+ independent verification
+ security review
+ broad regression
+ rollback consideration
```

그러나 기존 cc-harness의 필수 안전 계약을 임의로 약화하지 않는다.

특히 현재 `AGENTS.md`와 orchestration policy에서 독립 검증이 필수인 부분과 충돌할 수 있다.

따라서 반드시 분석하라.

> 작은 작업까지 항상 별도 worker + independent verifier를 강제하는 현재 정책이 품질 대비 토큰 비용 측면에서 합리적인가?

단순히 제거하지 말고 다음을 비교하라.

```text
A. 현재 strict policy 유지

B. risk-based verification depth 도입

C. independent verification은 유지하되
   전달 context와 검증 범위를 최소화

D. 다른 안전한 대안
```

추천안을 제시하고 사용자 승인 전 정책을 변경하지 않는다.

---

# 5. Escalation은 Model Upgrade가 아니라 Reasoning Service로 취급

상위 모델을 단순히 더 비싼 worker로 사용하지 않는다.

가능하면:

```text
Default Worker
      ↓
failure
      ↓
classification
      ↓
Reasoning Model
      ↓
diagnosis / hypothesis / plan
      ↓
Default Worker
      ↓
implementation
      ↓
Verifier
```

형태를 우선한다.

즉 reasoning model은 가능한 경우:

* 원인 분석
* architecture 판단
* hypothesis 생성
* 접근 방법 재설계

에 집중한다.

실제 구현은 다시 default worker가 수행할 수 있도록 한다.

이를 통해 expensive-model token consumption을 제한한다.

---

# 6. Escalation Budget

모델 escalation도 반드시 유한해야 한다.

예:

```text
worker_retry <= configured limit

reasoning_escalation <= configured limit
```

다음 패턴을 금지한다.

```text
5.6 fail
→ Astra
→ fail
→ Astra
→ fail
→ Astra
→ ...
```

진전 없는 반복은 기존 STOP contract를 따른다.

Escalation은 STOP을 우회하는 수단이 아니다.

---

# 7. Just-In-Time Repository Understanding

특히 Legacy Adoption에서 repository 전체를 처음부터 깊게 분석하고 문서화하지 않는다.

대규모 legacy repository에서는 다음 전략을 검토한다.

```text
Repository
    │
    ▼
cheap structural discovery
    │
    ▼
current change area
    │
    ├─ dependencies
    ├─ tests
    ├─ interfaces
    └─ relevant docs
           │
           ▼
     selective deep analysis
```

즉:

> **필요한 변경 범위를 중심으로 repository 이해도를 점진적으로 확장한다.**

이를 Just-In-Time Understanding 원칙으로 정의할 수 있는지 검토한다.

전체 repository 분석이 필요한 경우에만 그 이유와 범위를 명확하게 한다.

---

# 8. Context Reconstruction Cost

장기 프로젝트에서는 모델 자체의 추론 비용만큼 다음 비용이 중요하다.

```text
새 세션
→ repository 재탐색
→ architecture 재이해
→ 현재 작업 재이해
→ 이전 결정 재이해
```

이를 줄이는 것이 Adaptive Execution의 핵심 목표 중 하나다.

현재 cc-harness의:

* progress
* ADR
* AC
* verification evidence
* issue state
* spec-fixed

등을 이용해 새로운 agent에게 전달할 **Minimum Sufficient Context**를 정의할 수 있는지 검토하라.

목표:

```text
전체 대화 전달 X

전체 repository 전달 X

긴 로그 전달 X

필요한 결정
+ 현재 issue
+ 관련 파일
+ 관련 evidence
+ 현재 checkpoint
```

만으로 작업을 재개할 수 있도록 한다.

---

# 9. Legacy Baseline과 Ratchet

Legacy Adoption에서는 기존 기술부채를 모두 수정하려 하지 않는다.

예:

```text
baseline

lint warnings = 173
failing legacy tests = 2
missing E2E = payment
architecture docs = partial
```

새 변경은 가능한 범위에서 baseline을 악화시키지 않는다.

```text
before = 173 warnings

after = 170 → improvement

after = 173 → no regression

after = 181 → regression
```

단, security blocker, 데이터 손상 위험, broken environment 등은 baseline debt라는 이유로 허용하지 않는다.

---

# 10. Evidence Reuse

이미 생성된 검증 증거를 가능한 경우 재사용한다.

단 다음 조건을 확인한다.

```text
same relevant code version
same contract
same test
same relevant environment
```

관련 코드나 계약이 변경되었다면 필요한 검증만 다시 수행한다.

전체 lifecycle을 무조건 다시 실행하지 않는다.

목표는:

> **검증을 줄이는 것이 아니라 유효한 검증의 불필요한 반복을 줄이는 것**

이다.

---

# 11. Token / Cost Observability

가능하다면 cc-harness가 실제 token usage를 정확히 얻을 수 있는지 조사한다.

지원되지 않는다면 추정값을 사실처럼 기록하지 않는다.

대신 최소한 다음 execution metadata를 기록할 수 있는지 검토한다.

```text
task_tier
process_profile
worker_role
worker_model_if_known
reasoning_level_if_known
retry_count
escalation_count
failure_class
verification_depth
context_scope
```

이를 통해 향후 실제 프로젝트 데이터를 가지고 Adaptive Execution policy를 개선할 수 있어야 한다.

---

# 12. 향후 Learning Loop

이번 구현에서 self-learning system을 만들 필요는 없다.

그러나 향후 다음 분석이 가능하도록 execution evidence 구조를 검토한다.

```text
Task Type
   ↓
Process Profile
   ↓
Model
   ↓
Retries
   ↓
Escalations
   ↓
Verification
   ↓
Outcome
```

프로젝트가 쌓이면 예를 들어:

```text
UI small change
→ lightweight profile 성공률 높음

DB migration
→ intensive profile 필요

cross-module bug
→ reasoning escalation 효과 높음
```

같은 근거를 만들 수 있다.

향후 하네스가 경험 데이터를 기반으로 routing policy를 개선할 수 있도록 확장 가능성만 보존한다.

이번 범위에서 자동 학습 시스템을 구현하지 않는다.

---

# 13. 최종 목표 구조

이번 개선의 장기적인 방향은 다음과 같다.

```text
                     TASK
                       │
                       ▼
              Risk / Complexity
                 Assessment
                       │
                       ▼
                Process Router
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
     Lightweight    Standard     Intensive
          │            │            │
          ▼            ▼            ▼
       Default       Default      Default
        Model         Model        Worker
                                      │
                              failure / uncertainty
                                      │
                                      ▼
                              Reasoning Model
                                      │
                                      ▼
                               Default Worker
          │            │            │
          └────────────┴────────────┘
                       │
                       ▼
                 Verification
                       │
                       ▼
                    Evidence
                       │
                       ▼
                Progress State
                       │
                       ▼
             Minimum Context for
                next execution
```

이 구조의 목적은 가장 강한 모델을 최대한 많이 사용하는 것이 아니다.

목표는:

> **필요한 순간에 필요한 만큼의 reasoning, process, verification을 사용하여 전체 프로젝트 완성 비용과 실패율을 동시에 낮추는 것**

이다.

---

# 14. 매우 중요한 범위 제약

이 요구사항 때문에 이번 작업을 거대한 orchestration framework 재작성으로 만들지 않는다.

현재 cc-harness를 먼저 분석하고 다음을 분리하라.

### NOW

현재 Model Routing 기능을 구현하면서 반드시 필요한 최소 Adaptive Execution contract.

### NEXT

범용 Process Routing / Legacy Adoption / Harness Upgrade를 위해 가까운 시점에 필요한 후속 기능.

### LATER

실제 execution history를 이용한 adaptive policy optimization 또는 learning.

가능하면 기존 구조와 스킬을 재사용하고 새 abstraction, config, dependency를 최소화한다.

---

# 15. 구현 전 반드시 멈출 것

이 추가 요구사항을 읽은 뒤 바로 구현하지 않는다.

기존 요청들과 함께 전체 요구사항을 다시 정리하여 다음을 제시하라.

1. 현재 cc-harness 구조에서 이미 해결된 부분
2. 실제 문제점
3. Model Routing과 Adaptive Execution의 관계
4. Legacy Adoption과의 관계
5. 현재 strict orchestration policy의 token-efficiency 분석
6. 최소 구현안
7. 변경 예정 파일
8. 추가되는 contract
9. 테스트 전략
10. backward compatibility 영향
11. NOW / NEXT / LATER 범위
12. 예상되는 장점과 새로운 복잡성
13. 최종 추천안

그리고 **사용자 승인을 기다려라.**

특히 기능을 많이 넣는 것이 좋은 설계라고 가정하지 않는다.

현재 cc-harness의 장점인:

* 명확한 lifecycle
* 승인 gate
* 독립 검증
* 유한 반복
* 증거 기반 판단
* 재개 가능한 상태

를 유지하면서도 **불필요한 agent 호출, 전체 repository 재탐색, 과도한 reasoning, 과도한 verification을 제거하는 것**을 우선한다.

최종적으로 cc-harness가 지향할 질문은:

> "어떤 모델을 사용할까?"

만이 아니라,

> **"이 작업을 안전하게 완료하는 데 필요한 최소한의 프로세스와 지능은 무엇인가?"**

가 되어야 한다.
