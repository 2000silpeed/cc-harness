# 아키텍처 재설계 확정 요구사항 v1

- 상태: G1 목적·결과 승인. 근거는 `spec-original.md`의 구현 승인 원문과 기존 보고서의 추천 결과다. 아래 세부 구조는 AI가 승인 결과 안에서 정한 기술 기본값이며 사용자 직접 선택으로 표기하지 않는다.
- 주 사용자: 로컬 cc-harness로 승인된 작업을 진행하고 인계·검증하는 운영자와 구현자·독립 검증자.
- UI: 새 제품 화면은 없다. 기존 HTML 보고서는 사람이 읽는 설계·상태 뷰다.

## 목적과 기본 시나리오

운영자가 같은 승인·STOP·예산·증거 입력으로 기존 로컬 CLI를 실행할 때, 상태 판정이 재현 가능하고 외부 동작이 보존되며, 대표 fixture의 현재 결과를 같은 입력의 기준선과 비교할 수 있어야 한다. 독립 검증자는 판정 ID·입력 해시·실제 로그를 보고 AC 의미와 승인 출처를 별도 판단한다.

## 오류·경계·저장·성능

- 잘못된 입력, stale HEAD/dirty/contract/approval/evidence, 활성 STOP, 소진된 예산, 동시 작업은 기존 거부 동작을 유지한다. 저장된 receipt 무결성 보강은 의도된 좁은 수정이며, 명령별 오류 인터페이스와 유효 기록의 동작은 유지한다. 새 판정 코어가 권한을 넓히면 실패다.
- 평가 fixture는 로컬의 비밀 없는 대표 입력만 사용한다. 동일 입력은 동일 판정과 ID를 만든다. 비교 불가능한 입력 또는 누락된 기준선은 pass로 위장하지 않고 별도 실패/미평가 상태로 남긴다.
- 기존 원본 승인·증거와 로그를 복사·삭제하지 않는다. 활성 참조와 퇴역 metadata를 구분한다.
- 속도 개선은 실제 측정한 경우에만 주장한다. 우선 목표는 중복 검사 제거와 읽기 범위 축소이며 성능 수치를 가정하지 않는다.

## 용어와 제외 범위

- **순수 코어**: 파일·Git·CLI I/O 없이 입력값에서 결정 결과를 계산하는 내부 함수 집합. 새 클래스 계층을 뜻하지 않는다.
- **평가 세트**: 로컬 대표 fixture와 기대 결정·기준선 비교 자료. 운영 trace 수집이 아니다.
- **승인 확인**: CLI 외부에서 신뢰 가능한 사용자 원문·결정자·범위·시점·철회를 대조하는 행위.
- 제외: 새 승인 issuer/암호학적 증명, 별도 DB·SaaS·유료 judge, 무인 권한 발급, 자동 외부 게시·배포, 새 제품 UI. 구체적인 경계와 이유는 `prd.md`에 둔다.
