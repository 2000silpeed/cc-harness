# cc-harness 아키텍처 재설계 PRD v1

## 개요

- 기준 요구사항: `spec-fixed.md` v1 (R1–R6). 디자인 참조: 기존 `docs/architecture/redesign-review-2026-09-30.html`; 새 앱 화면 없음.
- 기존 구조: `scripts/session-handoff.mjs`가 schema·Git/파일 검사·판정을 함께 수행하고, `scripts/check-harness.mjs`와 `package.json`이 정적 검사를 구성한다. `docs/harness/lifecycle.md` §5가 승인 경계를 정의한다. 기존 schema/명령/STOP/계보/예산을 깨지 않는 점진 변경이 필요하다.

## 사용자 스토리

1. 운영자는 같은 인계 입력을 기존 CLI로 처리해 동일한 허용/STOP 결정을 얻는다(R1, R2).
2. 독립 검증자는 대표 fixture의 현재/기준선 결과와 실패 ID·해시를 보고 실제 AC를 판정한다(R3).
3. 유지보수자는 중복 검사를 줄인 명령과 현재 계약에 맞는 문서·보고서를 사용한다(R4, R5).
4. 운영자는 손상된 저장 receipt를 `STOP_MALFORMED`로 거부하고, 유효한 기록은 계속 처리한다(R6).

### [GATE 2] 아키텍처 선택

- 상태/모드: B 선택, `policy-delegated`.
- 결정 출처: 사용자는 추천 결과의 로컬 구현을 승인했다. B의 구체적인 내부 함수 경계는 AI 기술 판단이다. 기존 CLI와 계약 보존, 의존성 0개, 작은 변화와 오프라인 평가 용이성 때문에 B를 선택한다.
- 대상: `spec-fixed.md` v1, HEAD `ae9ff54c33518b77fc0de18feb217660303ac739`. 독립 검증과 실제 Green은 아직 이 결정의 증거가 아니다.

### ADR: 기존 CLI를 유지하는 작은 상태 코어

**Context** — 승인·STOP·계보·예산 규칙은 문서와 CLI에 분산되어 있다. CLI 자체가 승인 진위를 인증하지 못한다. 기존 사용자 명령·JSON 인계와 회귀를 보존해야 한다.

**Decision** — B를 택한다. I/O와 순수 판정을 가르는 최소 경계만 도입하고 파일·Git·CLI는 현재 인터페이스를 유지한다. 로컬 fixture 평가로 동일 입력의 기준선과 현재 결과를 비교한다. 이 결정은 승인된 결과 안의 AI 기술 선택이며 사용자 직접 선택으로 기록하지 않는다.

**Alternatives** — A는 초기 수정이 작지만 분산 규칙·fixture 결합이 남아 평가를 반복하기 어렵다. C는 이력 모델이 풍부하지만 새 schema·영속 저장·마이그레이션과 테스트 비용이 현재 로컬 범위를 넘는다.

**Consequences** — 판정 경계와 실패 비교가 명확해진다. 내부 모듈·호환 검사가 늘고 기존 스크립트에서 코어를 추출하는 동안 이중 규칙이 생길 위험이 있다. 저장 receipt 무결성 보강만 의도된 거부 동작 수정으로 구분한다. 사용자 승인 진위와 AC 의미, 독립성은 자동 판정하지 않는다.

## Out of Scope

- 별도 승인 issuer, CLI가 발급하는 `verified`, 암호학적 서명 또는 보안 권한 모델 변경: 기존 승인 출처 계약과 별도 보안 결정이 필요하다.
- LangSmith SaaS, 온라인 trace 수집, 외부 피드백 전송, 유료 LLM judge, DB: 로컬 오프라인 평가에 불필요하며 별도 외부·비용 권한이 없다.
- 원본 승인·증거·로그 복사/삭제 및 전면 schema·명령 교체: 계보와 호환 계약에 어긋난다.
- Git·PR·배포·외부 이슈 등록: 별도 권한 대상이다.
- 모든 Bash에 대한 훅을 추정만으로 제거하지 않는다. 실제 중복·발화·신뢰를 확인한 구간만 단순화한다.

### [GATE 3] 제외 범위 확정

- 상태/모드: 승인 결과 안에서 구체화, `policy-delegated`; 대상 `spec-fixed.md` v1.
- 출처: 사용자 구현 승인과 현재 lifecycle §5의 외부 권한 경계. AI가 위 제외 범위를 설계했으며 사용자 직접 선택으로 쓰지 않는다.
- 목적·비용·위험: 로컬 가역 구현, 의존성 0개, 기존 STOP/예산/승인 경계 유지. 새로운 보안 결정을 요구하는 상황은 G3으로 되돌린다.

## 용어 정의

`spec-fixed.md`의 순수 코어·평가 세트·승인 확인 정의를 그대로 사용한다. baseline은 동일 fixture 입력의 변경 전 실제 결과이며, historical 검사 로그를 현재 Green으로 대체하지 않는다.

## 검증·위험

G4 이슈와 G5 시나리오는 분리된 검증자의 감사 전까지 대기다. R1의 기존 출력·저장 호환성, R2의 자기 선언 승인 오판, R3의 비교 가능성, R4의 필수 게이트 누락이 핵심 위험이다.
