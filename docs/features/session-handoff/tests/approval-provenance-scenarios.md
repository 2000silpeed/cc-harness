# 승인 출처 확인 전 자동 진행 차단 시나리오

- 대상: `scripts/session-handoff.mjs`의 `prepare`, `decide`, `claim`, `receipt`와 `docs/features/{feature}/session-handoff.json`의 v1/v2 기록
- 근거: 사용자 결정 “권고대로 진행” — 신뢰 가능한 승인 출처 검증 수단이 마련되기 전까지 CLI의 자동 단계 전환과 rollover/claim을 fail-closed로 보류한다. 이전 fixture에서는 자신이 작성한 `approval_refs`와 올바른 SHA만으로 `PHASE_READY`가 재현되었고 독립 검증되었다.
- 기존 코드·회귀 위치: `scripts/session-handoff.mjs`의 `approval`, `readiness`, `receiptPrompt`, `prepare`, `claim` 및 `tests/unit/harness-portability.test.ts`의 준비/단계 전환(약 594–625행), 위험 상태(약 674–713행), claim/receipt(약 942–1041행) 사례. 행 번호는 이 문서 작성 시점의 참고 위치다.
- 상태: G5 계약·시나리오 초안. 독립 계약 검토, Red, Green 및 AC 검증은 아직 수행되지 않았다. 기존 테스트가 기대하는 `PHASE_READY`/`ROLLOVER_READY`/`CONTINUE_CURRENT` 성공은 이 계약에 맞춰 Red에서 변경해야 한다.

## 권한 결정과 AI 선택

사용자가 결정한 것은 **검증 가능한 승인 출처가 없을 때 자동 진행을 보류**하는 정책이다. 아래의 STOP 이름, 적용 지점, 응답 필드 및 테스트 분류는 그 결정을 구체화한 AI 선택이다. 이 선택을 사용자가 직접 승인한 세부 구현이라고 기록하지 않는다.

이 문서는 별도의 신뢰 서비스, 서명 기능, 승인 검증 프로토콜을 도입하지 않는다. CLI 입력, `approval_refs.status: "approved"`, 파일 내용, SHA-256 일치, `resume` 참조, receipt 또는 CLI가 스스로 설정한 플래그만으로 원문 승인 주체·범위·시점·철회 여부를 확인할 수 없다. 수동 검토자는 CLI 바깥의 신뢰할 수 있는 사용자 원문과 주체, 대상 범위, 결정 시점 및 후속 철회를 대조한다. 그 검토가 끝나도 현 계약의 CLI는 `verified`를 자체 선언하거나 자동 실행 허가를 반환하지 않는다. 실제 자동 재개는 별도 승인된 신뢰 검증 수단과 그 계약·독립 검토가 마련된 뒤의 작업이다.

## AC와 호출 계약

| AC   | 관찰 가능한 계약                                                                                                                                                                                                                                                                                                                                                        |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AP-1 | `prepare`는 기존 v1/v2 schema, 계보, source/dirty/contract/approval/evidence 해시 무결성을 계속 검사하고 유효하면 `PREPARED` 기록만 저장한다. `PREPARED`에는 실행 허가나 다음 단계 명령이 없다.                                                                                                                                                                         |
| AP-2 | `decide`가 무결성 및 기존 안전 조건을 통과하여 기존에는 `PHASE_READY`, `ROLLOVER_READY` 또는 `CONTINUE_CURRENT`가 되었을 모든 경로에서 `STOP_APPROVAL_PROVENANCE_UNVERIFIED`를 반환한다. 자동 진행을 허가하는 `next_skill`, `next_action`, `instruction`, `launch_prompt`, `resume_prompt` 및 `launch_allowed: true`는 반환하지 않는다.                                 |
| AP-3 | `claim`은 같은 출처 STOP을 반환하며 record의 `status`, `rollover.claim`, 카운터, ID 및 파일 바이트를 바꾸지 않는다. 호출 반복이나 다른 executor도 claim을 획득하지 못한다.                                                                                                                                                                                              |
| AP-4 | 기존 STOP 우선순위와 구체 원인을 유지한다. source 불가/변경, dirty 변경, contract/approval/evidence 해시 변경, prepared 경로의 active STOP·inflight 활동·필수 승인·증거 누락/무효·단계/예산·rollover 제한, 이미 claimed인 reconciliation 및 receipted 세션 불일치·중복 등은 출처 STOP으로 가리지 않는다. 출처 STOP은 기존 조건을 모두 통과한 자동 성공 직전에 적용한다. |
| AP-5 | v1/v2 모두 같은 차단 정책을 받는다. `receipt` 성공 응답의 `resume_prompt`는 승인 출처 수동 검토가 필요함을 명시하고 실행 허가를 주장하지 않는다. 저장된 receipt의 session ID가 일치해도 이어지는 `decide`는 출처 STOP을 반환하고 자동 재개 지시를 제공하지 않는다.                                                                                                      |
| AP-6 | 출처 STOP에는 CLI 밖 수동 검토 조건을 사람이 읽을 수 있게 돌려준다. 검토 대상은 원문, 승인 주체, 범위, 시점 및 철회 여부다. 이 조건은 우회용 CLI 인자나 자체 `verified` 상태가 아니다.                                                                                                                                                                                  |

`decide`는 동기식 read-only 명령이다. 입력은 기존 `--state`, `--root`, 선택 `--session-id`이며 출력은 JSON 결정이다. `claim`은 기존 `--state`, `--handoff-id`, `--executor-id`를 받지만 출처 미검증 상태에서 write가 없어야 한다. `prepare`의 기존 입력/schema와 원자적 record 저장은 유지한다. STOP 응답의 `resume_condition`은 수동 검토 필요성과 검토 항목을 설명하는 문자열로 정한다. 이 문자열 자체가 검증 결과나 실행 허가는 아니다. 일반 STOP은 기존 JSON 출력과 종료 코드 관례를 유지하되, malformed 입력·I/O 오류는 기존 오류 계약대로 처리한다.

## 미정·제외 및 인계

- 신뢰 승인 출처의 기술 구현, 서명·외부 검증 서비스, 자동 재개 인자와 그 권한 모델은 이 이슈 범위 밖이다. 향후 구현 전 별도 계약과 승인·독립 검토가 필요하다.
- 기존 `receipt` 기록 API는 이미 claimed된 과거 record의 사실 기록을 위한 계약으로 남는다. 그 성공 응답이나 `resume_prompt`는 현재 작업의 실행 허가가 아니며, 이어지는 `decide`가 AP-S11을 만족해야 한다.
- 독립 검토자는 기존 STOP 우선순위, legacy record 호환 및 `resume_condition` 문구의 오인 가능성을 검토한다. 통과 기록 전에는 G5 완료로 표시하지 않는다.

## 실행할 테스트 명령

Red 작성 후 관련 검사: `npx vitest run tests/unit/harness-portability.test.ts`.

구현·관련 검사 후 저장소 최종 검사: `npm run check`. 이 문서 작성 단계에서는 테스트 코드와 구현을 실행하지 않는다.
