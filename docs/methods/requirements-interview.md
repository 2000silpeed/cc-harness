# 요구사항 인터뷰

기능의 목적과 동작 정책을 사용자와 확정한 뒤 설계로 넘긴다. 기존 기능의 인터뷰·최초 요청·승인 상태는 해당 변경 요청 없이 다시 작성하지 않는다. 상세 질문 영역과 산출물 양식은 [기획](planning.md)을 함께 사용한다.

## 결정의 원칙

### 코딩 전에 결정할 것은 사람이 정한다

기능을 짧게 요청하면 AI가 저장 방식, 제한, 중복 처리 등 빈칸을 대신 채울 수 있다. 코드가 빠르게 만들어져도 그 전제가 틀리면 다시 고쳐야 한다. 따라서 먼저 **무엇을 만들고 어떤 조건을 만족해야 하는지**를 정한다.

- 기능 요구사항: 시스템이 해야 하는 동작.
- 비기능 요구사항: 성능·저장·복구·사용 환경 등 만족해야 하는 조건.
- 구현·아키텍처: 확정한 요구사항을 어떻게 실현할지 정하는 후속 작업.

### AI가 질문하고, 사용자가 결정한다

사용자가 모든 예외를 먼저 나열하는 대신 AI가 정의서와 실제 코드를 읽고 질문한다. 질문은 **한 번에 하나**, 필요한 경우 **추천과 이유**를 함께 제시한다. 추천은 결정의 근거이지 사용자의 결정을 대신하는 승인이 아니다.

### 원본과 확정본을 나눈다

- `spec-original.md`: 처음 받은 요청을 보존한다.
- `spec-fixed.md`: 인터뷰로 구체화하고 사용자가 확정한 요구사항을 기록한다.
- 결정 이유와 용어를 함께 남겨 나중에 “왜 이 규칙인가?”에 답할 수 있게 한다.

확정본이라는 파일명만 붙였다고 승인된 것은 아니다. 사용자가 검토·확정한 사실과 AI의 미확정 제안을 구분해야 한다.

## 인터뷰 실행

### 새 기능의 인터뷰를 요청할 때

새 기능의 초기 아이디어를 준비하고, 프로젝트의 새 Codex 세션에서 아래와 같이 요청한다. 경로는 실제 대상 기능의 파일로 바꾼다. **이 예시는 재사용 방법이며, 기존 인터뷰를 자동 재실행하라는 뜻이 아니다.**

```text
AGENTS.md와 docs/features/<기능명>/spec-original.md를 읽어줘.
먼저 실제 코드와 설정을 확인하고, 구현 전에 결정해야 할 내용을 질문해줘.
앱 소스가 없다면 기존 앱이 있는 것으로 가정하지 마.

질문은 한 번에 하나씩 해줘.
판단이 필요한 질문에는 추천 방식과 이유도 포함해줘.
이미 확인한 사실은 반복해서 묻지 말고, 내 답변 없이 결정을 확정하지 마.

인터뷰가 끝나면 같은 폴더의 spec-fixed.md에 다음을 정리해줘.
- 목적과 사용자, 기능 및 비기능 요구사항
- 용어 정의, 경계 조건과 오류 처리
- 결정 사항과 이유, 이번에 하지 않을 것, 수락 기준
- 합의한 내용과 아직 확인이 필요한 제안의 구분

최초 요청은 보존하고, 다른 기능의 인터뷰 파일은 수정하지 마.
내가 정의서를 확정하기 전에는 구현하거나 커밋하지 마.
```

### 결과를 검토할 때

1. 원래 요청이 삭제되거나 다른 의미로 바뀌지 않았는지 확인한다.
2. 질문별 사용자 답변과 최종 규칙을 연결해 읽는다.
3. AI 추천을 그대로 채택한 부분과 사용자가 수정한 부분을 구분한다.
4. 빈 값·중복·실패·되돌리기 같은 예외가 어떻게 처리되는지 확인한다.
5. 코드·문서·대화에서 같은 용어가 같은 의미인지 확인한다.
6. 확인하지 않은 성능 수치나 기술 선택이 확정 사실로 섞이지 않았는지 확인한다.
7. 사용자가 최종 확정한 뒤에만 문서 상태를 확정으로 바꾼다. 이후 요구사항 변경은 이유와 함께 기록한다.

문서 커밋이 필요하면 변경 내용을 먼저 검토하고 명시적으로 요청한다. 메시지 예시는 `docs(requirements): 기능 요구사항 인터뷰 정리`이며, 별도 요청 없이 커밋·푸시하지 않는다.

## 검증과 인계

최초 요청의 보존, 질문·답변·최종 규칙의 추적, 미결 항목, 사용자 승인 대상 버전을 확인한다. 보호 대상 파일은 필요하면 작업 전후 해시로 보존 여부를 검사한다. 문서의 서식 통과나 지침 로딩은 실제 인터뷰 완료·요구사항 승인과 다르다. 승인 후 [기획의 PRD·ADR 단계](planning.md)로 넘기며, 새 요구사항은 영향을 받는 승인 게이트에서 다시 판단한다.
