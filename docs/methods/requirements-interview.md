# 요구사항 인터뷰

요구사항 인터뷰의 목적은 기능의 목적과 동작 정책을 사용자와 확정하거나, 사용자가 명시한 유한한 위임 안에서 판정한 뒤 설계 단계로 넘기는 것입니다. 기본은 사용자 직접 승인입니다. 기존 기능의 인터뷰, 최초 요청, 승인 상태는 사용자가 변경을 요청하지 않는 한 다시 작성하지 않습니다. 자세한 질문 영역과 산출물 양식은 [기획](planning.md)을 함께 사용합니다.

## 결정의 원칙

### 목적과 위임 경계는 사용자가 정한다

기능 요청이 짧으면 AI가 저장 방식, 제한, 중복 처리와 같은 빈칸을 임의로 채울 수 있습니다. 코드를 빨리 만들더라도 전제가 틀리면 다시 고쳐야 합니다. 따라서 먼저 **무엇을 만들고 어떤 조건을 만족해야 하는지**와 **어떤 판단을 AI에 맡길지**를 정합니다.

- 기능 요구사항은 시스템이 해야 하는 동작입니다.
- 비기능 요구사항은 성능, 저장, 복구, 사용 환경처럼 시스템이 만족해야 하는 조건입니다.
- 구현과 아키텍처는 확정한 요구사항을 어떻게 실현할지 정하는 후속 작업입니다.

### AI가 질문하고, 사용자가 결정하거나 범위를 위임한다

사용자가 모든 예외를 먼저 나열할 필요는 없습니다. AI가 정의서와 실제 코드를 읽고 필요한 내용을 질문합니다. 질문은 **한 번에 하나**만 하며, 판단을 도울 필요가 있으면 **추천과 이유**를 함께 제시합니다. 추천은 판단 자료일 뿐 사용자의 결정을 대신하는 승인이나 위임이 아닙니다.

게이트 권한은 [승인과 외부 작업](../harness/lifecycle.md#5-승인과-외부-작업)을 따릅니다. 구현 승인이 없으면 `human-required`입니다. 명확한 추천 결과에 대한 “승인하고 구현”은 추천 결과의 채택과 가역적 로컬 구현·검증의 승인으로 기록합니다. 사용자가 게이트 이름이나 별도 양식을 채울 필요는 없습니다. AI의 후속 선택은 근거를 가진 `policy-delegated` 판단으로 분리하고, G4·G5는 독립 검토를 포함한 `auto-with-audit`로 처리합니다. 별도 게이트 정책의 명시적 한계는 유지합니다.

G1에서 제품 목적·사용자 가치·중대한 범위나 위험이 불명확하면 결과를 좌우하는 질문 하나에 구체적인 추천과 이유를 제시합니다. 승인 후 저장·오류·경계·성능 같은 세부 중 목적과 위험을 바꾸지 않는 것은 작은 가역적 기본값과 이유·적용 한계를 기록해 해결합니다. 이를 사용자의 답변으로 꾸미거나 필수 정책을 “미결”로 남긴 채 G1을 통과시키지 않습니다. 중요한 충돌이나 의도 누락은 사용자에게 상향합니다.

### 원본과 확정본을 나눈다

- `spec-original.md`에는 처음 받은 요청을 그대로 보존합니다.
- `spec-fixed.md`에는 사용자 원문과 승인 결과·실행 범위, AI가 구체화한 요구사항·기본값·이유, 별도 위임 정책의 결정을 출처별로 기록합니다.
- 결정 이유와 용어를 함께 남겨 나중에 “왜 이 규칙인가?”라는 질문에 답할 수 있게 합니다.

파일 이름에 확정본이라는 뜻을 담았다고 승인된 것은 아닙니다. 사용자 직접 결정, 위임 정책에 따른 결정, AI가 제안만 한 내용을 분명히 구분해야 합니다.

## 인터뷰 실행

### 새 기능의 인터뷰를 요청할 때

새 기능의 초기 아이디어를 준비한 뒤 프로젝트의 새 Codex 세션에서 아래와 같이 요청합니다. 경로는 실제 대상 기능의 파일로 바꿉니다. **이 예시는 재사용 방법이며, 기존 인터뷰를 자동으로 다시 실행하라는 뜻이 아닙니다.**

```text
AGENTS.md와 docs/features/<기능명>/spec-original.md를 읽어줘.
먼저 실제 코드와 설정을 확인하고, 구현 전에 결정해야 할 내용을 질문해줘.
앱 소스가 없다면 기존 앱이 있는 것으로 가정하지 마.

질문은 한 번에 하나씩 해줘.
판단이 필요한 질문에는 추천 방식과 이유도 포함해줘.
이미 확인한 사실은 반복해서 묻지 말고, 내 답변 없이 결정을 확정하지 마.

인터뷰가 끝나면 같은 폴더의 spec-fixed.md에 다음을 정리해줘.
- 목적과 사용자, 기능 및 비기능 요구사항
- 용어 정의, 경계 조건과 오류 처리
- 결정 사항과 이유, 이번에 하지 않을 것, 수락 기준
- 합의한 내용과 아직 확인이 필요한 제안의 구분

최초 요청은 보존하고, 다른 기능의 인터뷰 파일은 수정하지 마.
내가 정의서를 확정하기 전에는 구현하거나 커밋하지 마.
```

### 결과를 검토할 때

1. 원래 요청이 삭제되거나 다른 의미로 바뀌지 않았는지 확인합니다.
2. 질문별 사용자 답변과 최종 규칙을 연결해서 읽습니다.
3. AI의 추천을 그대로 채택한 부분과 사용자가 수정한 부분을 구분합니다.
4. 빈 값, 중복, 실패, 되돌리기 같은 예외를 어떻게 처리하는지 확인합니다.
5. 코드, 문서, 대화에서 같은 용어가 같은 의미로 쓰였는지 확인합니다.
6. 확인하지 않은 성능 수치나 기술 선택이 확정된 사실처럼 섞이지 않았는지 확인합니다.
7. 사용자 결정과 구현 승인 범위의 기본값 또는 별도 위임 판정으로 필요한 정책·성공 조건을 갖춘 뒤에만 문서 상태를 확정으로 바꿉니다. 필요한 독립 감사, 결정 모드·출처도 남깁니다. 단순한 승인 응답만으로 빈 산출물을 완료 처리하지 않습니다. 이후 요구사항이 바뀌면 그 이유도 함께 기록합니다.

문서를 커밋해야 한다면 변경 내용을 먼저 검토하고 정확한 대상과 범위를 명시적으로 요청합니다. 메시지 예시는 `docs(requirements): 기능 요구사항 인터뷰 정리`입니다. 게이트 위임만으로 커밋·push·PR·병합·배포나 다른 외부 쓰기 권한을 추정하지 않습니다.

## 검증과 인계

인계하기 전에 최초 요청이 보존되었는지, 질문·답변·최종 규칙을 서로 추적할 수 있는지, 미결 항목과 게이트 대상 버전·결정 모드·결정 출처가 무엇인지 확인합니다. 보호 대상 파일은 필요하면 작업 전후 해시를 비교해 보존 여부를 검사합니다. 문서 서식이 검사를 통과했거나 지침을 불러왔다는 사실은 인터뷰 완료, 사용자 승인, 정책 위임을 뜻하지 않습니다. 사용자 승인 또는 유효한 위임 판정 후에는 [기획의 PRD·ADR 단계](planning.md)로 넘깁니다. 새 요구사항이 생기면 그 영향을 받는 게이트를 다시 열고, 위임 envelope 밖이면 사용자에게 상향합니다.
