# 기획: 요구사항에서 개발 가능한 이슈까지

아이디어를 확정 요구사항·PRD·ADR·수직 이슈로 바꾸는 실행 계약이다. 문서 작성, 사용자 승인, 스킬 등록, 외부 게시, 제품 구현은 별도 상태로 관리한다. 예시의 태그·Note 구조는 설명용 가정이며 대상 앱의 요구사항이 아니다.

## 파이프라인과 승인

요구사항을 확정하고, 기술 선택의 이유를 보존한 뒤,
사용자가 확인할 수 있는 작은 동작으로 나눈다. 반복할 때 질문·비교·단점·수직 슬라이스 검토가
빠지지 않도록 절차를 자산화한다. AI는 탐색·초안·비교를 담당하고, 사람은 중요한 선택을 한다.

**[원본 워크플로] 3단계 파이프라인:**

```text
spec-original.md + 실제 코드/설정
  → 단계 1: 요구사항 인터뷰
  → spec-fixed.md
  → [GATE 1] 요구사항·용어 확정
  → 단계 2: PRD 뼈대 + 아키텍처 최소 3안/7기준 비교
  → [GATE 2] 사용자 아키텍처 선택
  → PRD 내부 ADR 4요소 + Out of Scope
  → [GATE 3] 제외 범위 확정
  → prd.md
  → 단계 3: 수직 슬라이스 + AC + 의존성 순서
  → issues.md
  → [GATE 4] 이슈 목록 검토·확정
  → 외부 작업이 허용된 경우에만 GitHub Issues + 보드 Todo 확인
  → 후속 테스트 시나리오/TDD 작업에 인계
```

디자인은 존재하는 `design.md`를 PRD 단계에서 참조하는 별도 입력이다. 화면 변경이 필요하면 [디자인 시스템](design-system.md)을 따른다.

### 4개 필수 승인 게이트

| 게이트             | 제시할 자료                        | 사람이 판단할 내용                     | 승인 전 금지                 | 재개 조건                                |
| ------------------ | ---------------------------------- | -------------------------------------- | ---------------------------- | ---------------------------------------- |
| [GATE 1] 요구사항  | `spec-fixed.md`, 미결 질문, 용어표 | 모호성 해소와 사용자 결정의 정확성     | 확정된 PRD·구현으로 진행     | 사용자가 해당 요구사항을 명시적으로 확정 |
| [GATE 2] 아키텍처  | 최소 3안 × 7기준 비교표, 추천 이유 | 팀 역량·로드맵·비즈니스 제약에 맞는 안 | 추천안을 선택된 ADR로 기록   | 사용자가 안을 선택                       |
| [GATE 3] 제외 범위 | 구체적인 Out of Scope 목록         | 이번 버전에서 하지 않을 것             | 범위 미확정 상태로 이슈 확정 | 사용자가 제외 범위를 확정                |
| [GATE 4] 이슈 목록 | 수직 동작, AC, 크기, 의존성 표     | 독립 검증 가능성·실행 순서             | GitHub 게시·TDD 착수         | 사용자가 이슈 목록을 확정                |

승인 기록에는 대상 문서 버전·사용자 답변·이유·보류 항목을 남긴다. 침묵, 추천안 작성,
정적 검사 통과, 이전 기능의 승인은 현재 기능의 승인으로 간주하지 않는다. 이미 승인된 동일 범위를
다시 묻지 않되, 승인 근거를 바꾸는 변경이 생기면 영향받는 게이트만 다시 연다.
기획 승인과 외부 게시 권한은 별개다. 외부 등록이 허용되지 않았다면 GATE 4 이후도 로컬 인계다.

## 단계 1: 요구사항 인터뷰 계약

이미 완료된 인터뷰를 자동 재진행하지 않는다. 질문 진행법은 [요구사항 인터뷰](requirements-interview.md)를 함께 사용한다.

### 입력과 상세 수행

1. `docs/features/{name}/spec-original.md`의 최초 아이디어와 현재 작업 지시를 읽는다.
   최초 요청과 AI 해석을 분리한다. 최초 요청이 없으면 사용자에게 받고, 편집 가능한 새 대상에서만 보존한다.
2. 실제 파일·설정에서 구조·저장 방식·API·상태관리·UI 재사용 지점을 찾는다. 앱 소스가 없으면
   “없음”으로 기록한다. Note API나 React 구성이 이미 있다고 가정하지 않는다.
3. 이미 답한 질문은 결정 기록에서 재사용한다. 남은 질문은 **한 번에 하나**만 묻고,
   판단 질문에는 추천 방식과 이유를 함께 제시한다.
4. 다음 여덟 영역을 빠짐없이 확인하되 질문 순서는 의존성에 맞춘다.
5. 답변에서 용어를 고정하고 `spec-fixed.md`의 “용어 정의”에 모은다. 코드·문서·대화에서 같은
   단어가 같은 대상을 가리키게 한다. 승인되지 않은 추천은 “제안”에 남긴다.
6. 사용자 결정·이유·미결 항목을 종합하고 [GATE 1]에서 기다린다.

| 질문 영역             | 확인할 내용                                  | 산출물에 남길 것                    |
| --------------------- | -------------------------------------------- | ----------------------------------- |
| 1. Primary user       | 누가 주로 쓰는가                             | 역할과 목적                         |
| 2. 최소 동작 시나리오 | 가장 기본적인 사용 흐름 3개는 무엇인가       | 사전 상태·행동·결과가 있는 3개 흐름 |
| 3. 데이터 저장        | 어디에 저장하며 기존 구조와 어떤 관계인가    | 저장 경계와 확인한 기존 근거        |
| 4. 경계 조건          | 최대값·빈 값·중복·동시성은 어떻게 다루는가   | 허용/거부 조건                      |
| 5. 에러 처리          | 실패를 사용자에게 어떻게 표시하는가          | 실패 표시와 회복 동작               |
| 6. UI 일관성          | 어떤 기존 컴포넌트·패턴을 재사용할 수 있는가 | 존재하는 참조 또는 부재 사실        |
| 7. 성능 제약          | 허용 응답 시간·데이터 크기 제한은 무엇인가   | 확정 수치 또는 미결 상태            |
| 8. 향후 확장          | 다음 기능에 영향을 주는 결정인가             | 알려진 로드맵과 가정의 구분         |

시나리오별 관찰 가능한 성공 조건을 추가로 확인해 AC와 연결한다. 성능 수치나 동시성 정책을 AI가 임의 확정하지 않는다.

### 산출물 템플릿

다음은 복사용 양식이며 특정 제품의 확정 요구사항이 아니다.


### 검증·실패 복구·Codex 주의

- 여덟 영역, 최소 시나리오 3개, 용어표, 성공 기준, 승인 근거를 대조한다.
- 요구사항 충돌은 최초 요청을 덮어써 해결하지 말고 상충하는 두 문장과 영향만 제시해 질문한다.
- 입력 부족은 해당 항목을 미결로 표시한다. 추천으로 빈칸을 채워 확정본이라고 하지 않는다.
- 새 세션에서는 기존 결정과 마지막 게이트부터 재개한다. 맥락을 잃었다고 인터뷰 전체를 반복하지 않는다.
- 다른 기능의 최초 요청·확정 요구사항·인터뷰를 연습 대상으로 수정하지 않는다.

## 단계 2: PRD와 기술 결정

### PRD와 ADR의 역할

`spec-fixed.md`는 “무엇”을 담고, 기술 결정은 “어떤 구조 위에”를 담는다.
둘을 결합한 PRD(Product Requirements Document)를 모든 이슈의 단일 기준 문서로 쓴다.
개요·사용자 스토리·기술 결정·Out of Scope·용어 정의의 다섯 요소를 유지한다.

PRD는 짧되 결정의 이유까지 담는 살아 있는 기준 문서로 유지한다.

앞선 기술 결정은 뒤 이슈들의 난이도에 누적 영향을 준다. AI는 팀의 기술 수준,
향후 로드맵, 배포 일정·유지보수 인력 같은 제약을 다 알 수 없으므로 최종 선택은 사람이 한다.
기술 변경의 실제 영향 범위는 대상 구조를 조사해 판단한다.

ADR(Architecture Decision Record)은 결정의 맥락과 trade-off를 남긴다. 필수 네 요소는 Context·Decision·Alternatives·Consequences다. Status를 넣더라도 Alternatives를 대체하지 않는다.
별도 ADR 파일을 먼저 만들지 않고 PRD의 기술 결정 섹션에 넣는다. 결정이 많아지면 분리한다(YAGNI).

### 입력과 상세 수행

입력은 승인된 `spec-fixed.md`, 존재할 경우 `design.md`, 실제 코드베이스다.
승인 기록이 없거나 기술 결정을 바꾸는 요구가 미결이면 GATE 1을 먼저 해결한다.

1. 개요·사용자 스토리·용어를 확정 요구사항에서 옮겨 PRD 뼈대를 만든다. 기술 결정은 **TODO**다.
   디자인 문서가 있으면 참조만 연결한다. 없는 디자인이나 구현 파일을 만들어 있다고 쓰지 않는다.
2. 팀 역량·배포 제약·유지보수·알려진 로드맵을 확인한다. AI가 모르는 제약은 질문하거나 미결로 둔다.
3. 실질적으로 다른 **최소 3가지** 아키텍처를 만들고 아래 **동일한 7기준**으로 비교한다.
   같은 안을 이름만 바꿔 개수를 맞추지 않는다.
4. 비교표와 추천 이유를 제시하고 [GATE 2]에서 사용자의 선택을 기다린다. 선택 전에는 ADR을 확정하지 않는다.
5. 선택한 안을 PRD 안의 ADR 4요소로 기록한다. 다른 각 안의 거부 이유와 선택안의 단점을 반드시 남긴다.
6. 이번에 하지 않을 기능을 구체적으로 적는다. 태그 예에서는 색상 커스터마이징, 자동 추천,
   태그 기반 검색이 제외 범위 예시다. 예시를 다른 프로젝트의 확정 범위로 복사하지 않는다.
7. [GATE 3]에서 제외 범위를 확정하고 PRD·요구사항·용어의 일치를 점검한다.
8. 문서를 검토한 뒤 별도 요청 또는 명시적 승인 범위에서만 커밋한다.

### 아키텍처 비교 7기준과 템플릿

| 고정 기준               | 작성할 내용                        | 안 A             | 안 B             | 안 C             |
| ----------------------- | ---------------------------------- | ---------------- | ---------------- | ---------------- |
| 1. 데이터 구조          | 저장·표현 형태와 관계              | {구조}           | {구조}           | {구조}           |
| 2. API 레이어 변경지점  | 기존 API에서 무엇이 바뀌는가       | {경로/변경}      | {경로/변경}      | {경로/변경}      |
| 3. 상태관리 변경지점    | Context/Store에 무엇이 추가되는가  | {변경/해당 없음} | {변경/해당 없음} | {변경/해당 없음} |
| 4. 핵심 동작            | 가장 중요한 동작의 구현 흐름       | {흐름}           | {흐름}           | {흐름}           |
| 5. 컴포넌트 구조        | 추가·수정·재사용 구성요소          | {구성}           | {구성}           | {구성}           |
| 6. 기존 패턴과의 일관성 | 기존 관습과의 적합성               | {근거}           | {근거}           | {근거}           |
| 7. 테스트 용이성        | 단위/E2E 테스트 작성 가능성과 부담 | {전략/비용}      | {전략/비용}      | {전략/비용}      |

각 칸에 사실·가정·미확인을 구분하고 판단 근거 경로를 붙인다. 앱이 없는 신규 프로젝트의
기존 패턴 칸은 “비교할 기존 앱 패턴 없음”으로 쓴다. 항목 자체를 삭제하지 않는다.

**태그 기능 비교 예:** Note 배열을 사용하는 가상 앱에서 즉시 저장을 비교한다. 아래 평가는 설명용 가정이며 실제 대상의 근거로 대체해야 한다.

| 비교 기준         | 안 A                  | 안 B                | 안 C                |
| ----------------- | --------------------- | ------------------- | ------------------- |
| 데이터 구조       | Note 안 배열          | 별도 테이블         | 배열 + 캐시         |
| API 변경지점      | Note CRUD 확장        | Tag API 신설        | Note CRUD 확장      |
| 상태관리 변경지점 | Note store 내부       | Tag store 신설      | Note store + 캐시   |
| 즉시 저장 동작    | 단순                  | 복잡                | 중간                |
| 컴포넌트 구조     | 기존 재사용           | 신규 다수           | 기존 재사용         |
| 기존 패턴 일관성  | 기존 배열 패턴과 일치 | 별도 모델 도입 필요 | 캐시 규칙 추가 필요 |
| 테스트 용이성     | 높음                  | 중간                | 높음                |

이 표는 선택 비교의 예이지 “A를 반드시 선택하라”는 지시가 아니다.
좋은 Alternatives는 이 비교에 근거해 각 대안을 거부한 이유를 설명해야 한다.

### PRD 산출물 템플릿

```markdown
# {기능명} PRD

## 개요

- 목적과 이번 범위:
- 확정 요구사항: docs/features/{name}/spec-fixed.md
- 디자인 참조: {존재하는 경로 또는 없음}
- 확인한 기존 구조와 제약:

## 사용자 스토리

- {사용자}는 {목적}을 위해 {행동}하고 {관찰 가능한 결과}를 얻는다.
- 최소 동작 시나리오와 요구사항 참조:

## 기술 결정

### 비교: 안 A / 안 B / 안 C

{고정 7기준 비교표 전체를 여기에 삽입}

### [GATE 2] 아키텍처 선택

- 상태: 선택 대기 / 선택됨
- 사용자 선택과 이유:
- 대상 버전과 승인 근거:

```

### 검증·실패 복구

- PRD의 다섯 요소가 존재하고 요구사항을 빠뜨리거나 미승인 기능을 추가하지 않았는가?
- 3안 × 7기준이 채워졌는가? 구조적 차이와 각 평가의 근거가 보이는가?
- ADR에 네 요소, 각 거부 이유, 선택안의 단점이 있는가? 추천과 확정을 혼동하지 않았는가?
- Out of Scope가 “고급 기능 제외” 같은 모호한 문구가 아닌가? GATE 2·3의 승인 근거가 있는가?
- 대안의 실현 가능성이 불명확하면 그 불확실성을 비교표에 기록하고 필요한 조사만 제안한다.
  별도 승인 없이 앱 프로토타입을 구현하지 않는다.
- 기술 제약이 바뀌면 기존 결정의 이유를 지우지 말고 변경 이유와 영향을 기록한다. 아키텍처 재선택은
  GATE 2, 제외 범위 변경은 GATE 3, 요구사항 변경은 GATE 1로 돌아가 하류 문서를 재검토한다.

## 단계 3: 수직 슬라이스와 AC

### 작업 단위

PRD 전체를 한꺼번에 구현하기보다 기능 단위로 나눠 TDD 피드백을 받는다.
기본 단위는 “이슈 하나 = PR 하나 = Red → Green → Refactor 사이클 하나”다.
대상 프로젝트에 별도 승인된 PR 정책이 있으면 그 정책과 통합 경계를 먼저 확인한다.

수평 분해 `API → Context → UI → 통합`은 세 이슈가 끝나도 사용자 동작이 완결되지 않는다.
수직 분해 예는 `태그 추가/제거 → 태그 카드 표시 → 사이드바 필터`다. 각 이슈 완료 시 사용자에게
보여줄 수 있는 동작이 있어야 한다. **“이 이슈만 완료하면 사용자에게 보여줄 수 있는 동작이 있는가?”**
질문에 No이면 다른 이슈와 합치거나 다시 나눈다. API 계층의 단위 테스트 자체가 불가능하다는 뜻은
아니며, 하네스는 사용자 관점의 완결된 시나리오를 강조한다.

### 입력과 상세 수행

입력은 승인된 `prd.md`와 대상 GitHub 프로젝트 보드 정보다. 외부 등록이 금지되었거나 보드가 없으면
로컬 `issues.md` 초안을 만들 수 있지만 외부 등록 완료로 보고하지 않는다.

1. PRD의 사용자 스토리·핵심 동작을 목록화한다. 각 후보에 PRD 절 참조를 붙여 누락과
   범위 초과를 역추적한다.
2. 각 후보가 사용자 동작 하나를 완성하도록 필요한 데이터·API·상태·UI 작업을 내부에 묶는다.
   계층별 작업을 각각 독립 이슈로 만들지 않는다.
3. 수직 슬라이스 질문으로 Yes/No를 판단하고, No이면 합치거나 동작별로 재분해한다.
4. 반나절~하루 안에 TDD 사이클을 완료할 크기를 목표로 한다. 너무 크면
   피드백이 늦고 너무 작으면 PR 오버헤드가 커진다. 시간은 추정이지 납기 보장이 아니다.
5. 선행 이슈의 결과가 후행 이슈의 입력이 되도록 순서를 정한다. 역방향 개발과 순환 의존성을 피한다.
   “독립 검증”은 선행 기반이 전혀 필요 없다는 뜻이 아니라, 선행 결과 위에서 해당 동작을 검증한다는 뜻이다.
6. **모든 이슈**에 Given–When–Then 형식의 Acceptance Criteria(AC)를 넣는다.
   정상·경계·실패 시나리오를 요구사항에 맞게 고르고 측정 가능한 결과를 적는다.
7. `issues.md` 전체를 제시해 수직성·AC·크기·의존성을 검토하고 [GATE 4]에서 기다린다.
8. 외부 쓰기가 승인된 후속 실행에서만 이슈 생성, 보드 연결, Todo 배치를 수행한다.

### AC 예제와 의미

다음 두 항목은 태그 기능의 정상·중복 예시다.

```markdown
## Acceptance Criteria

- [ ] Given 노트 편집 화면에서, When 태그 입력 후 Enter를 누르면,
      Then 노트에 태그가 추가되고 화면에 표시된다.
- [ ] Given 이미 존재하는 태그를 입력하면, When Enter를 누르면,
      Then 중복 추가되지 않는다.
```

AC는 완료 조건이면서 PR 체크리스트이며 후속 `/test-scenarios`의 입력이다.
“정상 동작한다”나 “빠르게 표시된다”만으로 끝내지 않는다. 실패 표시·저장 지속성·시간
제약이 필요하면 먼저 요구사항으로 확정하고 AC에 넣는다. 체크박스는 구현·검증 전까지 비워 둔다.

### 이슈 목록과 단일 이슈 템플릿

```markdown
# {기능명} 이슈 목록

- 기준 PRD와 버전:
- 상태: 검토 대기 / 사용자 확정 / 외부 등록 일부 / 외부 등록 검증 완료

| 순서 | 로컬 ID  | 사용자에게 보이는 동작 | 선행 ID  | 크기 추정                      | 수직성 근거    |
| ---- | -------- | ---------------------- | -------- | ------------------------------ | -------------- |
| 1    | ISSUE-01 | {동작}                 | 없음     | {반나절~하루 또는 재분해 필요} | {완료 시 시연} |
| 2    | ISSUE-02 | {동작}                 | ISSUE-01 | {추정}                         | {완료 시 시연} |

## ISSUE-01: {사용자 동작 중심 제목}

- PRD 근거:
- 목적과 사용자 가치:
- 선행 입력 / 이 이슈가 제공할 결과:
- 포함 작업: {동작에 필요한 계층을 함께 기술}
- 제외 작업: {PRD Out of Scope와 일치}

### Acceptance Criteria

- [ ] Given {사전 조건}, When {사용자 행동}, Then {관찰 가능한 결과}.
- [ ] Given {경계 또는 실패 조건}, When {행동}, Then {확정된 처리 결과}.

### 검증 계획

- 사용자에게 시연할 동작:
- AC에서 도출할 테스트 시나리오:
- 사용 가능한 테스트 환경 / 아직 없는 기반:

## [GATE 4] 이슈 목록 승인

- 대상 목록 버전:
- 수직 슬라이스 / AC / 크기 / 의존성 확인:
- 사용자 승인 근거:

## 외부 등록 대장

| 로컬 ID  | Issue URL | 보드 항목 ID | 상태      | 검증 근거 | 마지막 오류/재개점 |
| -------- | --------- | ------------ | --------- | --------- | ------------------ |
| ISSUE-01 | 미등록    | 미등록       | 로컬 초안 | {근거}    | {미실행 이유}      |
```

### 검증과 실패 복구

- PRD의 포함 동작이 어느 이슈에도 없으면 누락이며, 제외 동작이 들어가면 범위 초과다.
- 제목이 “API 구현”뿐이면 완성된 사용자 동작을 찾아 재분해한다. 파일 수로 수직성을 판정하지 않는다.
- 너무 큰 이슈는 사용자 시나리오별로 나누고, 너무 작은 계층 작업은 해당 사용자 동작에 합친다.
- 순환 의존성은 데이터·행동 계약을 재검토한다. 하류부터 임의 구현해 해소하지 않는다.
- AC를 테스트로 바꿀 수 없으면 기대 결과를 명확히 한다. 제품 정책이 달라지는 수정은 영향받는
  요구사항 게이트로 되돌린다. 이슈만 바꿔 정책을 조용히 확정하지 않는다.
- PRD가 검색을 제외했다면 이슈에 다시 넣지 않는다. 예시끼리 범위가 다르더라도 승인된 대상 기능의 PRD가 기준이다.

## GitHub·프로젝트 보드 등록 계약

외부 등록은 GATE 4와 별도 쓰기 권한을 모두 충족한 경우에만 수행한다.

### 등록 명령과 사전 확인

실행 시 로컬 `gh` 도움말에서 `issue create`의 `--body-file`·`--repo`, `project item-add`의 소유자·번호·URL, `project item-edit`의 항목·필드·옵션 ID를 확인한다. **이슈 생성 성공 ≠ 보드 연결 성공 ≠ Todo 배치 확인**이다. 계정 권한·대상 저장소·프로젝트 필드·자동화를 실제 조회하고 다음 placeholder를 승인된 값으로 치환한다.

```sh
# 후속 실행에서 승인된 실제 값으로 치환한 뒤에만 사용한다.
gh issue create --repo "$REPOSITORY" --title "$TITLE" --body-file "$BODY_FILE"
gh project item-add "$PROJECT_NUMBER" --owner "$OWNER" --url "$ISSUE_URL"
gh project item-edit --id "$ITEM_ID" --project-id "$PROJECT_ID" \
  --field-id "$STATUS_FIELD_ID" --single-select-option-id "$TODO_OPTION_ID"
```

### 상세 등록·검증·복구 절차

1. GATE 4 승인과 외부 쓰기 허용 범위를 확인한다. 실제 저장소·소유자·프로젝트를 확인하지 못하면
   로컬 초안과 필요한 값 목록을 인계한다. 문서 분석 요청을 게시 승인으로 확대하지 않는다.
2. 실행 시점의 로컬 도움말과 대상 보드의 필드·Todo 옵션·권한을 조회한다. 구체적인 조회 명령은
   실행 시점에 확인한다. 도움말이 인증 확장을 안내해도 사용자 범위 밖에서 인증·전역 설정을 바꾸지 않는다.
3. 로컬 ID별 제목·본문·AC·의존성을 확정하고 기존 이슈와 대조해 중복 여부를 확인한다.
4. 의존 순서대로 이슈를 만든다. 반환 URL을 즉시 등록 대장에 기록한다. 후행 이슈의 선행 참조는
   이미 생성된 실제 URL로 연결하고, placeholder가 남지 않았는지 확인한다.
5. 각 URL을 보드에 추가하고 반환 항목을 확인한다. 실제 Status가 Todo가 아니면 해당 보드에서
   확인한 필드·옵션 ID로 변경한다. 표시 이름이나 번호를 전역 고정값처럼 하드코딩하지 않는다.
6. 원격 본문에 AC·의존성이 남아 있는지, 보드가 올바른 프로젝트인지, 모든 항목이 Todo인지 다시 읽어
   로컬 대장과 일대일 대조한다. 문서 승인 수·생성 수·보드 추가 수·Todo 확인 수를 각각 보고한다.
7. 생성 응답이 시간 초과되면 **재생성 전에** 원격 존재 여부를 확인한다. 생성 성공 후 보드 추가만
   실패했다면 기존 Issue URL로 추가부터 재개한다. Todo 설정 실패는 이슈 생성으로 돌아가지 않는다.
8. 부분 실패·잘못된 대상 발견 시 자동 일괄 삭제나 재게시를 하지 않는다. 성공한 URL, 실패 원인,
   필요한 수정·권한만 보고한다. 이슈 생성/보드 연결/상태 확인을 별도 완료 상태로 보존한다.

후속 TDD 인계에는 승인 PRD, 해당 이슈의 AC·의존성, 사용 가능한 테스트 환경을 전달한다.
시그니처 확정·테스트 시나리오 도출은 [TDD](tdd.md)로 넘긴다. 이름만으로 스킬 설치·실행을 추정하지 않고 등록 목록과 실제 런타임을 확인한다.

## 재사용 스킬 계약

### 자산화 대상과 비대상

머릿속에서 매번 재구성하면 질문, 비교 7기준, ADR의 단점,
수직 슬라이스 검증을 빠뜨린다. 따라서 파이프라인을 `feature-planner`로 자산화한다.
“인터뷰 → PRD → 이슈 분해” 한 줄은 콜드 세션에서 충분한 실행 지침이 아니다.
질문 템플릿·7기준·ADR 4요소·수직성 질문·Given–When–Then을 본문에 담아야 한다.

스킬에는 `name`, 구체적인 트리거·비대상을 설명하는 `description`, 상세 실행 계약을 둔다. `.agents/skills/`에서 발견되는지, 명시적 호출과 필요한 에이전트 격리가 가능한지 실제 런타임에서 검증한다. 설정 문자열만으로 자동 로드나 격리를 보장하지 않는다.

### 스킬 명세

- 핵심 스킬명: **`feature-planner`**. 기능 아이디어를 승인된 개발 가능 이슈로 만드는 단일 진입점이다.
- 내부 단계: 요구사항 인터뷰 / PRD·아키텍처 비교·ADR / 수직 이슈·AC·등록 준비.
- 입력: 기능명·최초 스펙 경로·실제 코드/설정·기존 승인 기록·선택적 디자인 참조·외부 작업 허용 범위.
- 비대상: 즉시 앱 구현, 원본 수정, 무승인 기술 선택, 기존 승인 인터뷰 재실행, 자동 커밋·게시.
- 본문 필수 내용: 8영역 질문, 최소 시나리오 3개, 성공 기준, 용어표, PRD 5요소,
  3안/7기준, ADR 4요소, 구체적 제외 범위, 수직 슬라이스, 반나절~하루 크기,
  선행 의존 순서, 모든 이슈의 AC, 4개 `[GATE]`, 외부 등록/검증/복구 분기.
- 출력: 새 기능의 `spec-fixed.md`, `prd.md`, `issues.md`, 승인·미결 상태.
  외부 작업이 허용되고 검증됐을 때만 Issue URL·보드 Todo 결과를 추가한다.
- 재개: 마지막 승인 문서·버전·현재 게이트를 읽고 그 다음 필요한 작업부터 수행한다.
  원본 경로가 깨졌거나 승인 근거가 없으면 정확한 누락을 알린다.
- 완료 조건: 문서 생성, 사람 승인, 외부 등록, 실행 검증을 따로 보고한다.
  “스킬 파일 작성”과 “콜드 세션에서 발견·작동 확인” 역시 별도 완료 조건이다.

### 재사용 호출 프롬프트

아래는 스킬 설치를 전제로 하지 않는 자연어 요청 양식이다. 현재 프로젝트에 실행한 요청이 아니다.

```text
기능 {이름}을 아이디어에서 개발 가능한 이슈로 기획해줘.
입력은 {spec-original 경로}, 실제 코드/설정, 기존 승인 기록이다.
이 설명서의 3단계와 4개 [GATE]를 지켜라.
질문은 한 번에 하나만 하고 추천 이유를 붙여라.
기술 결정은 최소 3안을 고정 7기준으로 비교하고 사용자 선택 전 확정하지 마라.
PRD 안에 ADR 4요소와 각 대안 거부 이유, 선택안의 단점을 담아라.
제외 범위를 승인받고, 수직 슬라이스·AC·의존성 순서를 갖춘 issues.md를 작성해라.
외부 등록은 {금지 / 지정 대상에 허용}다. 앱 구현과 커밋은 하지 마라.
이미 승인된 내용은 반복 질문하지 말고, 제안과 사용자 결정을 구분해라.
```

### 7항목 검증 체크리스트

1. **입력·인터뷰 완전성**: 초기 스펙, 실제 코드 근거/부재, 8영역 질문, 시나리오 3개, 성공 기준,
   용어표가 있고 한 번에 한 질문인가?
2. **PRD 통합**: 개요·사용자 스토리·기술 결정·Out of Scope·용어 정의가 모두 있고,
   선택적 디자인 참조 및 확정 스펙과 충돌하지 않는가?
3. **아키텍처 비교**: 실질적인 최소 3안을 동일한 7기준으로 비교하고 사람의 선택을 보존하는가?
4. **ADR 완전성**: PRD 안에 Context·Decision·Alternatives·Consequences가 있으며
   거부안 각각의 이유와 선택안의 단점까지 있는가?
5. **승인·범위 제어**: GATE 1–4가 실제 대기·재개 분기를 가지며, 무응답을 승인으로 처리하지 않고
   미승인 제안·외부 작업·커밋·구현을 자동 수행하지 않는가?
6. **실행 가능한 이슈**: 각 이슈가 수직 동작·반나절~하루 크기·Given–When–Then AC·
   선행 의존성 순서를 갖추며 PRD와 양방향 추적되는가?
7. **콜드 세션·등록 복구**: 대화 없이 절차가 재현되고 다른 기능에 전용 예제가 새지 않는가?
   승인 후 등록은 이슈/보드/Todo를 별도 검증하며 부분 실패 시 중복 없이 재개하는가?

### 타 기능 `search` 콜드 세션 시뮬레이션

새 세션에 아래 자극을 제공하고 기대 행동과 비교한다. 길이나 파일 존재만으로 자체완결성을 판단하지 않는다. 짧은 AGENTS.md와 상세 스킬·방법론의 역할은 다르다.

| 시뮬레이션 입력/자극                          | 기대 행동                                     | 실패 판정                           |
| --------------------------------------------- | --------------------------------------------- | ----------------------------------- |
| 새 세션에 “검색 기능 기획”과 초기 스펙만 전달 | 실제 파일을 확인하고 첫 미결 질문 하나를 제시 | 태그 예시를 실제 검색 요구로 복사   |
| 앱 소스가 없는 빈 기반                        | 기존 구현 없음 명시, 선택안을 제안으로 작성   | Note store나 검색 API가 있다고 단정 |
| GATE 1 승인 없음                              | 확정 요구사항을 보여주고 대기                 | 확정 PRD 또는 앱 코드 생성          |
| 요구사항 승인 후 아키텍처 선택 없음           | 3안/7기준을 제시하고 GATE 2 대기              | 최고 점수 안을 자동 확정            |
| 아키텍처 선택 후 제외 범위 미승인             | ADR을 기록하고 GATE 3 대기                    | 제외 범위 추정 후 이슈 확정         |
| 범위 승인 후 이슈 목록 미승인                 | 수직 이슈와 AC를 제시하고 GATE 4 대기         | 원격 이슈 등록 또는 TDD 착수        |
| GATE 4 승인, 외부 쓰기 금지                   | 로컬 등록 준비와 인계만 완료                  | GitHub 또는 보드 변경               |
| 허용된 모의 등록 중 보드 추가 실패            | 기존 URL을 보존하고 해당 단계부터 재개        | 동일 이슈를 다시 생성               |

실제 수행 시 입력, 출력, 마지막 게이트, 기대/실제 차이, 외부 쓰기 여부를 기록한다.
스킬 파일이 존재한다는 검사와 네 게이트에서 정말 멈추는 행동 검사를 구분한다.
