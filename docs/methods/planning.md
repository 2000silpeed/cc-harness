# 기획: 요구사항에서 개발 가능한 이슈까지

이 문서는 아이디어를 확정 요구사항, 제품 요구사항 문서(PRD), 아키텍처 결정 기록(ADR), 사용자가 확인할 수 있는 수직 이슈로 바꾸는 실행 계약입니다. 문서 작성, 사용자 직접 승인, 위임 정책에 따른 결정, 독립 감사, 외부 게시, 제품 구현은 각각 별도 상태로 관리합니다. 예시에 나오는 태그와 Note 구조는 설명을 위한 가정이며 대상 앱의 요구사항이 아닙니다.

## 파이프라인과 승인

먼저 요구사항을 확정하고 기술 선택의 이유를 보존한 뒤, 사용자가 확인할 수 있는 작은 동작으로 나눕니다. 같은 절차를 반복할 때도 질문, 대안 비교, 단점, 수직 슬라이스 검토를 빠뜨리지 않도록 재사용 가능한 절차로 만듭니다. 구현 승인이 없으면 사용자가 게이트를 직접 결정합니다. 결과·구현 승인이 있으면 승인 범위의 후속 판단을 진행하며, 별도로 게이트 정책을 위임한 경우에는 지정한 기준과 한계를 따릅니다.

**[원본 워크플로] 3단계 파이프라인:**

```text
spec-original.md + 실제 코드/설정
  → 단계 1: 요구사항 인터뷰
  → spec-fixed.md
  → [GATE 1] 요구사항·용어 확정
  → 단계 2: PRD 뼈대 + 아키텍처 최소 3안/7기준 비교
  → [GATE 2] 아키텍처 선택
  → PRD 내부 ADR 4요소 + Out of Scope
  → [GATE 3] 제외 범위 확정
  → prd.md
  → 단계 3: 수직 슬라이스 + AC + 의존성 순서
  → issues.md
  → [GATE 4] 이슈 목록 검토·확정
  → 외부 작업이 허용된 경우에만 GitHub Issues + 보드 Todo 확인
  → 후속 테스트 시나리오/TDD 작업에 인계
```

디자인은 PRD 단계에서 존재하는 `design.md`를 참조하는 별도 입력입니다. 화면을 바꿔야 한다면 [디자인 시스템](design-system.md)을 따릅니다.

### 4개 필수 의사결정 게이트

게이트의 기본 모드는 `human-required`입니다. [승인과 외부 작업](../harness/lifecycle.md#5-승인과-외부-작업)에 따라 명확한 결과와 로컬 구현·검증을 승인받았다면 통상적인 후속 선택은 `policy-delegated`, G4·G5의 독립 검토는 `auto-with-audit`로 기록하고 진행합니다. 아래 표의 직접 승인 대기는 구현 승인이 없을 때의 기본 경로입니다. 별도 게이트 정책이나 사용자 제한은 그 범위대로 유지합니다.

| 게이트             | 제시할 자료                        | 기본 결정                        | 허용되는 위임과 필수 상향                                                    |
| ------------------ | ---------------------------------- | -------------------------------- | ---------------------------------------------------------------------------- |
| [GATE 1] 요구사항  | `spec-fixed.md`, 미결 질문, 용어표 | 사용자가 요구사항·용어를 확정    | 정책 위임은 가능하지만 제품 목적·가치 충돌 또는 의도 누락은 항상 사용자 상향 |
| [GATE 2] 아키텍처  | 최소 3안 × 7기준 비교표, 추천 이유 | 사용자가 기술안을 선택           | 명시된 기술 판단 기준·예산·위험 한도 안에서 위임 가능                        |
| [GATE 3] 제외 범위 | 구체적인 Out of Scope 목록         | 사용자가 이번 버전의 경계를 확정 | 범위·비용·우선순위 envelope 안에서만 위임 가능                               |
| [GATE 4] 이슈 목록 | 수직 동작, AC, 크기, 의존성 표     | 사용자가 이슈 목록을 확정        | `auto-with-audit`로 위임하면 분리된 검증자의 독립 감사 후 통과 가능          |

별도 게이트 정책에는 대상·버전, 목적·판단 기준, 허용·금지 범위, 비용·시간·위험 한도, 외부 권한, 만료·철회, 상향·STOP을 기록하고 누락·충돌을 해결합니다. 통상적인 결과·구현 승인에는 사용자 원문과 승인 결과·실행 범위, AI 선택·이유·적용 한계를 기록하며 사용자가 게이트명이나 인위적인 위임 필드를 채우게 하지 않습니다. `policy-delegated` 판단과 `auto-with-audit`의 독립 검증자·감사 결과는 사용자 직접 결정과 분리합니다.

사용자의 침묵, AI의 추천안 작성, 정적 검사 통과, 이전 기능의 승인이나 위임을 현재 기능의 권한으로 간주하지 않습니다. 이미 유효하게 결정된 같은 범위를 다시 묻지 않으며, 결정 근거나 envelope가 바뀌면 영향을 받는 게이트만 다시 엽니다. 기획 게이트와 외부 작업 권한은 별개입니다. Git 초기화·브랜치·커밋·push·PR·병합·배포·유료 호출·파괴적 작업·보안/법적 결정과 다른 외부 쓰기는 정확한 대상과 범위가 별도로 포함되지 않으면 수행하지 않습니다.

## 단계 1: 요구사항 인터뷰 계약

이미 완료된 인터뷰를 자동으로 다시 진행하지 않습니다. 질문하는 방법은 [요구사항 인터뷰](requirements-interview.md)를 함께 사용합니다.

### 입력과 상세 수행

1. `docs/features/{name}/spec-original.md`의 최초 아이디어와 현재 작업 지시를 읽습니다. 최초 요청과 AI의 해석은 분리합니다. 최초 요청이 없다면 사용자에게 받아, 편집할 수 있는 새 대상에만 보존합니다.
2. 실제 파일과 설정에서 구조, 저장 방식, API, 상태 관리, UI 재사용 지점을 찾습니다. 앱 소스가 없다면 “없음”으로 기록합니다. Note API나 React 구성이 이미 있다고 가정하지 않습니다.
3. 이미 답한 질문은 결정 기록에서 재사용합니다. 남은 질문은 **한 번에 하나**만 묻고, 판단이 필요한 질문에는 추천 방식과 이유를 함께 제시합니다.
4. 다음 여덟 영역을 빠짐없이 확인하되 질문 순서는 항목 사이의 의존성에 맞춥니다.
5. 답변에서 용어를 고정하고 `spec-fixed.md`의 “용어 정의”에 모읍니다. 코드, 문서, 대화에서 같은 단어가 같은 대상을 가리키게 합니다. 승인되지 않은 추천은 “제안”으로 남깁니다.
6. 사용자 결정과 구현 승인, AI 기본값·이유·적용 경계, 남은 중요한 질문을 종합합니다. 구현 승인이 없으면 [GATE 1]에서 기다립니다. 승인한 목적을 바꾸지 않는 낮은 위험의 세부는 가역적 기본값으로 해결하되 목적·가치·중대한 범위·위험이 미결이면 상향합니다. 필수 정책과 성공 조건을 갖춘 뒤에만 G1을 통과합니다.

| 질문 영역             | 확인할 내용                                  | 산출물에 남길 것                    |
| --------------------- | -------------------------------------------- | ----------------------------------- |
| 1. Primary user       | 누가 주로 쓰는가                             | 역할과 목적                         |
| 2. 최소 동작 시나리오 | 가장 기본적인 사용 흐름 3개는 무엇인가       | 사전 상태·행동·결과가 있는 3개 흐름 |
| 3. 데이터 저장        | 어디에 저장하며 기존 구조와 어떤 관계인가    | 저장 경계와 확인한 기존 근거        |
| 4. 경계 조건          | 최대값·빈 값·중복·동시성은 어떻게 다루는가   | 허용/거부 조건                      |
| 5. 에러 처리          | 실패를 사용자에게 어떻게 표시하는가          | 실패 표시와 회복 동작               |
| 6. UI 일관성          | 어떤 기존 컴포넌트·패턴을 재사용할 수 있는가 | 존재하는 참조 또는 부재 사실        |
| 7. 성능 제약          | 허용 응답 시간·데이터 크기 제한은 무엇인가   | 확정 수치 또는 미결 상태            |
| 8. 향후 확장          | 다음 기능에 영향을 주는 결정인가             | 알려진 로드맵과 가정의 구분         |

각 시나리오에서 관찰할 수 있는 성공 조건을 인수 조건(AC), 즉 기능이 요구대로 완성됐는지 판단하는 조건과 연결합니다. 성능 수치나 동시성 정책을 사용자가 정한 사실로 꾸미지 않습니다. 구현 승인 범위의 세부 목표를 AI가 정했다면 이유·한계와 실제 검증 결과를 구분합니다.

### 산출물 템플릿

다음 양식은 복사해 사용할 수 있지만, 그 자체가 특정 제품의 확정 요구사항은 아닙니다.

```markdown
# {기능명} 확정 요구사항

## 원본과 현재 근거

- 최초 아이디어: docs/features/{name}/spec-original.md
- 확인한 코드/설정: {경로와 사실, 없으면 없음}
- 상태: 제안 / 사용자 확인 대기 / 확정

## 주 사용자와 목적

{누가 어떤 문제를 해결하는가}

## 최소 동작 시나리오 3개

1. {사전 상태 → 행동 → 관찰 가능한 결과}
2. {사전 상태 → 행동 → 관찰 가능한 결과}
3. {사전 상태 → 행동 → 관찰 가능한 결과}

## 동작 정책

- 저장 방식 및 기존 구조와의 관계:
- 최대값 / 빈 값 / 중복 / 동시성:
- 에러 표시 및 복구:
- 재사용할 UI 패턴 또는 부재:
- 응답 시간 / 데이터 크기 제한:
- 향후 확장 영향:
- 성공 기준:

## 용어 정의

| 용어   | 의미   | 같은 뜻으로 쓰지 않을 단어 |
| ------ | ------ | -------------------------- |
| {용어} | {정의} | {혼동 표현}                |

## 결정과 미결 사항

| 항목   | 결정             | 결정 모드·출처                                                                | 이유   | 근거        | 미승인 제안 |
| ------ | ---------------- | ----------------------------------------------------------------------------- | ------ | ----------- | ----------- |
| {항목} | {결정 또는 미결} | {human-required 사용자 / policy-delegated 정책 / auto-with-audit 정책+검증자} | {이유} | {근거 참조} | {제안}      |

## [GATE 1] 요구사항 확정

- 대상 버전:
- 모드: human-required / policy-delegated / auto-with-audit
- 결정 출처와 근거:
- 위임 envelope / 독립 감사 결과:
- 보류 항목:
```

### 검증·실패 복구·Codex 주의

- 여덟 영역, 최소 시나리오 3개, 용어표, 성공 기준, 게이트 결정 근거가 서로 맞는지 대조합니다.
- 요구사항이 충돌하면 최초 요청을 덮어쓰지 않습니다. 상충하는 두 문장과 그 영향만 제시하고 사용자에게 묻습니다.
- 중요한 입력이 부족하면 해당 항목을 미결로 표시하고 관련 게이트를 통과시키지 않습니다. 구현 승인 범위의 낮은 위험의 세부는 기본값·이유·출처를 기록해 해결하며 단순 추천이나 사용자 직접 결정으로 혼동하지 않습니다.
- 새 세션에서는 기존 결정과 마지막 게이트부터 재개합니다. 맥락을 잃었다는 이유로 인터뷰 전체를 반복하지 않습니다.
- 다른 기능의 최초 요청, 확정 요구사항, 인터뷰를 연습 대상으로 수정하지 않습니다.

## 단계 2: PRD와 기술 결정

### PRD와 ADR의 역할

`spec-fixed.md`는 “무엇을 만들지”를 담고, 기술 결정은 “어떤 구조 위에 만들지”를 담습니다. 둘을 결합한 PRD(Product Requirements Document, 제품 요구사항 문서)를 모든 이슈의 단일 기준 문서로 사용합니다. 개요, 사용자 스토리, 기술 결정, Out of Scope(제외 범위), 용어 정의의 다섯 요소를 유지합니다.

PRD는 간결하게 작성하되 결정의 이유까지 담고, 변경에 맞춰 계속 갱신하는 기준 문서로 유지합니다.

앞선 기술 결정은 뒤에 이어지는 이슈들의 난이도에 계속 영향을 줍니다. AI는 팀의 기술 수준, 향후 로드맵, 배포 일정, 유지보수 인력 같은 제약을 자동으로 안다고 가정하지 않습니다. 기본적으로 사용자가 선택하며, 결과·구현 승인이 있으면 그 결과에 필요한 통상적인 기술안을 근거와 한계를 기록해 선택합니다. 중요한 비용·위험·범위 변화나 별도 정책 한계는 확인합니다. 기술 변경의 실제 영향 범위는 대상 구조를 조사해 판단합니다.

ADR(Architecture Decision Record, 아키텍처 결정 기록)은 결정의 맥락과 장단점(trade-off)을 남깁니다. 필수 네 요소는 Context, Decision, Alternatives, Consequences입니다. Status를 추가하더라도 Alternatives를 대신할 수 없습니다. 처음부터 별도 ADR 파일을 만들지 않고 PRD의 기술 결정 절에 기록합니다. 결정이 많아질 때만 분리해, 아직 필요하지 않은 구조를 미리 만들지 않는 YAGNI 원칙을 지킵니다.

### 입력과 상세 수행

입력은 GATE 1을 유효하게 통과한 `spec-fixed.md`, 존재하는 경우의 `design.md`, 실제 코드베이스입니다. 게이트 기록이 없거나 기술 결정을 바꾸는 요구가 아직 결정되지 않았다면 GATE 1을 먼저 해결합니다.

1. 개요, 사용자 스토리, 용어를 확정 요구사항에서 옮겨 PRD의 뼈대를 만듭니다. 기술 결정은 **TODO**로 둡니다. 디자인 문서가 있다면 참조만 연결하며, 존재하지 않는 디자인이나 구현 파일을 만들었다고 쓰지 않습니다.
2. 팀 역량, 배포 제약, 유지보수 여건, 알려진 로드맵을 확인합니다. 승인 결과를 좌우하는 공백은 질문하고, 로컬 구현 범위의 가역적 세부는 기본값과 이유·한계로 기록합니다.
3. 실질적으로 다른 아키텍처를 **최소 3가지** 만들고 아래의 **동일한 7기준**으로 비교합니다. 같은 안의 이름만 바꿔 개수를 채우지 않습니다.
4. 비교표와 추천 이유를 제시합니다. 구현 승인이나 유효한 기술 선택 위임이 없으면 [GATE 2]에서 기다립니다. 권한이 있으면 승인 결과·제한과 실제 근거를 대조해 선택하고 사용자 선택과 구분해 ADR을 확정합니다.
5. 선택한 안을 PRD 안에 ADR의 네 요소로 기록합니다. 사용자 직접 선택과 위임 정책 판정을 구분하고, 선택하지 않은 각 안의 거부 이유와 선택한 안의 단점을 반드시 남깁니다.
6. 이번에 만들지 않을 기능을 구체적으로 적습니다. 태그 예에서 색상 사용자 설정, 자동 추천, 태그 기반 검색은 제외 범위를 설명하기 위한 예입니다. 이를 다른 프로젝트의 확정 범위로 그대로 복사하지 않습니다.
7. [GATE 3]에서 제외 범위를 확정합니다. 결과·구현 승인 또는 별도 위임 범위 안인지 확인하고 PRD, 요구사항, 용어의 일치를 점검합니다. 승인한 핵심 결과나 AC를 편의상 줄이지 않습니다.
8. 문서를 검토합니다. 커밋은 게이트 위임과 별도이며 정확한 대상과 범위가 명시된 경우에만 수행합니다.

### 아키텍처 비교 7기준과 템플릿

| 고정 기준               | 작성할 내용                        | 안 A             | 안 B             | 안 C             |
| ----------------------- | ---------------------------------- | ---------------- | ---------------- | ---------------- |
| 1. 데이터 구조          | 저장·표현 형태와 관계              | {구조}           | {구조}           | {구조}           |
| 2. API 레이어 변경지점  | 기존 API에서 무엇이 바뀌는가       | {경로/변경}      | {경로/변경}      | {경로/변경}      |
| 3. 상태관리 변경지점    | Context/Store에 무엇이 추가되는가  | {변경/해당 없음} | {변경/해당 없음} | {변경/해당 없음} |
| 4. 핵심 동작            | 가장 중요한 동작의 구현 흐름       | {흐름}           | {흐름}           | {흐름}           |
| 5. 컴포넌트 구조        | 추가·수정·재사용 구성요소          | {구성}           | {구성}           | {구성}           |
| 6. 기존 패턴과의 일관성 | 기존 관습과의 적합성               | {근거}           | {근거}           | {근거}           |
| 7. 테스트 용이성        | 단위/E2E 테스트 작성 가능성과 부담 | {전략/비용}      | {전략/비용}      | {전략/비용}      |

각 칸에서 사실, 가정, 미확인을 구분하고 판단 근거가 있는 경로를 붙입니다. 앱이 없는 신규 프로젝트라면 기존 패턴 칸에 “비교할 기존 앱 패턴 없음”이라고 씁니다. 항목 자체를 삭제하지 않습니다.

**태그 기능 비교 예:** Note 배열을 사용하는 가상 앱에서 즉시 저장 방식을 비교합니다. 아래 평가는 설명을 위한 가정이므로 실제 작업에서는 대상 프로젝트에서 확인한 근거로 바꿔야 합니다.

| 비교 기준         | 안 A                  | 안 B                | 안 C                |
| ----------------- | --------------------- | ------------------- | ------------------- |
| 데이터 구조       | Note 안 배열          | 별도 테이블         | 배열 + 캐시         |
| API 변경지점      | Note CRUD 확장        | Tag API 신설        | Note CRUD 확장      |
| 상태관리 변경지점 | Note store 내부       | Tag store 신설      | Note store + 캐시   |
| 즉시 저장 동작    | 단순                  | 복잡                | 중간                |
| 컴포넌트 구조     | 기존 재사용           | 신규 다수           | 기존 재사용         |
| 기존 패턴 일관성  | 기존 배열 패턴과 일치 | 별도 모델 도입 필요 | 캐시 규칙 추가 필요 |
| 테스트 용이성     | 높음                  | 중간                | 높음                |

이 표는 선택지를 비교하는 예일 뿐 “A를 반드시 선택하라”는 지시가 아닙니다. 좋은 Alternatives 기록은 이 비교를 근거로 각 대안을 선택하지 않은 이유를 설명해야 합니다.

### PRD 산출물 템플릿

```markdown
# {기능명} PRD

## 개요

- 목적과 이번 범위:
- 확정 요구사항: docs/features/{name}/spec-fixed.md
- 디자인 참조: {존재하는 경로 또는 없음}
- 확인한 기존 구조와 제약:

## 사용자 스토리

- {사용자}는 {목적}을 위해 {행동}하고 {관찰 가능한 결과}를 얻는다.
- 최소 동작 시나리오와 요구사항 참조:

## 기술 결정

### 비교: 안 A / 안 B / 안 C

{고정 7기준 비교표 전체를 여기에 삽입}

### [GATE 2] 아키텍처 선택

- 상태: 선택 대기 / 선택됨
- 모드: human-required / policy-delegated / auto-with-audit
- 결정과 이유 / 결정 출처:
- 대상 버전과 근거:
- 위임 envelope / 독립 감사 결과:

### ADR: {결정 제목}

**Context** — {당시 문제, 요구, 제약과 근거}
**Decision** — {선택한 안, 결정 출처와 적용 경계; 게이트 통과 전에는 TODO}
**Alternatives** — {거부한 안 B와 그 이유; 거부한 안 C와 그 이유}
**Consequences** — {장점, 단점, 유지보수 부담, 달라지는 것}

## Out of Scope

- {이번에 하지 않을 구체 기능과 경계}
- {필요하면 다음 판단 시점; 자동 구현 약속은 아님}

### [GATE 3] 제외 범위 확정

- 대상 버전:
- 모드: human-required / policy-delegated / auto-with-audit
- 결정 출처와 근거:
- 범위·비용·우선순위 envelope:
```

### 검증·실패 복구

- PRD의 다섯 요소가 존재하고 요구사항을 빠뜨리거나 미승인 기능을 추가하지 않았는가?
- 3안 × 7기준이 채워졌는가? 구조적 차이와 각 평가의 근거가 보이는가?
- ADR에 네 요소, 각 거부 이유, 선택안의 단점이 있는가? 추천과 확정을 혼동하지 않았는가?
- Out of Scope가 “고급 기능 제외” 같은 모호한 문구가 아닌가? GATE 2·3의 모드·결정 출처·근거가 있는가?
- 대안의 실현 가능성이 불명확하면 필요한 조사를 수행하고 근거를 기록합니다. 구현 승인이 없으면 앱 시제품을 만들지 않으며, 승인이 있으면 그 범위의 작은 가역적 로컬 검증만 수행합니다.
- 기술 제약이 바뀌면 기존 결정의 이유를 지우지 않고 변경 이유와 영향을 기록합니다. 아키텍처를 다시 선택해야 하면 GATE 2, 제외 범위가 바뀌면 GATE 3, 요구사항이 바뀌면 GATE 1로 돌아가 이후 문서를 다시 검토합니다.

## 단계 3: 수직 슬라이스와 AC

### 작업 단위

PRD 전체를 한꺼번에 구현하지 않고 기능 단위로 나눠 테스트 주도 개발(TDD)의 피드백을 받습니다. 기본 단위는 “이슈 하나 = PR 하나 = Red → Green → Refactor 사이클 하나”입니다. 대상 프로젝트에 별도로 승인된 PR 정책이 있다면 그 정책과 통합 경계를 먼저 확인합니다.

`API → Context → UI → 통합`처럼 계층별로 수평 분해하면 세 이슈가 끝나도 사용자의 동작이 완성되지 않을 수 있습니다. 수직 분해의 예는 `태그 추가/제거 → 태그 카드 표시 → 사이드바 필터`입니다. 각 이슈를 마칠 때 사용자에게 보여줄 수 있는 동작이 있어야 합니다. **“이 이슈만 완료하면 사용자에게 보여줄 수 있는 동작이 있는가?”**라는 질문에 No라면 다른 이슈와 합치거나 다시 나눕니다. 이는 API 계층의 단위 테스트가 불가능하다는 뜻이 아닙니다. 하네스는 사용자 관점에서 완결된 시나리오를 강조합니다.

### 입력과 상세 수행

입력은 GATE 2·3을 유효하게 통과한 `prd.md`와, 외부 등록이 별도로 허용된 경우의 대상 GitHub 프로젝트 보드 정보입니다. 외부 등록이 금지되었거나 보드가 없다면 로컬 `issues.md` 초안은 만들 수 있지만 외부 등록이 끝났다고 보고하지 않습니다.

1. PRD의 사용자 스토리와 핵심 동작을 목록으로 만듭니다. 각 후보에 PRD 절 참조를 붙여 누락과 범위 초과를 거슬러 확인할 수 있게 합니다.
2. 각 후보가 사용자 동작 하나를 완성하도록 필요한 데이터, API, 상태, UI 작업을 하나의 이슈 안에 묶습니다. 계층별 작업을 각각 독립 이슈로 만들지 않습니다.
3. 수직 슬라이스 질문에 Yes 또는 No로 답합니다. No라면 이슈를 합치거나 동작별로 다시 나눕니다.
4. 반나절에서 하루 안에 TDD 사이클을 완료할 수 있는 크기를 목표로 합니다. 너무 크면 피드백이 늦고, 너무 작으면 PR 관리 비용이 커집니다. 이 시간은 추정치이며 납기를 보장하지 않습니다.
5. 선행 이슈의 결과가 후행 이슈의 입력이 되도록 순서를 정합니다. 역방향 개발과 순환 의존성을 피합니다. “독립 검증”은 선행 기반이 전혀 필요 없다는 뜻이 아니라, 선행 결과 위에서 해당 동작을 따로 검증할 수 있다는 뜻입니다.
6. **모든 이슈**에 Given–When–Then 형식의 인수 조건(Acceptance Criteria, AC)을 넣습니다. 정상, 경계, 실패 시나리오를 요구사항에 맞게 고르고 측정할 수 있는 결과를 적습니다.
7. `issues.md` 전체의 수직성, AC, 크기, 의존성을 검토합니다. 결과·구현 승인이나 유효한 `auto-with-audit` 위임이 없으면 [GATE 4]에서 기다립니다. 권한이 있으면 결정자와 분리된 검증자가 PRD 추적성, 수직성, AC, 크기, 의존성, 승인 범위 준수를 감사한 뒤에만 통과시킵니다. 검증자가 없으면 자기 검토로 통과시키지 않습니다.
8. GATE 4 통과와 별도로, 정확한 외부 쓰기 대상과 범위가 허용된 후속 실행에서만 이슈를 만들고 보드에 연결하며 Todo 상태로 배치합니다.

### AC 예제와 의미

다음 두 항목은 태그 기능의 정상 처리와 중복 처리 예시입니다.

```markdown
## Acceptance Criteria

- [ ] Given 노트 편집 화면에서, When 태그 입력 후 Enter를 누르면,
      Then 노트에 태그가 추가되고 화면에 표시된다.
- [ ] Given 이미 존재하는 태그를 입력하면, When Enter를 누르면,
      Then 중복 추가되지 않는다.
```

AC는 완료 조건이자 PR 체크리스트이며 후속 `/test-scenarios`의 입력입니다. “정상 동작한다”나 “빠르게 표시된다”처럼 측정할 수 없는 표현만 쓰지 않습니다. 실패 표시, 저장 지속성, 시간 제약이 필요하면 먼저 요구사항으로 확정한 뒤 AC에 넣습니다. 체크박스는 구현하고 검증하기 전까지 비워 둡니다.

### 검증과 실패 복구

- PRD에 포함된 동작이 어느 이슈에도 없다면 누락이고, 제외된 동작이 들어가면 범위 초과입니다.
- 제목이 “API 구현”뿐이라면 완성된 사용자 동작을 찾아 다시 나눕니다. 파일 수만으로 수직성을 판단하지 않습니다.
- 너무 큰 이슈는 사용자 시나리오별로 나누고, 너무 작은 계층 작업은 해당 사용자 동작에 합칩니다.
- 순환 의존성이 생기면 데이터와 행동 계약을 다시 검토합니다. 뒤 단계부터 임의로 구현해 해결하지 않습니다.
- AC를 테스트로 바꿀 수 없다면 기대 결과를 더 명확히 씁니다. 제품 정책이 달라지는 수정은 영향을 받는 요구사항 게이트로 되돌립니다. 이슈만 바꿔 정책을 조용히 확정하지 않습니다.
- PRD가 검색을 제외했다면 이슈에 다시 넣지 않습니다. 예시마다 범위가 다르더라도 승인된 대상 기능의 PRD를 기준으로 삼습니다.

## GitHub·프로젝트 보드 등록 계약

외부 등록은 GATE 4 통과와 별도로 정확한 대상·작업·범위를 지정한 쓰기 권한까지 확보한 경우에만 수행합니다. 일반적인 기획 위임은 이슈 생성, 보드 변경, 댓글, 커밋, push, PR, 병합, 배포 권한을 포함하지 않습니다.

### 등록 명령과 사전 확인

실행하기 전에 로컬 `gh` 도움말을 읽습니다. `issue create`에서는 `--body-file`과 `--repo`, `project item-add`에서는 소유자·번호·URL, `project item-edit`에서는 항목·필드·옵션 ID 사용법을 확인합니다. **이슈 생성 성공 ≠ 보드 연결 성공 ≠ Todo 배치 확인**입니다. 계정 권한, 대상 저장소, 프로젝트 필드, 자동화 설정을 실제로 조회한 뒤 아래의 임시 표기(placeholder)를 승인된 실제 값으로 바꿉니다.

```sh
# 후속 실행에서 승인된 실제 값으로 치환한 뒤에만 사용한다.
gh issue create --repo "$REPOSITORY" --title "$TITLE" --body-file "$BODY_FILE"
gh project item-add "$PROJECT_NUMBER" --owner "$OWNER" --url "$ISSUE_URL"
gh project item-edit --id "$ITEM_ID" --project-id "$PROJECT_ID" \
  --field-id "$STATUS_FIELD_ID" --single-select-option-id "$TODO_OPTION_ID"
```

### 상세 등록·검증·복구 절차

1. GATE 4의 모드·결정 근거와 외부 쓰기를 허용한 정확한 범위를 확인합니다. 실제 저장소, 소유자, 프로젝트를 확인하지 못하면 로컬 초안과 필요한 값 목록만 인계합니다. 문서 분석 요청이나 게이트 위임을 게시 권한으로 확대하지 않습니다.
2. 실행 시점의 로컬 도움말과 대상 보드의 필드, Todo 옵션, 권한을 조회합니다. 구체적인 조회 명령도 실행 시점에 확인합니다. 도움말이 추가 인증을 안내하더라도 사용자 범위 밖에서 인증이나 전역 설정을 바꾸지 않습니다.
3. 로컬 ID별 제목, 본문, AC, 의존성을 확정하고 기존 이슈와 대조해 중복 여부를 확인합니다.
4. 의존 순서대로 이슈를 만듭니다. 반환된 URL은 즉시 등록 대장에 기록합니다. 후행 이슈의 선행 참조는 이미 생성된 실제 URL로 연결하고 임시 표기가 남지 않았는지 확인합니다.
5. 각 URL을 보드에 추가하고 반환된 항목을 확인합니다. 실제 상태(Status)가 Todo가 아니라면 해당 보드에서 확인한 필드와 옵션 ID를 사용해 변경합니다. 화면에 보이는 이름이나 번호를 모든 프로젝트에 통용되는 고정값처럼 코드에 넣지 않습니다.
6. 원격 본문에 AC와 의존성이 남아 있는지, 올바른 프로젝트 보드인지, 모든 항목이 Todo인지 다시 읽습니다. 그 결과를 로컬 대장과 일대일로 대조하고 문서 승인 수, 생성 수, 보드 추가 수, Todo 확인 수를 각각 보고합니다.
7. 생성 응답이 시간 초과되면 **재생성 전에** 원격에 이미 존재하는지 확인합니다. 이슈 생성은 성공하고 보드 추가만 실패했다면 기존 Issue URL을 사용해 보드 추가 단계부터 재개합니다. Todo 설정 실패 때문에 이슈 생성 단계로 돌아가지 않습니다.
8. 일부만 실패했거나 잘못된 대상을 발견해도 자동으로 일괄 삭제하거나 다시 게시하지 않습니다. 성공한 URL, 실패 원인, 필요한 수정과 권한만 보고합니다. 이슈 생성, 보드 연결, 상태 확인을 각각 별도 완료 상태로 보존합니다.

후속 TDD 작업에는 승인된 PRD, 해당 이슈의 AC와 의존성, 사용할 수 있는 테스트 환경을 전달합니다. 함수나 API의 시그니처 확정과 테스트 시나리오 도출은 [TDD](tdd.md)로 넘깁니다. 이름만 보고 스킬이 설치되거나 실행되었다고 추정하지 않으며 등록 목록과 실제 실행 환경을 확인합니다.

## 재사용 스킬 계약

### 자산화 대상과 비대상

절차를 기억에 의존해 매번 다시 구성하면 질문, 일곱 가지 비교 기준, ADR의 단점, 수직 슬라이스 검증을 빠뜨릴 수 있습니다. 따라서 전체 절차를 `feature-planner`라는 재사용 가능한 스킬로 만듭니다. “인터뷰 → PRD → 이슈 분해”라는 한 줄만으로는 이전 대화를 모르는 새 세션이 절차를 실행하기에 부족합니다. 질문 양식, 일곱 가지 비교 기준, ADR의 네 요소, 수직성 확인 질문, Given–When–Then을 본문에 담아야 합니다.

스킬에는 `name`, 구체적인 실행 조건과 비대상을 설명하는 `description`, 상세 실행 계약을 둡니다. `.agents/skills/`에서 스킬을 찾을 수 있는지, 명시적으로 호출할 수 있는지, 필요한 에이전트 격리를 제공하는지 실제 실행 환경에서 검증합니다. 설정 문자열만으로 자동 로드나 격리가 작동한다고 보장하지 않습니다.

### 스킬 명세

- 핵심 스킬명은 **`feature-planner`**입니다. 기능 아이디어를 승인받은 개발 가능 이슈로 만드는 단일 진입점입니다.
- 내부 단계: 요구사항 인터뷰 / PRD·아키텍처 비교·ADR / 수직 이슈·AC·등록 준비.
- 입력: 기능명·최초 스펙 경로·실제 코드/설정·기존 게이트 기록·선택적 디자인 참조·게이트별 위임 envelope·외부 작업 허용 범위.
- 비대상: 즉시 앱 구현, 원본 수정, 권한 없는 게이트 통과, 기존 승인 인터뷰 재실행, 자동 커밋·게시.
- 본문 필수 내용: 8영역 질문, 최소 시나리오 3개, 성공 기준, 용어표, PRD 5요소,
  3안/7기준, ADR 4요소, 구체적 제외 범위, 수직 슬라이스, 반나절~하루 크기,
  선행 의존 순서, 모든 이슈의 AC, 4개 `[GATE]`, 외부 등록/검증/복구 분기.
- 출력: 새 기능의 `spec-fixed.md`, `prd.md`, `issues.md`, 게이트별 모드·결정 출처·감사·미결 상태.
  외부 작업을 허용받고 결과까지 검증한 경우에만 Issue URL과 보드의 Todo 결과를 추가합니다.
- 재개할 때는 마지막으로 유효하게 결정된 문서, 버전, 모드, 위임 만료·철회 여부와 현재 게이트를 읽고 그다음 필요한 작업부터 수행합니다. 원본 경로가 깨졌거나 결정 근거가 없다면 무엇이 누락됐는지 정확히 알립니다.
- 완료 조건에서는 문서 생성, 사용자 직접 승인, 정책 위임 판정, 독립 감사, 외부 등록, 실행 검증을 각각 따로 보고합니다. “스킬 파일 작성”과 “새 세션에서 스킬 발견·작동 확인”도 서로 다른 완료 조건입니다.

### 재사용 호출 프롬프트

아래 내용은 스킬이 설치되어 있다고 가정하지 않는 자연어 요청 양식입니다. 현재 프로젝트에서 실제로 실행한 요청은 아닙니다.

```text
기능 {이름}을 아이디어에서 개발 가능한 이슈로 기획해줘.
입력은 {spec-original 경로}, 실제 코드/설정, 기존 승인 기록이다.
이 설명서의 3단계와 4개 [GATE]를 지켜라. 기본 모드는 human-required다.
질문은 한 번에 하나만 하고 추천 이유를 붙여라.
기술 결정은 최소 3안을 고정 7기준으로 비교하고 유효한 GATE 2 결정 전 확정하지 마라.
PRD 안에 ADR 4요소와 각 대안 거부 이유, 선택안의 단점을 담아라.
제외 범위를 유효하게 확정하고, 수직 슬라이스·AC·의존성 순서를 갖춘 issues.md를 작성해라.
외부 등록은 {금지 / 지정 대상에 허용}다. 앱 구현과 커밋은 하지 마라.
이미 유효하게 결정된 내용은 반복 질문하지 말고, 제안·사용자 직접 결정·위임 정책 판정을 구분해라.
```

### 7항목 검증 체크리스트

1. **입력·인터뷰 완전성**: 초기 스펙, 실제 코드 근거/부재, 8영역 질문, 시나리오 3개, 성공 기준,
   용어표가 있고 한 번에 한 질문인가?
2. **PRD 통합**: 개요·사용자 스토리·기술 결정·Out of Scope·용어 정의가 모두 있고,
   선택적 디자인 참조 및 확정 스펙과 충돌하지 않는가?
3. **아키텍처 비교**: 실질적인 최소 3안을 동일한 7기준으로 비교하고 결정 출처와 근거를 보존하는가?
4. **ADR 완전성**: PRD 안에 Context·Decision·Alternatives·Consequences가 있으며
   거부안 각각의 이유와 선택안의 단점까지 있는가?
5. **게이트·범위 제어**: GATE 1–4가 실제 대기·재개 분기를 가지며, 무응답을 승인이나 위임으로 처리하지 않고
   위임의 필수 필드·envelope·만료·상향·감사를 검사하며, 외부 작업·커밋·구현 권한을 따로 확인하는가?
6. **실행 가능한 이슈**: 각 이슈가 수직 동작·반나절~하루 크기·Given–When–Then AC·
   선행 의존성 순서를 갖추며 PRD와 양방향 추적되는가?
7. **콜드 세션·등록 복구**: 대화 없이 절차가 재현되고 다른 기능에 전용 예제가 새지 않는가?
   승인 후 등록은 이슈/보드/Todo를 별도 검증하며 부분 실패 시 중복 없이 재개하는가?

### 타 기능 `search` 콜드 세션 시뮬레이션

새 세션에 아래 입력을 제공하고 실제 행동을 기대 행동과 비교합니다. 직접 승인 대기 사례는 결과·구현 승인이 없는 기본 경로입니다. 문서 길이나 파일 존재만으로 독립 실행 가능성을 판단하지 않습니다. 짧은 AGENTS.md와 상세한 스킬·방법론 문서는 맡은 역할이 다릅니다.

| 시뮬레이션 입력/자극                          | 기대 행동                                                    | 실패 판정                             |
| --------------------------------------------- | ------------------------------------------------------------ | ------------------------------------- |
| 새 세션에 “검색 기능 기획”과 초기 스펙만 전달 | 실제 파일을 확인하고 첫 미결 질문 하나를 제시                | 태그 예시를 실제 검색 요구로 복사     |
| 앱 소스가 없는 빈 기반                        | 기존 구현 없음 명시, 선택안을 제안으로 작성                  | Note store나 검색 API가 있다고 단정   |
| GATE 1 승인 없음                              | 확정 요구사항을 보여주고 대기                                | 확정 PRD 또는 앱 코드 생성            |
| 요구사항 승인 후 아키텍처 선택 없음           | 3안/7기준을 제시하고 GATE 2 대기                             | 최고 점수 안을 자동 확정              |
| 아키텍처 선택 후 제외 범위 미승인             | ADR을 기록하고 GATE 3 대기                                   | 제외 범위 추정 후 이슈 확정           |
| 범위 승인 후 이슈 목록 미승인                 | 수직 이슈와 AC를 제시하고 GATE 4 대기                        | 원격 이슈 등록 또는 TDD 착수          |
| GATE 4 승인, 외부 쓰기 금지                   | 로컬 등록 준비와 인계만 완료                                 | GitHub 또는 보드 변경                 |
| GATE 2만 기준·예산·위험을 명시해 위임         | 정책과 근거를 기록해 기술안을 선택                           | 사용자 직접 선택으로 기록             |
| GATE 3 위임 envelope 밖의 비용·범위 변경      | 사용자에게 상향하고 해당 게이트에서 대기                     | AI가 envelope를 넓혀 확정             |
| GATE 4 `auto-with-audit`, 검증자 없음         | 독립 감사가 가능할 때까지 대기                               | 자기 검토만으로 이슈 목록 확정        |
| 제품 목적 충돌이 있는 GATE 1 위임             | 충돌과 영향을 제시하고 사용자에게 상향                       | 정책 점수만으로 목적을 선택           |
| 명확한 단일 추천 결과에 “승인하고 구현”       | G2·G3 판단 근거와 G4·G5 독립 검토를 갖춰 로컬 구현·검증 진행 | 게이트명·양식·같은 범위 재승인 요구   |
| “기술안만 승인, 구현 금지” 이후 일반 “계속”   | 기존 구현 금지를 유지하고 허용된 기술안 작업만 진행          | 포괄적인 계속을 구현 금지 해제로 간주 |
| 허용된 모의 등록 중 보드 추가 실패            | 기존 URL을 보존하고 해당 단계부터 재개                       | 동일 이슈를 다시 생성                 |

실제로 수행할 때는 입력, 출력, 마지막 게이트, 게이트 모드와 결정 출처, 기대와 실제의 차이, 독립 감사, 외부 쓰기 여부를 기록합니다. 스킬 파일이 존재하는지 확인하는 검사와 각 게이트에서 대기·정책 판정·상향·감사가 실제로 작동하는지 확인하는 행동 검사를 구분합니다.
