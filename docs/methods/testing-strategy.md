# 테스트 전략과 결과 읽기

이 문서는 작은 기능을 끝까지 검증하는 방법과 테스트 결과를 해석하는 기준을 설명합니다. 하네스는 지침, 검증, 피드백 반복 과정, 사람이 판단할 지점을 연결합니다. 환경 준비 → 요구사항·설계 → 이슈별 테스트 주도 개발(TDD) → 전체 사용자 흐름 테스트(E2E)·변경 제안(PR)·지속적 통합(CI)·병합 순서로 진행합니다. 반복 자동화는 승인이나 실패 판정을 없애지 않으며, 검증 절차를 빠짐없이 재사용하게 합니다.

Git, npm, 터미널의 기본 사용법을 안다고 가정합니다. 전체 흐름은 [생명주기](../harness/lifecycle.md), 이슈 실행은 [TDD](tdd.md), 통합과 전달은 [전달·자동화](delivery-automation.md)를 따릅니다.

## 테스트의 역할

테스트는 주어진 사전 조건에서 어떤 행동을 했을 때 기대한 결과가 나오는지 자동으로 비교하는 코드입니다. 자판기, 덧셈, 장바구니는 이 개념을 설명하는 예일 뿐 제품 요구사항은 아닙니다.

### 자연어를 테스트로 바꾸는 방법

1. Given(사전 조건)에 초기 데이터와 환경을 적습니다.
2. When(행동)에 사용자 행동이나 호출 하나를 적습니다.
3. Then(기대 결과)에 관찰 가능한 결과를 적습니다.
4. 같은 구조를 Arrange(준비)·Act(실행)·Assert(검증)로 코드화합니다. 용어를 외우기보다 준비, 행동, 검증을 분리하는 데 집중합니다.
5. 실패 로그에서 예상값, 실제값, 실패 지점을 읽고 환경 오류인지 계약 위반인지 판단합니다.

React에서는 버튼을 클릭한 뒤 표시되는 횟수나, 비동기 응답 전의 로딩 문구와 응답 후의 사용자 이름을 검증할 수 있습니다. 내부 상태(state)보다 사용자가 관찰할 수 있는 결과를 검사합니다. 즉시 존재하는 요소와 나중에 나타나는 요소를 구분하고 비동기 작업이 끝날 때까지 기다립니다. 테스트 라이브러리가 제공하는 조건 기반 대기를 사용하며 임의의 sleep으로 실행 시점을 맞추지 않습니다.

### Matcher·대역·FIRST

- 원시 값이나 참조의 동일성을 비교하는 것과 객체 내용을 비교하는 것은 다릅니다. 오류, 비동기 거부, 문서 객체 모델(DOM) 요소의 존재, 호출 횟수 등 검증 대상에 맞는 비교 함수(assertion 또는 matcher)를 선택합니다.
- 스텁(Stub)은 정해진 응답을 제공하고, 목(Mock)은 필요한 상호작용이 일어났는지 검증합니다. 실제 결제, 메일, 외부 네트워크는 테스트에서 안전한 대역으로 바꿉니다.
- 날짜, 난수, 외부 상태를 통제해 결과를 재현할 수 있게 합니다. 대역을 사용한 테스트만 통과하고 실제 경계 연동은 검증하지 못했다면 별도의 통합 테스트나 E2E 테스트로 보완합니다.
- FIRST 원칙에 따라 테스트는 빠르고(Fast), 독립적이며(Independent), 반복 가능하고(Repeatable), 스스로 결과를 판정하며(Self-validating), 적시에 작성해야(Timely) 합니다. 실행 시간 제한은 테스트 계층과 실행 환경에 맞게 정합니다.
- 테스트는 회귀를 막고 리팩터링을 안전하게 하며 실행 가능한 명세 역할을 합니다. 테스트가 통과했다는 사실만으로 모든 요구사항을 충족했다고 판단하지 않습니다.

### 초보자 확인 과제

실제로 승인된 인수 조건(AC), 즉 기능이 요구대로 완성됐는지 판단하는 조건 하나를 골라 Given·When·Then(GWT)을 작성하고 어떤 결과를 검증할지 설명합니다. 네트워크나 시간 가운데 통제할 의존성도 하나 찾습니다. 테스트를 실행해 실패 이유를 설명한 뒤 최소 구현으로 통과시킵니다. 기존 테스트 실행기와 테스트 위치를 사용하며, 연습을 위해 제품 요구사항이나 앱을 임의로 추가하지 않습니다.
