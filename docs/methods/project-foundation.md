# 프로젝트 기반과 품질 자동화

## 입력과 조사

프로젝트 기반을 만들기 전에 대상의 현재 구조와 이미 쓰는 도구부터 확인합니다. 대상 작업 경로, 사용자 요청, 적용 범위의 `AGENTS.md`, 실제 소스·설정·잠금 파일을 읽습니다. 앱, 테스트 실행기, 지속적 통합(CI) 환경이 있는지는 파일로 확인하고, 없다면 없다고 기록합니다. 다른 프로젝트의 프레임워크, 내보내기(export), 이벤트 처리 방식은 이 프로젝트에도 같을 것이라고 추정해 강제하지 않습니다.

1. 사람용 README에는 목적, 실행·검사 명령, 구조, 현재 구현과 미구현을 기록합니다.
2. AI용 AGENTS.md에는 범위·변경 제한·핵심 명령·승인·검증 규칙과 상세 문서 경로를 짧게 남깁니다.
3. 반복 절차는 `.agents/skills/<name>/SKILL.md`에 입력, 순서, 산출물, 실패 복구, 승인 관문을 담습니다.
4. 기존 설정을 병합하고 중복 기준을 만들지 않습니다. 전역 설정과 다른 작업자의 파일은 건드리지 않습니다.
5. 구조도는 실제 파일·호출·검사 관계로 작성합니다. Mermaid 텍스트는 버전 관리하고 실제 SVG·한글 레이블·연결선은 브라우저에서 확인합니다.
6. 지침 초안 생성, 런타임 발견, 실제 호출 성공을 각각 검증합니다. 파일 존재만으로 활성화를 보고하지 않습니다.

스킬이 명시적인 요청으로 실행되는지 자동으로 시작되는지는 실제 설정에서 확인합니다. 구조도 갱신 스킬이 있어도 파일 감시기나 자동 동기화 기능까지 있다는 뜻은 아닙니다.

## 커밋 전 품질 체인

```text
사용자가 요청한 git commit
  → pre-commit
    → lint-staged: 스테이징된 대상만 검사
      → ESLint --fix → Prettier --write
  → commit-msg
    → commitlint: 메시지 형식 검사
  → 모두 성공하면 커밋 진행
```

- **Husky**: Git 훅을 프로젝트 파일로 관리하고 설치 시 연결합니다.
- **lint-staged**: 바뀐 전체 작업 폴더가 아니라 스테이징된 대상만 검사합니다.
- **ESLint / Prettier**: 코드 오류와 서식을 나눠 검사하고 가능한 것은 자동 수정합니다.
- **commitlint**: Conventional Commits 메시지 형식을 검사합니다.

이 Git 훅은 에이전트가 만든 커밋과 사람이 터미널에서 직접 만든 커밋에 공통으로 적용됩니다. Git 훅과 에이전트 실행 환경의 훅을 혼동해서는 안 됩니다. 지침을 따르려는 AI의 행동과 Git이 실제로 실행하는 검사는 서로 다른 장치입니다.

## 설치와 연결

- 먼저 `package.json`, 잠금 파일, 기존 ESLint·Prettier·Git 훅 설정을 확인합니다. 기존 도구와 충돌하는 중복 설치를 피합니다.
- npm 프로젝트의 재현 설치는 `npm ci`를 사용합니다. `prepare`가 Husky를 연결하는지 실제 실행 결과로 확인합니다.
- `.husky/pre-commit`에는 lint-staged, `.husky/commit-msg`에는 메시지 파일을 받는 commitlint를 연결합니다.
- lint-staged 대상은 실제 파일 종류에 맞춥니다. JS/MJS/TS/TSX, HTML 내부 스크립트, 문서, 설정을 모두 같은 방식으로 검사할 수 있다고 가정하지 않습니다.
- 자동 수정이 불가능한 오류는 비정상 종료로 커밋을 차단합니다. 훅 우회나 오류 무시는 해결책이 아닙니다.
- `feat`, `fix`, `test`, `refactor`, `chore`, `docs` 등 허용 type과 길이는 실제 commitlint 설정이 기준입니다. `docs(requirements): 기능 요구사항 정리`처럼 작성하되 도구가 설명의 정확성이나 한국어 여부까지 보장하지는 않습니다.

## 실패를 포함한 검증

훅은 격리된 임시 저장소에서 검증하여 실제 프로젝트에 불량 코드를 남기거나 커밋하지 않도록 합니다. 검증용 환경에도 사용자의 변경을 복사하거나 스테이징하지 않습니다.

| 검사                            | 기대 결과                              |
| ------------------------------- | -------------------------------------- |
| 정상 스테이징 파일의 pre-commit | 종료 0, 코드·서식 작업과 스테이징 반영 |
| 미사용 변수·미정의 식별자 JS    | ESLint 오류로 비정상 종료              |
| HTML 내부 모듈의 미정의 식별자  | 구성된 HTML 검사 범위에서 거부         |
| 정상 Conventional 메시지        | commit-msg 종료 0                      |
| `bad message`                   | type·subject 오류로 비정상 종료        |

격리 저장소의 훅 연결을 준비한 뒤 `git hook run pre-commit`, `git hook run commit-msg -- <메시지파일>`로 검사합니다. 명령·작업 경로·종료 코드·로그·자동 변경 파일을 기록합니다. 전체 작업 트리 검사와 스테이징 대상 검사는 다르므로 하나로 다른 하나를 대체하지 않습니다.

지침 입력의 포함 여부, 스킬 발견과 형식, 실제 스킬 호출, 구조도 렌더링, 훅 동작은 각각 별도 결과로 보고합니다. 브라우저나 실행 환경이 실패하면 실제 오류와 대신 검증한 범위를 남깁니다. 패키지 감사가 통과해도 실행 시점의 의존성 검사 결과일 뿐, 제품 전체의 보안을 보장하지는 않습니다.

## 완료와 인계

관련 검사를 먼저 수행하고 실패 원인을 수정한 뒤, 가능한 통합 검사를 마지막에 수행합니다. 현재 검사 범위는 실제 scripts와 [검증 기록](../harness/verification.md)에서 확인합니다. 로컬 통합 검사, 원격 CI, 앱 기능 검증은 서로 구분하여 보고합니다. 새 컴퓨터로 이전할 때는 [재사용 안내](../harness/reuse.md)를 따릅니다.

```text
기반 점검 결과
대상 경로 / 확인한 소스·설정:
유지한 기존 도구 / 병합한 변경:
README / AGENTS / 스킬 / 구조도 경로:
설치·발견·호출·훅·화면: 각각 실행/미실행/실패
검사 명령 / 종료 코드 / 로그:
남은 제약 / 다음 단계 입력:
```
