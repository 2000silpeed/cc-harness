# AX 대회용 운영안: 인터뷰에서 작동하는 에이전트까지

가상 인물 인터뷰로 단서를 얻고 AI 에이전트를 제작·심사받는 과제에 쓰는 **선택적 운영안**입니다. 대회용 시간 배분은 하네스의 `compact` 위험 프로필이나 필수 게이트를 바꾸지 않습니다. 실제 과제·도구·제출 조건을 현장에서 먼저 확인하고, 과업의 핵심 동작을 줄이지 않는 범위에서 순서를 조정합니다.

## 확인된 사실과 현장 확인

2026-10-01에 확인한 [대회 공식 사이트](https://aitop100.org/) 소개에 따르면 예선은 **2026-10-31 10:00–15:00, 총 5시간**이며 AI 도구 제한은 없습니다. 개인전은 본인이 직접 수행하고, 카카오톡 활용 및 계정 연동이 필수입니다. 소개는 문제 정의, 단서 조합, 실제 상황에서 에이전트가 적절히 작동하는지를 심사 관점으로 제시합니다. 이 문서의 작업 순서와 시간 배분은 **AI 제안**이며 공식 규칙이나 수상 기준이 아닙니다.

구체적인 플랫폼, 제출 형식·마감 처리, API, 인터뷰 횟수, 평가 가중치, 재제출 허용 여부는 여기서 확인되지 않았습니다. 시작 시 최신 공식 공지와 현장 지시를 다시 확인하고 출처·시각을 기록합니다. 확인 전에는 재제출이나 특정 연동 방식을 전제하지 않습니다. 카카오톡 필수 조건의 실제 수행 방법도 현장 안내에 맞춥니다. 계정 연결·외부 쓰기·유료 호출·배포는 별도 권한과 환경 조건을 확인한 뒤에만 수행합니다.

## 시작 프롬프트

터미널에서 저장소 루트(`scripts/ax-session.mjs`가 보이는 디렉터리)로 이동하고 `node --version`과 `npm --version`을 확인합니다. Node.js와 npm이 없다면 먼저 설치합니다. 저장소의 검사를 실행할 계획이면 루트에서 `npm ci`로 의존성을 준비합니다. 이 운영안의 프롬프트를 사용하는 데 설치가 필요한 것은 아닙니다.

현장 공식 과제와 최신 규칙·제출 안내를 원문, 출처, 확인 시각과 함께 별도 파일에 보존합니다. 아래 블록을 참가자가 사용할 AI 채팅의 **첫 메시지**에 복사하고 대괄호를 그 자료로 채웁니다. 실제 인물 발언은 답변을 받은 뒤 원문과 ID를 다음 메시지에 순서대로 전달합니다. 개인전의 제작·제출은 참가자 본인이 직접 수행합니다.

```text
목표: [공식 과제 원문]을 가상 인물 인터뷰의 확인 가능한 발언에 근거해 해결하는 AI 에이전트를 만든다.
현재 공식 규칙/제출 안내: [출처, 확인 시각, 원문 또는 링크]. 모르는 항목은 미확인으로 표시한다.
먼저 과제의 성공 조건과 확인할 인물을 정리하라. 질문마다 knownRules(이미 확인한 규칙·근거 ID)와 newInfo(이 질문으로 새로 알아야 할 결정 조건)를 적어라. newInfo가 없으면 질문을 계획하지 말라. 같은 인물·주제의 재질문이면 얻을 새 정보와 이유를 적어라. 질문은 한 번에 하나씩, 실제 답변의 인물·발언 ID·원문을 보존하라.
발언에서 도출한 규칙은 근거 ID, 결정 권한, 확실성, 충돌 여부를 함께 적고, 모순을 임의로 합치지 말라. 결정권자나 추가 근거가 필요하면 보류하라.
규칙의 조건·행동·근거를 한 표로 확정하고 정상·정보부족·실패의 실제 입력→출력 사례를 만들라. 같은 뜻을 뒷받침하는 발언 ID는 허용하되 모든 인용이 그 출력에 관련되는지 확인하라. 공개 테스트 계약을 검토·동결한 뒤 동일 테스트 파일 해시로 Red 실패와 Green 통과를 기록하라. 첫 실제 동작을 실행하고 결과를 기록하며 실패를 고친 뒤 해당 사례를 다시 실행하라.
단일 에이전트로 시작하는 것은 기본안일 뿐이다. 과제에 필요한 역할·행동을 확인한 뒤 구조를 선택하고, 핵심 동작을 속도 때문에 빼지 말라.
기존 하네스의 G1–G5 산출물, 승인·STOP, 작업자 역할과 독립 검증을 유지하라. 한 장 작업표는 진행 색인으로만 쓰라.
독립 검증에 쓸 소스·평가기준·입력을 동결하고 실제 실행 명령·종료 코드·원 결과를 먼저 보관하라. 각 출력의 해시와 설명의 의미·근거 관련성을 검토하고, 기존 출력을 마감한 뒤 판정을 공유하라. 판정 저장 전에는 평가 중인 소스를 수정하지 말라.
외부 연동, 제출, 비용 발생 행동은 권한과 현장 규칙을 확인하기 전에는 실행하지 말라.
```

## 증거에서 행동까지

원문은 한 곳에 보존하고 이후 단계에는 ID, 승인 버전, 바뀐 결정과 미결만 전달합니다. 같은 인터뷰를 단계마다 다시 하지 않고, Red–Green처럼 이어지는 구현은 한 작업자가 맡을 수 있습니다. 이는 [필수 오케스트레이션 정책](delivery-automation.md#필수-오케스트레이션-정책)의 작업자·독립 검증·인계 계약을 유지하면서 중복 읽기와 교체 비용을 줄이는 방법입니다. 작업표는 `spec-original`, 인터뷰, `spec-fixed`, PRD/ADR, 이슈·AC, 시나리오, 실행·검증 증거를 대체하지 않습니다.

현장에서는 다음 순서로 작업합니다. 각 단계의 원문·명령·시각·종료 코드·해시를 작업 폴더에 남기고, 미확인 항목을 통과로 표시하지 않습니다.

1. 공식 과제·규칙·제출 방법을 확인해 원문과 확인 시각을 보관합니다. 발표 자료가 바뀌면 바뀐 조건과 영향을 받는 테스트부터 확인합니다.
2. 질문마다 `knownRules`와 `newInfo`를 적습니다. 새 결정 정보가 없다면 건너뜁니다. 필요할 때 아래 `question`으로 **계획**을 기록한 다음 현장 인터뷰 수단에서 사람이 실제로 질문합니다. 받은 답변은 인물·발언 ID·원문과 함께 별도 기록에 보존합니다.
3. 발언마다 결정 조건, 권한, 행동, 예외와 근거 ID를 표에 연결합니다. 같은 뜻의 다른 발언도 근거가 될 수 있으므로 특정 ID 문자열만 정답으로 강제하지 않습니다. 반대로 관련 없는 발언을 덧붙인 출력은 설명이 풍부해 보여도 통과시키지 않습니다.
4. 정상·정보부족·충돌·실패의 공개 입력과 기대 행동을 실제 발언으로 검토합니다. 계약의 오류를 고친 **후** 테스트 파일 해시를 동결하고 Red 실패 로그를 남깁니다. 같은 해시의 테스트로 Green을 실행합니다. 테스트를 바꿨다면 새 계약으로 검토·동결하고 Red부터 다시 시작합니다.
5. 구현자와 분리된 검증자가 소스·평가기준·평가 입력의 버전과 실제 실행 명령을 확인합니다. 원 결과를 먼저 보관한 뒤 각 출력의 해시, 근거와 설명의 의미를 독립 검토합니다. 합격·실패 판정을 보관한 뒤 소스를 수정합니다. 수정본은 새 버전으로 다시 검증합니다.
6. 공식 제출 형식과 시각을 재확인하고 참가자가 현장 절차로 제출합니다. 접수 확인이나 미제출 사유를 기록합니다.

5번의 **기존 출력 마감(finalize)**은 아래 로컬 CLI 기능이 아닙니다. 모의 평가기에서 이미 실행한 결과를 다시 실행하지 않고 마감한 절차를 설명한 것입니다. 현장 평가기가 그 기능을 제공하지 않으면 원 결과와 의미 검토를 별도로 보관하고, 재실행 여부를 실제 수행한 그대로 기록합니다.

| 인물        | 발언 ID | 원문          | 도출 규칙        | 확실성           | 충돌                | 검증 사례 |
| ----------- | ------- | ------------- | ---------------- | ---------------- | ------------------- | --------- |
| [인물/역할] | Q1-A1   | [원문 그대로] | [규칙 또는 가설] | 확정/추정/미확인 | 없음 또는 [상충 ID] | C1        |

| 입력             | 근거 ID | 규칙        | 행동        | 출력               | 보류 조건                  |
| ---------------- | ------- | ----------- | ----------- | ------------------ | -------------------------- |
| [실제 입력 형식] | Q1-A1   | [적용 조건] | [수행할 일] | [관찰 가능한 결과] | [정보 부족·충돌·실패 조건] |

| 요구사항·AC ID | 인터뷰 근거 ID | 에이전트 행동 | 실행 사례 ID | 실제 결과·로그        | 검증 판정        |
| -------------- | -------------- | ------------- | ------------ | --------------------- | ---------------- |
| R1             | Q1-A1          | [행동]        | C1           | [입력→출력/로그 경로] | 통과/실패/미검증 |

발언이 충돌하면 두 원문과 영향을 받는 행동을 함께 남기고, 결정권자 또는 추가 근거를 확인할 때까지 해당 행동을 보류합니다. G1의 목적·가치·중대한 범위·위험이나 필수 동작 정책을 미결로 둔 채 통과시키지 않습니다. G2·G3 판단은 승인 범위와 이유를 남기고, G4·G5와 실제 AC는 구현자와 분리된 검증자가 근거를 확인합니다. STOP과 외부 권한은 [승인과 외부 작업](../harness/lifecycle.md#5-승인과-외부-작업)을 따릅니다.

### 로컬 질문 계획과 판정 보관

아래 명령은 저장소 루트의 터미널에서 실행하며 현장 연결 없이 로컬 파일만 다룹니다. 작업 폴더 `./evidence/ax-run`은 예시이므로 실제 제출 규칙에 맞는 보관 위치를 정합니다. 다른 사용자가 경로를 바꿀 수 없는 신뢰할 수 있는 로컬 폴더를 쓰세요. 이 CLI는 상위 경로의 심볼릭 링크나 권한을 고정하는 보안 격리 도구가 아닙니다. 먼저 `mkdir -p ./evidence/ax-run`으로 원장 부모 폴더를 만듭니다. 이 폴더는 현재 작업의 현장 원문·로그·결과용이며 민감한 발언이나 비밀 값을 Git에 넣지 않습니다. `question`은 인물·주제 중복을 확인하는 **계획** 도구로, 질문을 전송하거나 답변을 받지 않습니다. 기존 인물·주제에 새 정보가 필요하면 이유를 명시해 재질문 계획을 남깁니다.

```sh
mkdir -p ./evidence/ax-run
node scripts/ax-session.mjs question --ledger ./evidence/ax-run/questions.jsonl --role '행사 담당자' --topic '예약 확인' --text '예약 확인 기준은 무엇인가요?'
node scripts/ax-session.mjs question --ledger ./evidence/ax-run/questions.jsonl --role '행사 담당자' --topic '예약 확인' --text '취소 상태는 어떻게 처리하나요?' --follow-up '첫 답변에 취소 정책이 없었음'
```

명령 직후 셸에서 `echo $?`로 마지막 종료 코드를 확인합니다. 최초 계획이나 이유를 적은 재질문은 0으로 저장됩니다. 같은 인물·주제를 이유 없이 다시 계획하면 2이고 원장은 바뀌지 않습니다. 다른 프로세스의 잠금 충돌도 2입니다. 빈 필드·잘못된 인자·손상된 원장·입출력 실패는 1입니다. `questions.jsonl`은 한 줄에 JSON 객체 하나이며 줄 끝 개행과 기존 행의 형식을 검사합니다. 손상되었다면 원본을 복사해 보존하고 오류 행을 확인한 뒤 유효한 백업에서 복구합니다. 무작정 다시 실행하거나 손상 행을 지워 증거를 바꾸지 않습니다. `questions.jsonl.lock`이 남았을 때는 실행 중인 소유 프로세스와 원장 상태를 확인한 뒤 수동 복구를 결정합니다. 도구가 남의 잠금을 해제하지 않습니다. 계획 수는 실제 질문·답변·확보 발언 수가 아닙니다. 중요한 정책이 미결이면 질문 수를 임의로 제한해 G1을 통과시키지 않습니다.

검증자는 **실제 판정 실행에 사용한 소스**를 동결하고, 평가 도구에서 나온 원 결과 JSON을 `./evidence/ax-run/raw-result.json`에 먼저 보관합니다. 소스 예시 경로 `./agent.py`는 실제 실행 파일로 바꿉니다. 아래 Node 명령은 원 결과가 JSON 객체인지 확인하고 소스 SHA-256을 `agent_sha256`으로 추가해 **새** `judge-result.json`을 만듭니다. 이미 그 파일이 있으면 덮어쓰지 않습니다. 이는 결과를 생성하거나 평가를 실행하는 명령이 아닙니다.

```sh
node -e 'const fs=require("node:fs"); const crypto=require("node:crypto"); const [source,input,output]=process.argv.slice(1); const raw=JSON.parse(fs.readFileSync(input,"utf8")); if (!raw || typeof raw!=="object" || Array.isArray(raw)) throw Error("Result must be an object"); const agent_sha256=crypto.createHash("sha256").update(fs.readFileSync(source)).digest("hex"); fs.writeFileSync(output,JSON.stringify({...raw,agent_sha256},null,2)+"\n",{flag:"wx"});' ./agent.py ./evidence/ax-run/raw-result.json ./evidence/ax-run/judge-result.json
node scripts/ax-session.mjs record-result --source ./agent.py --result ./evidence/ax-run/judge-result.json --out ./evidence/ax-run/results
```

결과 JSON의 최소 형식은 `{"agent_sha256":"<실제 소스의 SHA-256>","verdict":"<실제 판정>"}`처럼 해시와 **실제** 판정 내용을 담은 객체입니다. `record-result`가 확인하는 필수 키는 `agent_sha256` 하나이며 다른 필드의 의미나 판정 품질은 검사하지 않습니다. 실행 명령·종료 코드·시각·평가 입력·원 결과와 출력별 해시·의미 검토는 별도로 보관합니다. 이 단계까지 소스를 수정하지 말고, 저장 직후 manifest와 snapshot을 대조합니다.

`record-result`도 성공은 종료 0입니다. 도구는 현재 소스를 두 번 읽어 바이트 일치를 확인하고 결과의 선언 해시와 대조합니다. 성공하면 `<out>/<source-sha256>/<result-sha256>/`에 `source.snapshot`, `result.snapshot`, `manifest.json`을 새로 저장합니다. 선언 해시가 현재 소스와 다르거나 JSON이 잘못되면 종료 1입니다. 같은 bundle이 이미 있으면 종료 2로 덮어쓰지 않습니다. 입력·출력 경로 오류나 쓰기 실패가 나면 일부 파일이 남을 수 있으므로 성공 메시지와 세 파일을 확인하기 전에는 완료 판정으로 취급하지 않습니다. 저장된 해시는 검사 실행, 검사 시점의 소스 정체, 심사 품질을 증명하지 않습니다. 실제 실행 시각·명령·소스 동결은 호출자와 독립 검증자가 별도 확인해야 합니다. 이 CLI는 질문 전송, 검증 실행, 기존 출력 마감, 공식 제출을 수행하지 않습니다.

## 가상 연습 예제: 행사 안내 에이전트

아래 인물과 발언은 **설명용 가상 자료**입니다. 실행하거나 독립 검증한 증거가 아닙니다.
