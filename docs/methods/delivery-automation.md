# 전달 검증과 제한된 TDD 자동화

이 문서는 승인된 구현을 전체 사용자 흐름 테스트(E2E), 변경 제안(PR), 지속적 통합(CI), 리뷰로 검증하고 전달하는 기준을 설명합니다. 반복 실행은 명시적인 권한과 중단(STOP) 조건 안에서만 허용합니다. 현재 등록 목록은 [registry.json](../harness/registry.json), 실제 검증 상태는 [verification.md](../harness/verification.md)에서 확인합니다. 문서나 스킬을 등록했다는 사실은 제품 실행이나 병합 증거를 대신하지 않습니다.

## 필수 오케스트레이션 정책

이 절은 대화형·자동 워크플로와 하네스 자체 유지보수에 모두 적용합니다. 실행 스킬의 개별 절차도 다음 역할 경계를 따라야 합니다.

- **메인**은 현재 상태와 승인 근거를 확인하고, 작업을 나누어 배정하며, 결과와 증거를 대조·통합하고, 사용자에게 진행 상황을 알립니다. 이 역할에 필요한 지침·상태·증거 읽기와 진행 기록은 할 수 있습니다. 실제 탐색, 코드·문서 같은 산출물의 작성·수정, 테스트 작성·실행은 반드시 서브에이전트가 수행합니다. 작은 수정에도 메인이 직접 구현하는 예외를 두지 않습니다.
- **작업자**는 메인이 지정한 유한 범위의 실제 작업을 직접 수행합니다. 이 정책을 다시 위임하라는 지시로 해석해 하위 작업자를 만들지 않습니다. 추가 작업이 필요하면 메인에 돌려보냅니다. 메인은 필요한 최소 수의 작업자만 만들고, 의존 작업과 파일 소유권을 분리하며, 제한 없는 병렬 생성과 재시도를 금지합니다.
- **컨텍스트**는 작업마다 새로 시작합니다. 도구가 지원하면 `fork_turns="none"`을 사용합니다. 다른 실행 환경에서는 전체 대화를 물려받지 않는 동등한 기능을 실제로 확인한 경우에만 사용합니다. 지원 여부를 추정하거나, 작업이 끝났다는 이유만으로 컨텍스트가 해제되었다고 주장하지 않습니다. 컨텍스트 분리는 파일시스템 격리를 뜻하지 않습니다.
- **최소 입력**에는 작업 목적과 AC, 필요한 파일 경로와 기준 버전, 변경을 허용한 범위·권한·승인 근거, 검사 명령, 종료·재시도 조건, 반환할 증거 계약만 담습니다. 전체 대화, 전체 저장소, 긴 로그를 복제하지 않습니다. 작업을 시작할 때의 HEAD와 작업 트리 변경 상태(dirty)를 기록하고, 변경 대상의 사본이나 해시로 커밋하지 않은 버전을 식별해 기존 변경을 보존합니다.
- **최소 반환**에는 완료·실패·미검증 상태, 변경 경로와 검증 대상 버전, 명령·종료 코드·검사 수, 증거와 전체 로그 파일 경로, 남은 문제와 다음 행동만 담습니다. 코드 본문과 긴 로그는 파일에 둡니다. 메인은 필요한 증거를 직접 열어 버전과 실제 결과를 대조하며 `passed=true`라는 값만 믿지 않습니다. 결과를 반환한 뒤 파일이 바뀌면 해당 검증이 여전히 유효한지 다시 판단합니다.
- **독립 검증**은 이 하네스의 필수 조건입니다. 메인은 구현자와 다른 검증 작업자에게 승인된 AC와 실제 변경·검사 증거를 제공하고 검토를 맡깁니다. 같은 에이전트가 역할만 바꾸는 방식으로 대체하지 않습니다. 메인이 증거를 통합하는 일도 독립 검증을 대신하지 않습니다.
- **실행 불가** 상태라면 메인은 사용할 수 없는 도구나 기능, 실제 오류, 수행하지 못한 범위, 재개 조건을 알립니다. 확인된 동등 실행 환경이나 독립 작업자에게 인계할 수 없다면 해당 실행을 보류하며, 메인이 직접 구현하는 방식으로 우회하지 않습니다.

이 위임 의무가 의사결정을 자동 승인하는 것은 아닙니다. 요구사항, 아키텍처, 범위, 이슈, 시나리오의 승인과 외부 작업 권한을 그대로 유지합니다. `tdd-auto-loop`의 유한한 범위와 상한은 별도의 명시적 승인으로만 정합니다. 이 정책은 지침에 따른 의무이며, 실행 환경에서 메인의 편집이나 실행을 기술적으로 차단하는 장치는 아닙니다. 기존에 다른 프로젝트로 옮긴 사본은 자동으로 갱신되지 않으므로 대상 지침과 이 문서를 명시적으로 갱신해야 합니다.

## Adaptive Execution: process와 model의 분리

적응형 실행(Adaptive Execution)은 단일 요청의 토큰이나 프로젝트 총비용 절감을 보장하지 않습니다. 탐색, 컨텍스트 재구성, 구현, 테스트, 검증, 추론, 재시도, 재작업, 상향 판단을 포함한 전체 프로젝트 비용을 나중에 실행 증거로 검증하기 위한 초기 정책입니다. **Process Routing**은 필요한 절차의 깊이를 정하고, **Model Routing**은 그 절차 안에서 각 역할에 요청할 능력을 정합니다. 기존 승인 게이트와 STOP 조건을 항상 먼저 적용합니다.

모델 역량(model capability)은 선택한 모델 자체의 추론·생성 능력입니다. 하네스 역량(harness capability)은 승인, 역할 분리, 기획, 검증, 재시도, 상향 판단, 증거를 조직하는 계약입니다. 하네스가 약한 모델을 강한 모델과 같게 만들거나 낮은 편차와 비용을 증명하지는 않습니다. 의도한 품질과 비용 효과는 실제 실행 관측값이 있어야 평가할 수 있습니다.

| process profile | 선택 조건                                                                | 실행 계약                                                                                                                                  |
| --------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `compact`       | 관련 호출·계약·의존성을 확인해 영향 범위가 국소적이고 충분히 알려진 변경 | 최소 충분 컨텍스트(MSC)와 변경에 집중한 관련 검사를 사용합니다. 작업자, 독립 검증자, 필수 검사, 재시도·STOP 예산을 생략할 권한은 없습니다. |
| `standard`      | 일반 기능 또는 영향 범위가 불명확한 변경                                 | 기존 이슈 TDD와 관련 회귀 검사를 적용합니다. 알지 못하는 영향이 있으면 `compact`로 낮추지 않습니다.                                        |
| `intensive`     | 복잡한 통합, 공통 계약 변경, 알 수 없는 실행 동작                        | 제한된 진단, 독립 검증, 범위를 넓힌 관련 회귀 검사와 명시한 컨텍스트 범위를 적용합니다.                                                    |

파일 수나 변경분(diff)의 크기는 프로필을 고르는 주된 기준이 아닙니다. 보안, 데이터, 권한, 파괴적 작업이나 운영 환경, 사용자 게이트, STOP 계약이 관련되면 변경분이 작아도 `compact`로 보지 않으며 사용자 게이트를 우선합니다. 프로필은 안전 계약의 면제 수단이 아닙니다. 실제 실행 기록이 없다면 프로필 선택만으로 에이전트가 올바르게 행동했음을 증명할 수 없습니다.

기본 역할 요청은 `default_worker=Sol/medium`, `diagnostic=Astra/high`, `verifier=Sol/high`입니다. 환경이 제공하는 모델로 바꿀 수 있지만, 요청한 `requested` 값과 실행 메타데이터에서 관찰한 `observed` 값은 분리합니다. 메타데이터가 없으면 `unknown`으로 기록하며, 모델 요청이 성공했다는 사실만으로 역할의 독립성이나 실제 백엔드 모델을 주장하지 않습니다. 진단 역할(diagnostic)은 읽기 전용으로 원인, 가설, 권고 계획만 반환하고 이후 구현은 새 작업자가 수행합니다.

`tdd-auto-loop`의 Green 총예산은 `min(3, 1 + user_approved_retry)`이고 진단 예산은 이슈마다 1회입니다. 진단 실패도 예산을 소비하며, 새 컨텍스트, 모델 교체, 재개(RESUME)는 횟수를 초기화하지 않습니다. 진전 없음(`no-progress`) 또는 Green 3회 실패 뒤에는 상향 처리하지 않고 STOP합니다. 수동 `tdd-loop` 유지보수에는 이 자동 상한을 묵시적으로 적용하지 않으며, 승인된 유한 범위와 실제 누적 시도를 기록합니다. 같은 실패인지 판단할 때는 분류뿐 아니라 명령, 실패 특징, 도구 버전, 범위를 함께 비교합니다. `LOCAL_IMPLEMENTATION_ERROR`, `ARCHITECTURE_UNCERTAINTY`, `CROSS_MODULE_DEPENDENCY`, `UNKNOWN_RUNTIME_BEHAVIOR`, `REQUIREMENT_AMBIGUITY`, `BROKEN_ENVIRONMENT`, `EXTERNAL_TOOL_FAILURE`, `SECURITY_BLOCK` 가운데 증거에 맞는 값을 기록하고, 요구사항의 모호성과 새 권한은 사용자 승인 단계로 보냅니다.

### Minimum Sufficient Context, JIT, Evidence Reuse

새 작업자에게 주는 최소 충분 컨텍스트(Minimum Sufficient Context, MSC)는 승인 목표, 허용 범위, 리비전과 작업 트리 해시, 관련 파일과 계약 참조, 검사·STOP·남은 예산, 체크포인트, 증거 링크, 반환 형식입니다. 전체 대화, 전체 저장소, 긴 로그는 기본 입력에 포함하지 않습니다.

적시 저장소 이해(JIT repository understanding)는 먼저 구조를 얕게 살핀 뒤 현재 변경 영역과 직접 연결된 의존성, 테스트, 인터페이스, 관련 문서만 읽는 방식입니다. 범위를 넓힐 근거가 있을 때만 더 읽습니다. 증거 재사용(Evidence Reuse)은 메타데이터, 버전·해시, 명령, 체크포인트를 먼저 비교합니다. 관련 코드, 계약·AC, 테스트, 명령, 환경이 모두 같다고 확인된 경우에만 재사용하고, 불확실한 부분만 추가로 탐색하거나 다시 검증합니다. 관련된 변경만 증거를 무효화하며 전체 HEAD가 달라졌다는 이유만으로 모든 증거를 폐기하지 않습니다.

### Execution metadata와 관측 경계

진행 기록과 결과 JSON에는 선택한 프로필과 이유·위험 표시, 컨텍스트 범위, 검증 깊이·범위, 증거 재사용 여부와 확인 항목, 작업자·검증자의 역할과 컨텍스트 ID를 기록합니다. 요청한 모델·추론 강도와 실제 관찰값, 재시도·상향 판단·재작업, 실패 분류·결과·다음 행동, 정책 체크포인트도 함께 기록합니다. 관찰된 사용량은 출처, 단위, 포함 범위를 밝혀야 합니다. `unknown`이나 `unavailable`은 0을 뜻하지 않습니다. 누적 사용량을 중복 합산하거나 일부 사용량을 전체 프로젝트 비용이라고 주장하지 않습니다.

지원되는 Codex CLI에서 `exec --json`이 내보내는 `turn.completed` 사용량과 App Server 스레드의 토큰 사용량 알림은 관찰 가능한 실행 메타데이터 후보입니다. 이 하네스는 별도의 수집기를 추가하지 않습니다. 현재 협업 도구에서 모델이나 사용량 정보를 제공하지 않는다면 `unknown`으로 남깁니다.

실행 도구가 모델 식별자(slug) 선택을 지원한다면 `gpt-5.6-sol`, `gpt-6-astra`처럼 지원되는 값을 명시적으로 요청하고 실행 환경이나 설정이 이를 덮어쓰는지 먼저 확인합니다. 역할 이름은 바꿀 수 있습니다. 모델 지원 여부, 설정 덮어쓰기, 독립 컨텍스트를 확인할 수 없다면 성공으로 추정하지 않고 `unavailable` 또는 `manual-handoff`로 기록합니다. 실제 지원 여부는 [Codex Subagents](https://learn.chatgpt.com/docs/subagents) 문서와 현재 실행 환경의 도움말에서 확인합니다.

## 아이디어부터 전달까지 연결하는 입력 계약

전체 흐름은 `최초 요청 → 요구사항 인터뷰 → PRD/ADR → 이슈 분해 → Red/Green/Refactor → 보안 → E2E → CI/브랜치 보호 → main 머지`입니다. 앞단의 [기획](planning.md)과 [TDD](tdd.md)에서 확보한 승인 근거를 다음 단계로 인계합니다.

다음 필수 입력을 확인한 경우에만 해당 실행 단계로 넘어갑니다. 미결 입력을 AI가 승인된 사실로 대신 채우지 않습니다.

| 단계                 | 필수 입력                               | 수행과 산출물                                   | 다음 단계 승인                             |
| -------------------- | --------------------------------------- | ----------------------------------------------- | ------------------------------------------ |
| 아이디어/인터뷰 인계 | 최초 요청, 사용자 문제, 용어, 제외 범위 | 최초 요청과 확정 결정 분리, 미결 질문 목록      | 요구사항 승인                              |
| 아키텍처 인계        | 확정 요구사항, 실제 레포, 제약          | PRD, ADR, 디자인 근거, 기술 결정과 이유         | 아키텍처 승인                              |
| 구현 범위 인계       | 기능 우선순위, 예산, 데이터 경계        | 포함/제외 범위와 변경 허용 파일                 | 범위 승인                                  |
| 이슈 인계            | 승인 범위, 의존 순서                    | 이슈별 AC, 시그니처, 검증 계층, base/head 계획  | 이슈 목록 승인                             |
| TDD 사이클           | 승인 이슈와 실행 가능한 테스트 환경     | 실패 근거, 최소 구현, AC 검증, 리팩터·보안 결과 | 대화형 단계별 승인 또는 명시된 제한적 위임 |
| 기능 검증            | 기능 이슈 통합 결과, PRD 사용자 여정    | E2E 시나리오·실행·실패 복구 기록                | 기능 여정 검토                             |
| 전달                 | 검증 증거, PR 초안, 브랜치 정책         | PR, CI 결과, 리뷰, 머지 기록                    | 외부 변경 및 최종 머지 승인                |

재사용할 핵심은 도구 이름이 아니라 **입력과 검증 결과를 다음 단계에 넘기는 계약**입니다. 각 단계는 앞 단계의 파일 경로, 버전, 승인 근거를 참조하고 AI가 제안한 내용과 사용자가 확정한 내용을 섞지 않습니다.

## 최소한의 E2E로 연결 검증

### 계층과 비용

각 함수가 테스트를 통과해도 연결이 끊기면 앱은 동작하지 않습니다. 작은 규칙과 경계는 단위 테스트로 빠르게 확인하고, 핵심 사용자 여정 전체는 적은 수의 E2E로 확인합니다.

| 계층 | 검증 예시                                   | 비용·안정성                                                         | 구분 기준                                                      |
| ---- | ------------------------------------------- | ------------------------------------------------------------------- | -------------------------------------------------------------- |
| 단위 | `addTag()`가 올바른 객체를 반환             | 밀리초, 환경 의존 없음, 함수 단위 추적, flaky 거의 없음             | 작은 동작의 규칙·예외·경계값; 시간과 외부 상태를 통제해야 함   |
| 통합 | Context와 API 함수가 연결되어 동작          | 모듈 사이 연결 검증                                                 | 모듈 계약과 데이터 전달 검증; 사용자 전체 여정과 동일하지 않음 |
| E2E  | `react` 입력 후 Enter를 눌러 chip 표시 확인 | 초-분, 브라우저·서버·DB 필요, 원인 추적이 넓고 네트워크·타이밍 영향 | 사용자가 관찰하는 전체 경로; 실제 연결과 대체한 경계를 명시    |

위의 속도와 환경 의존성은 상대적인 비교이며 모든 테스트에 적용되는 보장값이 아닙니다. 단위 테스트도 전역 상태나 시간을 통제하지 않으면 불안정할 수 있습니다. 파일 이름에 E2E가 들어갔다는 이유만으로 서버와 데이터베이스까지 연결되었다고 판단하지 않습니다. 로컬 `npm run check`도 이 표의 통합 테스트로 분류하면 안 됩니다.

### 시점, 원칙, 도구

- 전달 순서: TDD·보안 완료 → `/e2e-write` → `/create-pr` → CI → main 머지.
- 기능의 모든 이슈를 병합한 뒤 E2E를 한 번 작성하고, 이후 새 이슈의 PR 전에는 기존 E2E 전체를 회귀 실행합니다. 첫 기능에서는 이슈를 **기능 통합 브랜치**에 모은 뒤 최종 main PR 전에 작성합니다.
- 네 가지 원칙을 적용합니다. 완결된 사용자 여정을 검증하고, 단위 테스트와 같은 내용을 중복해서 검사하지 않으며, 정상 흐름을 중심으로 구성합니다. 예외와 경계는 주로 단위 테스트에서 맡습니다. “태그가 잘 동작한다”처럼 추상적으로 쓰지 않고 “Enter를 누르면 chip이 표시된다”처럼 구체적인 행동과 결과를 적습니다.
- 도구 구성에서는 Playwright를 Vitest와 분리해 사용하고, `webServer`로 서버를 실행하며, 의미 기반 선택자와 Trace Viewer의 스크린샷·네트워크·콘솔 기록을 활용합니다.
- 선택자 우선순위는 `getByRole → getByText → getByPlaceholder → getByTestId`입니다. 마지막 방법은 다른 방법을 쓸 수 없을 때만 사용하며 `data-testid`를 남용하지 않습니다.
- 데이터 정리에서는 생성한 note ID를 보관했다가 `afterEach`에서 각각 API DELETE로 지우고 ID 배열을 비웁니다. 테스트 실행 순서와 무관하게 독립적으로 동작하게 합니다.
- 실행 모드에서 headless는 화면을 열지 않는 기본 자동 실행이고, headed는 브라우저 창을 보며 디버깅하거나 시연하는 방식입니다. 둘은 같은 테스트의 실행 모드 차이이며 서로 다른 테스트 계층이 아닙니다.

최소 E2E 전략에서는 정상 흐름을 먼저 검증합니다. 후속 앱에서 로그인 실패나 권한 차단처럼 사용자에게 직접 영향을 주는 위험이 핵심이라면, 승인된 위험 분석에 따라 E2E 범위를 넓힙니다. 이를 모든 제품에서 예외 E2E를 금지하는 보편 규칙으로 해석하지 않습니다. 브라우저 창을 표시하는 headed 모드와 표시하지 않는 headless 모드의 결과가 다르면 환경 차이를 조사하며, 모드 차이를 무시하고 같은 결과라고 보고하지 않습니다.

### 재사용 절차: E2E 작성과 실행

입력: 승인 PRD의 사용자 스토리, 통합된 기능, 기존 단위·통합 테스트, 실행 URL, 테스트 계정, 격리 데이터 정책, 설치된 러너/브라우저, 변경 승인 범위.

1. 기능 통합이 끝났는지와 앱을 실행할 수 있는지 확인합니다. 아직 구현하지 않은 여정을 실패 버그로 등록하지 않고 선행 구현 누락으로 구분합니다.
2. 사용자의 시작 상태부터 마지막으로 관찰할 결과까지 여정을 펼쳐 봅니다. 내부 함수의 세부 분기는 단위·통합 테스트로 보내고 핵심 정상 경로를 선택합니다.
3. 화면의 실제 역할(role), 이름, 텍스트를 확인해 요소 탐색자(locator) 후보를 정합니다. 선택자 우선순위와 선택 이유를 기록하며 존재하지 않는 UI나 선택자를 추정하지 않습니다.
4. 생성할 데이터에 테스트 소유권을 표시하고 생성된 ID를 수집합니다. 삭제 대상은 이번 실행에서 만든 테스트 데이터로 한정합니다. 운영 URL이라면 실행을 중단합니다.
5. 승인된 시나리오에 따라 테스트를 작성합니다. 서버 시작 방법, 데이터 초기화·정리, 실패 증거 수집 설정은 각각 확인합니다.
6. 관련 시나리오를 실행하고 결과를 읽습니다. headless 보고서와 실제 화면 검토를 구분합니다. 화면 확인이 필요한 실패는 headed 모드나 사용할 수 있는 브라우저 도구로 관찰합니다.
7. 실패 원인을 해결한 뒤 관련 테스트를 다시 실행하고, 최종 전달 시 승인된 전체 회귀 검사를 수행합니다. 변경이나 실패가 없는데 같은 검사만 반복하지 않습니다.

산출물에는 시나리오 목록, 테스트 파일, 실행 명령과 종료 코드, 대상 버전, 보고서와 실행 추적(trace) 경로, 데이터 정리 결과, 남은 실패와 승인 기록을 포함합니다. 이 문서에서는 산출물의 양식만 제공합니다.

```text
E2E 시나리오 ID / PRD 스토리 / 관련 이슈:
기능 통합 상태 / 대상 코드 버전:
사용자 / 시작 상태 / 테스트 URL:
Given: 테스트 소유 데이터와 초기 화면
When: 입력, 클릭, 키 동작의 구체적 순서
Then: 화면에 보여야 할 결과와 검증 지점
locator 후보와 선택 이유:
단위·통합에서 이미 검증한 내용 / 중복 제외 이유:
생성 데이터 ID 수집 / 정리 방법 / 정리 실패 처리:
실행 모드 / 명령 / 종료 코드 / 통과·실패·건너뜀 수:
화면 직접 검토 여부 / 보고서·trace 경로:
실패 계층 / 회귀 테스트 / 재실행 결과:
검토자 / 승인 범위 / 미결 사항:
```

### 실패 복구

E2E가 실패하면 API, 화면 렌더링, 내부 로직 가운데 어느 계층이 고장 났는지 찾습니다. 이어서 적합한 단위·통합 테스트에 회귀 사례를 추가해 Red를 확인하고, 제품 코드를 수정해 Green으로 만든 뒤 E2E를 다시 실행합니다. 테스트를 통과시키려고 E2E 기준을 약화해서는 안 됩니다.

먼저 제품 버그, 잘못 작성된 테스트, 환경 장애, 오염된 데이터를 구별합니다. 제품 버그를 검증문 완화나 테스트 건너뛰기로 숨기지 않습니다. 테스트 자체가 승인된 요구사항과 어긋났다면 근거와 변경 이유를 별도로 검토받아 수정할 수 있습니다. 모듈 연결 결함에는 적합한 통합 회귀 테스트도 추가합니다. 데이터 정리에 실패했다면 성공 결과에 묻어 두지 말고 데이터 ID와 소유 범위를 남깁니다. 실행 추적(trace)에 담긴 자격증명이나 개인정보는 외부에 공유하지 않습니다.

## PR, CI, 보호 규칙, 최종 머지

### 검증 순서

`create-pr`는 **PR 초안 생성 → 개발자 승인 → E2E → 실패하면 PR 생성 중단 / 성공하면 push → PR 생성** 순서로 진행합니다. 승인을 받기 전에 외부 PR부터 만드는 절차가 아닙니다.

검증은 코드 스타일(Husky+lint-staged), 커밋 메시지(commitlint), 보안, E2E, 깨끗한 환경의 CI 순서로 누적합니다. 로컬에서 성공했다는 사실만으로 누락된 의존성, 환경변수, 캐시, 컴퓨터 환경 차이까지 검증되지는 않습니다.

지속적 통합(CI)은 저장소 정책에 맞는 대상 브랜치의 PR에서 다음 순서로 실행되게 구성합니다. 깨끗한 체크아웃 → 실행 환경 준비 → 잠금 파일 기준 설치(`npm ci`) → 코드 규칙 검사(lint) → 타입 검사 → 의존성 감사 → 테스트 순서입니다. 예를 들어 `verify` 작업을 둘 수 있지만, 자동화 작업(action)의 버전과 운영체제·실행 환경은 대상 환경에서 검증한 값으로 고정합니다. Playwright를 사용한다면 브라우저, 서버, 데이터베이스 준비와 실패 보고서·실행 추적 보관을 별도로 구성합니다. `npm test`가 모든 테스트 계층을 실행한다고 가정하지 말고 실제 `scripts` 설정을 확인합니다.

브랜치 보호 설정에는 PR과 상태 검사를 필수 조건으로 연결합니다. 직접 push와 검사 미통과 병합이 실제로 차단되는지도 확인합니다. 가능하면 첫 병합 전에 보호와 리뷰 조건을 준비합니다. 보호 규칙을 나중에 적용했다면 이전 병합도 보호받았다고 보고하지 않습니다. 이슈별 이력을 보존해야 한다면 여러 커밋을 하나로 합치는 squash 대신 승인된 병합 전략을 사용합니다. CI 성공은 구성된 환경에서 통과했다는 증거이며 모든 환경에서의 성공을 보장하지 않습니다.

### 재사용 절차: 전달 후보 준비부터 머지 확인

입력: 승인된 변경 범위, 이슈 AC, 보안 결과, E2E 증거, 현재 head/base, PR 초안, CI 정의와 필수 검사 이름, 리뷰 정책, 외부 작업 승인.

1. 작업 트리와 각 변경의 소유자를 확인하고 해당 이슈의 변경분(diff)만 검토합니다. 다른 작업자의 변경을 커밋하거나 임시 보관(stash)하거나 초기화(reset)하지 않습니다.
2. PR 제목, 목적, 변경 파일, AC별 근거, 테스트 결과, 위험, 복구 계획을 초안으로 작성합니다. 작업 브랜치(head)와 기준 브랜치(base)를 명시하고 리뷰를 받습니다.
3. 승인 범위 안의 관련 검사와 기존 E2E를 실행합니다. 실패하면 push와 PR 생성 절차를 중단하고 E2E 실패 복구 절차로 돌아갑니다.
4. 커밋, push, 외부 PR 생성이 각각 사용자 요청에 포함되는지 확인합니다. 스킬 이름이나 로컬 검사 통과만으로 외부 작업 권한이 있다고 추정하지 않습니다.
5. 권한을 확인한 후속 실행에서만 실제 PR을 만듭니다. CI가 대상 head에 필요한 검사를 모두 완료했는지도 확인합니다. 대기 중(`queued`), 건너뜀(`skipped`), 취소(`cancelled`), 검사 없음 상태를 통과로 바꾸지 않습니다.
6. 필수 검사 이름이 실제 CI 작업(job)과 연결되는지, 대상 브랜치의 보호와 리뷰 조건을 충족하는지 확인합니다. main에만 설정된 CI가 기능 브랜치를 대상으로 하는 이슈 PR에도 실행된다고 가정하지 않습니다.
7. 최종 병합 승인을 받은 뒤에만 승인된 병합 전략을 사용합니다. 브랜치 이름, PR 번호, head 변경 여부를 병합 직전에 확인합니다. 승인된 이력 보존 정책을 임의로 squash 방식으로 바꾸지 않습니다.
8. 병합 결과와 대상 커밋을 확인하고 운영 설명서를 실제 코드에 맞춥니다. main 병합, 서비스 배포, 운영 정상 여부는 각각 별도의 결과로 기록합니다.

```text
전달/PR 초안
이슈 / 목적 / 승인된 범위:
head / base / 검증 대상 커밋:
변경 파일 / 다른 작업자 변경 제외 내역:
AC별 구현·테스트 근거:
단위 / 통합 / E2E / 타입 / lint / 보안: 실행·미실행·실패 구분
실제 명령 / 종료 코드 / 보고서:
Closes #N 사용 여부와 대상 이슈:
CI 필수 검사 이름 / 실행 URL / 대상 head / 결과:
리뷰 결과 / 알려진 위험 / 복구 계획:
커밋·push·PR 생성 승인 / 머지 승인: 각각 범위와 근거
merge 전략 / 결과 커밋 / 배포 검증은 별도:
```

실패를 복구할 때는 CI 로그에서 처음 발생한 실제 실패를 분류합니다. 환경 문제라면 실행 환경, 잠금 파일, 변수, 서비스 차이를 확인하고 제품 결함이라면 회귀 테스트로 재현합니다. 충돌이 생겼거나 head가 바뀌었다면 이전 테스트 결과를 그대로 재사용하지 않습니다. 병합 후 문제가 생기면 검토할 수 있는 되돌리기 계획을 준비하되 강제 push나 승인 없는 revert로 복구하지 않습니다.

### 문서 보존

README, 운영 가이드, 구조도를 실제 상태에 맞춥니다. ADR의 결정 이유와 명세(spec)·이슈의 승인 근거는 보존합니다. 장기 활용 여부와 프로젝트 보존 정책을 확인하고 별도 승인 없이 삭제하거나 이동하지 않습니다. 이 문서는 정리 작업을 실행할 권한을 부여하지 않습니다.

## tdd-loop는 순서 자동화, 승인은 유지

### 실제 이름과 0+7 단계

`/tdd-loop`는 새로운 구현 알고리즘이 아니라 기존 스킬과 에이전트를 정해진 순서로 호출하는 상위 조정 스킬입니다. 일곱 번의 명령을 한 번으로 줄이고 누락이나 실패가 발생한 위치를 관리하지만, 사람의 판단과 승인을 우회하지 않습니다. “7단계” 앞에 사전 점검인 0번이 있으므로 실제 단계 번호는 0부터 7까지입니다.

| 단계 | 호출/역할          | 입력과 수행                            | 산출물·검증·게이트                                             |
| ---- | ------------------ | -------------------------------------- | -------------------------------------------------------------- |
| 0    | 사전 점검          | 이슈·AC, base 확인, `feat/<slug>` 분기 | 브랜치 계획, 허용 변경, 실행 환경; 생성 승인 없으면 계획만     |
| 1    | `/test-scenarios`  | 시그니처·시나리오 설계                 | 정상·예외·경계 사례와 기대값; 시그니처·시나리오 사용자 승인    |
| 2    | `/tdd-red`         | 승인 시나리오로 실패 테스트 작성       | 기대 동작 미구현 때문에 실패한 로그; import/설정 오류와 구분   |
| 3    | `/tdd-green`       | 최소 구현, 내부 회귀 감시              | 테스트를 바꾸지 않은 최소 diff, 관련 테스트 결과               |
| 4    | `@ac-verifier`     | AC 충족 독립 검증                      | AC별 실제 근거와 미충족 목록; 구현자 자기 선언만으로 통과 금지 |
| 5    | `/tdd-refactor`    | 동작 보존 리팩터링                     | 변경 이유, 테스트 재검증, 과잉 추상화 여부                     |
| 6    | `/security-review` | 보안 점검                              | 발견 사항·심각도·수정·재검사·미해결 위험                       |
| 7    | `/create-pr`       | commitlint, `Closes #N`, PR 생성       | 승인된 PR 초안, E2E 결과, 외부 작업 승인, 실제 생성 결과       |

4번은 구현자와 분리된 검증자가 AC 충족 여부를 판단하는 단계입니다. `ac-verifier` 스킬에 검증 계약을 두고 실제로 독립 실행했는지 확인합니다. 대화형 `tdd-loop`의 승인 절차와 자동 모드의 수치 기반 STOP 정책을 혼동하지 않습니다.

### 브랜치 흐름과 종료점

기능 통합 중의 브랜치 예:

```text
main
  feature/<feature>              기능 통합 브랜치
    feat/<issue-1> -> PR -> feature/<feature>
    feat/<issue-2> -> PR -> feature/<feature>
    ...
  feature/<feature> -> 최종 PR -> main  (최종 전달 절차)
```

“PR 생성”과 “이슈 병합”을 별도의 완료 상태로 기록하고 병합 권한을 확인합니다. 이슈 PR이 기능 통합 브랜치에 병합되더라도 main에 자동으로 병합할 권한이 생기지는 않습니다.

기능 전체를 main에 넣은 뒤 생긴 독립 수정은 main에서 새 브랜치를 만들 수 있습니다. 모든 이슈 PR의 기준 브랜치(base)를 기능 통합 브랜치나 main으로 고정하지 않습니다. 기능을 통합하는 중인지, 통합 뒤의 독립 변경인지 입력에서 확정합니다.

### 정지, 재개, 승인 계약

어느 단계에서 실패했는지 명확히 보고하고, 함수·API 시그니처, 시나리오, 구현 등에 대한 사용자 승인 게이트를 유지합니다.

1. 처음 호출할 때 이슈, AC, 작업 브랜치(head), 기준 브랜치(base), 변경을 허용한 파일, 승인된 명령 범위를 확인합니다.
2. 각 하위 단계의 결과를 기록한 뒤 다음 단계에 필요한 입력이 충분한지 확인합니다. 승인받지 않은 시나리오로 Red 단계에 넘어가지 않습니다.
3. 테스트 실패가 기대한 Red인지, 도구가 비정상적으로 실패한 것인지 구분합니다. 도구 실패는 Green 단계에 들어갈 조건이 아닙니다.
4. AC 미충족, 해결하지 않은 보안 문제, 테스트 실패, 승인 누락, 범위 변경, 외부 도구 부재가 있으면 해당 위치에서 멈춥니다. 완료했다고 선언하지 않습니다.
5. 승인 대기와 기술 실패를 구별합니다. 승인이 필요한 단계에서는 검토할 산출물과 질문을 제시하고, 실패했다면 로그·원인·복구안을 남깁니다.
6. 재개할 때 작업 트리, 브랜치, 입력 버전을 다시 확인합니다. 유효한 이전 승인까지 반복해서 묻지 않지만 범위가 달라졌다면 변경된 부분을 확인합니다.

```text
TDD 실행 원장
이슈 / 승인 AC / 기획 승인 근거:
base / head / 대상 버전 / 변경 허용 파일:
단계 0-7 각각: 상태, 입력, 산출물 경로, 명령, 종료 코드, 증거
상태 값: 준비 / 실행 / 승인 대기 / 실패 / 통과 / 미실행
마지막 통과 단계 / 현재 실패·대기 단계:
승인자 / 승인 범위 / 변경된 전제:
PR 생성 여부 / feature 머지 여부 / main 머지는 별도:
복구 작업 / 재개 조건 / 재검증 필요 범위:
```

## tdd-auto-loop의 자체 승인과 객관 STOP

### 컨테이너와 다른 점

`/tdd-auto-loop`는 실행 순서와 제한된 의사결정을 자동화하는 자율 반복 절차입니다. 각 단계는 위 공통 정책에 따라 새 작업 컨텍스트의 서브에이전트가 실행합니다. 메인은 코드 본문을 직접 다루는 대신 결과 JSON을 누적하고 검사합니다. 명시적으로 위임된 구현 범위 안의 하위 승인 게이트만 자체 판정하며, Green 직후 별도의 `ac-verifier`가 검증합니다.

STOP은 “계속할까요?”라고 물은 채 세션을 열어 두는 상태가 아닙니다. 중단 이유를 로그에 남기고, 외부 쓰기가 승인된 경우에만 이슈 댓글을 게시한 뒤 실행을 종료합니다. 사용자가 필요한 입력을 보강한 뒤 다시 실행합니다. 자동 실행 후 사람의 역할은 **PR 리뷰 한 번**입니다. 자동 실행은 PR 준비 또는 승인된 PR 생성에서 끝나며 main 병합에는 별도 승인이 필요합니다.

### 필수 STOP 조건 전체

다음 표는 자동 모드에서 반드시 실행을 끝내야 하는 STOP 조건입니다. 임의로 완화하지 않습니다.

| 단계                | 필수 STOP 조건                      | 남길 근거와 복구                                                                         |
| ------------------- | ----------------------------------- | ---------------------------------------------------------------------------------------- |
| 0 사전 점검         | AC 누락 / uncommitted / 잘못된 base | 누락 AC, 작업 트리 상태, 기대·실제 base; 다른 사람 변경을 커밋·삭제해 조건을 맞추지 않음 |
| 1 시나리오          | 시나리오 5개 미만 / 경계값 누락     | 사례 목록과 AC 대응; 중복 사례로 숫자만 채우지 않고 승인 범위에서 보강                   |
| 2 Red               | 잘못된 이유로 실패(import 에러)     | 실제 stderr와 예상 실패 차이; 러너·경로를 수정하고 Red 증거 재수집                       |
| 3 Green (×3)        | 3회 실패 / 테스트 수정 시도         | 시도별 diff·실패 로그, 테스트 변경 감지; 네 번째 자동 시도 금지                          |
| 4 AC 검증           | `ac_passed=false`                   | AC별 미충족 증거; 기준 완화 대신 입력·구현 보강 후 새 실행                               |
| 5 Refactor          | `npm test` 미통과                   | 동작 회귀 위치; 해당 실행의 변경만 검토해 복구                                           |
| 6 Security + 재스캔 | 재스캔 후 high 이상                 | scanner·대상·결과와 잔여 심각도; 수정 후 재검사, 무근거 면제 금지                        |
| 7 PR 생성           | commitlint 실패                     | 메시지 규칙과 실제 오류; 훅 우회 금지, 통과 시 PR URL 기록                               |

Green 실행 시도는 1부터 3까지 기록하며 세 번째 실패 뒤 네 번째 자동 시도는 금지합니다. 시나리오가 5개라는 사실이 사례의 질을 대신하지는 않습니다. 각 결과의 버전, 증거, 상태를 함께 검증합니다.

`attempt`는 기존 단계 실행의 식별자이고 `green_attempts.used`는 실제 Green 구현 시도 횟수입니다. `retry_count`는 첫 Green 뒤에 추가로 구현한 시도만 셉니다. 기대한 Red와 코드·계약·테스트·환경이 모두 같은 버전에서 테스트만 다시 실행한 경우에만 Green 시도와 재시도 횟수에서 제외합니다. AC를 보완한 뒤 실제 구현이나 계약을 수정해 Green으로 돌아갔다면 모델, 컨텍스트, 재개 여부와 관계없이 누적 Green 시도와 재시도에 포함합니다. 진단에는 별도의 1회 예산을 두며 새 컨텍스트, 모델, 재개로 어떤 횟수도 초기화하지 않습니다.

| failure class                                                                     | 다음 행동                                                                       |
| --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `LOCAL_IMPLEMENTATION_ERROR`                                                      | 남은 Green 시도가 있을 때만 retry 후보                                          |
| `ARCHITECTURE_UNCERTAINTY`, `CROSS_MODULE_DEPENDENCY`, `UNKNOWN_RUNTIME_BEHAVIOR` | 새 근거가 있고 diagnostic budget·위임이 남았을 때 읽기 전용 diagnostic 후보     |
| `REQUIREMENT_AMBIGUITY`                                                           | user gate                                                                       |
| `BROKEN_ENVIRONMENT`, `SECURITY_BLOCK`                                            | STOP                                                                            |
| `EXTERNAL_TOOL_FAILURE`                                                           | evidence 보존, 중복 호출·model 교체로 재호출하지 않으며 권한/환경 복구까지 STOP |

진단을 호출하기 전에는 현재 STOP이나 승인 대기가 없고 환경이 정상인지 확인합니다. 승인된 범위와 진단 위임, 남은 Green·진단 예산, 이전과 같은 실패가 아님을 보여 주는 새 근거도 모두 확인합니다. 진단이 승인된 기술안 안에서 실행 계획을 제시하면 새 작업자가 구현합니다. 새로운 아키텍처 결정이 필요하면 사용자 승인 단계로 보내고, 진단 실패·불명확·진전 없음이면 STOP합니다. 기록에는 상향 판단 이유, 결과와 증거 참조, 요청·관찰한 모델과 추론 강도, 컨텍스트 ID, 승인 참조, 사용량·예산·상태를 둡니다. `not-run`과 `unknown`은 구분합니다.

CI가 `moderate` 이상 심각도의 감사를 차단하도록 설정되어 있다면, 이는 자동 모드 재검사에서 적용하는 `high 이상` STOP과 별도의 게이트입니다. `high`가 없다는 이유로 `moderate` 단계의 CI 실패를 통과로 바꾸지 않습니다.

### 자동 승인에 대한 필수 제한

프로젝트 지침과 사용자가 위임한 범위를 먼저 적용합니다.

- 자동 절차 안의 자체 승인을 모든 작업에 통하는 권한으로 해석하지 않습니다. 요구사항, 아키텍처, 범위, 이슈 목록에 대한 사용자 승인 경계를 그대로 유지합니다.
- 사용자가 후속 자율 실행을 명시적으로 위임한 경우에만, 이미 승인한 입력 안에서 되돌릴 수 있는 구현과 검증 판단을 자동 처리할 수 있습니다. 위임 범위 밖의 새 의존성, 요구사항 변경, 데이터 삭제, 외부 전송은 구현이 기술적으로 성공했는지와 별도로 승인 여부를 판단합니다.
- 커밋, push, PR, 이슈 댓글, 병합을 하나로 묶어 모두 승인받았다고 추정하지 않습니다. 외부 댓글이 금지되었거나 승인되지 않았다면 STOP 보고를 로컬 산출물로 남기며 댓글을 게시했다고 기록하지 않습니다.
- 실행할 때 실제 서브에이전트 도구와 격리 범위를 확인합니다. 문서에서 역할을 나눴다는 사실만으로 컨텍스트나 파일시스템 격리가 구현되었다고 보고하지 않습니다. 격리 실행이 불가능하다면 공통 정책의 실행 불가 절차를 따릅니다.
- 메인은 단계별 결과 JSON에 필수 필드가 있는지, 증거 경로가 유효한지, 코드 버전이 일치하는지, 실제 테스트 결과가 무엇인지 검증합니다. 결과 생성자가 적은 `passed=true` 값만으로 성공을 판정하지 않습니다. 코드를 직접 검토해야 한다면 추가한 검토 범위를 기록합니다.
- AC 검증은 구현자와 분리하고 승인된 AC를 검증자가 수정할 수 없게 합니다. Refactor 뒤에 동작이나 계약이 바뀌었다면 Green 직후에 수행한 기존 AC 검증만으로 종료하지 않습니다.
- 실행 기반이 없거나, 권한 범위를 넘었거나, 증거가 누락되었거나, 결과를 해석하지 못했거나, 사용자가 중단했다면 안전을 위해 실행을 끝내는 STOP 조건으로 처리합니다.

### 재사용 절차와 결과 JSON 템플릿

입력: 승인 이슈·AC, 자율 위임 범위, 실행 환경, base/head, 하위 단계 계약, 검사 도구, 반복 예산, 외부 작업 허용 여부.

1. 사전 점검 결과와 허용된 작업을 확정합니다. 앱이 없거나 구현 승인을 받지 않았다면 실행하지 않습니다.
2. 단계별 담당자에게 필요한 입력과 변경을 허용한 파일만 전달합니다. 같은 파일을 동시에 수정하도록 무작정 나누지 않습니다.
3. 각 단계가 끝나면 결과를 정해진 형식으로 수집합니다. 이전 단계가 통과한 근거를 다음 단계의 입력과 연결합니다.
4. 필수 STOP과 실행 안전 STOP을 구분해 검사합니다. STOP 조건이면 후속 단계와 외부 작업을 수행하지 않습니다.
5. Green은 제한된 횟수 안에서만 시도하고 별도의 AC 검증을 호출합니다. 보안을 수정한 뒤에는 다시 검사하고 관련 회귀 테스트도 실행합니다.
6. 모든 검사를 통과해도 외부 생성 권한이 없다면 PR 초안과 증거만 인계합니다. 권한이 있을 때만 실제 PR URL로 생성 결과를 증명합니다.
7. 사람의 PR 리뷰와 별도 병합 조건을 남깁니다. 사용자가 입력을 보강했거나 실패 원인이 해결된 뒤에만 새 상태 점검부터 다시 실행합니다.

## 실행 스킬과 검증 명령

스킬이 실제로 등록되고 호출되었는지는 실행 환경과 등록 목록에서 확인합니다. 스킬 이름이 있다는 사실만으로 독립 에이전트나 파일시스템 격리가 자동 제공되는 것은 아닙니다.

| 스킬·역할                          | 필수 계약                                                        |
| ---------------------------------- | ---------------------------------------------------------------- |
| `e2e-write`                        | PRD 여정, locator, 데이터 격리, 실행·보고서·정리                 |
| `create-pr`                        | 초안 승인, E2E 실패 차단, 승인된 push/PR, base/head·CI·머지 구분 |
| `tdd-loop`                         | 사전 점검+7단계, 하위 승인 유지, 실패 위치와 재개                |
| `tdd-auto-loop`                    | 격리 단계, 결과 JSON, 필수·안전 STOP, 독립 AC, PR 리뷰           |
| `test-scenarios`                   | 시그니처·시나리오 승인, 자동 모드의 최소 5개·경계값              |
| `tdd-red` / `tdd-green`            | 올바른 실패 증거, 최소 구현·회귀, 자동 모드 최대 3회·테스트 동결 |
| `ac-verifier`                      | 구현자와 분리한 AC 검증과 `ac_passed` 근거                       |
| `tdd-refactor` / `security-review` | 동작 보존·회귀, 보안 수정·재스캔·잔여 위험                       |
| `feature-planner`                  | 앞단 기획·네 승인 게이트, [상세 기획 계약](planning.md)          |

명령을 사용하기 전에 실제 설치 버전, 도움말, 프로젝트의 `scripts` 설정에서 사용법과 범위를 확인합니다. 아래 예시는 명령을 실행할 권한을 부여하지 않습니다.

| 명령·구성                                                          | 실행 전 확인                                  |
| ------------------------------------------------------------------ | --------------------------------------------- |
| `npx playwright test`, `--headed`                                  | 로컬 러너·브라우저·서버·실행 URL              |
| `npm run test:e2e`                                                 | script 존재와 실제 포함 범위                  |
| `npx playwright show-report`                                       | HTML 보고서 존재; trace 준비·열기는 별도 확인 |
| `webServer`, role/text/placeholder/testid locator                  | 실제 접근성 이름·중복·설치 버전 API           |
| `npm ci`, `npm run lint`                                           | 잠금 파일·런타임·실제 lint 범위               |
| `npx tsc --noEmit`, `npm audit --audit-level=moderate`, `npm test` | 타입 구성·감사 정책·테스트 층                 |
| `gh pr create --base "$BASE" --head "$HEAD" --title "$TITLE"`      | 인증·저장소·대상·외부 생성 승인               |
| `gh pr merge "$PR" --merge`                                        | 정확한 PR·리뷰·보호·CI·별도 머지 승인         |
| `gh issue create`                                                  | 외부 이슈 생성 요청과 중복 여부               |

## 최종 점검

- 요구사항·아키텍처·범위·이슈 목록 승인과 유한한 실행 대상·반복 상한이 있는가?
- 앱과 러너·명령을 실제 확인하고 단위·통합·E2E·로컬 품질·원격 CI를 구분했는가?
- Red가 올바른 이유로 실패하고 Green의 테스트 동결과 독립 AC 검증을 지켰는가?
- Refactor 후 회귀, 보안 수정 후 재스캔, E2E 데이터 정리 증거가 있는가?
- 대화형 승인 대기와 자동 모드 STOP 종료를 혼동하지 않았는가?
- 이슈 PR·기능 통합·main 머지·배포·사람 수락을 별도로 보고했는가?
- PR 승인·검사 성공·외부 작업·리뷰·머지 승인 및 head 일치가 확인됐는가?
- 보호 문서와 다른 작업자의 변경을 보존하고 미실행·실패·재개 조건을 명시했는가?
