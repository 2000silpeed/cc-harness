# 전달 검증과 제한된 TDD 자동화

승인된 구현을 E2E·PR·CI·리뷰로 검증하고, 반복 실행을 명시적인 권한과 STOP 조건 안에 둔다. 현재 등록 목록은 [registry.json](../harness/registry.json), 실제 검증 상태는 [verification.md](../harness/verification.md)을 확인한다. 문서·스킬 등록은 제품 실행이나 머지 증거를 대신하지 않는다.

## 아이디어부터 전달까지 연결하는 입력 계약

전체 흐름은 `최초 요청 → 요구사항 인터뷰 → PRD/ADR → 이슈 분해 → Red/Green/Refactor → 보안 → E2E → CI/브랜치 보호 → main 머지`다. 앞단의 [기획](planning.md)과 [TDD](tdd.md) 승인 근거를 다음 단계로 인계한다.

다음 필수 입력을 확인한 경우에만 해당 실행 단계로 넘어간다. 미결 입력을 AI가 승인된 사실로 채우지 않는다.

| 단계                 | 필수 입력                               | 수행과 산출물                                   | 다음 단계 승인                             |
| -------------------- | --------------------------------------- | ----------------------------------------------- | ------------------------------------------ |
| 아이디어/인터뷰 인계 | 최초 요청, 사용자 문제, 용어, 제외 범위 | 최초 요청과 확정 결정 분리, 미결 질문 목록      | 요구사항 승인                              |
| 아키텍처 인계        | 확정 요구사항, 실제 레포, 제약          | PRD, ADR, 디자인 근거, 기술 결정과 이유         | 아키텍처 승인                              |
| 구현 범위 인계       | 기능 우선순위, 예산, 데이터 경계        | 포함/제외 범위와 변경 허용 파일                 | 범위 승인                                  |
| 이슈 인계            | 승인 범위, 의존 순서                    | 이슈별 AC, 시그니처, 검증 계층, base/head 계획  | 이슈 목록 승인                             |
| TDD 사이클           | 승인 이슈와 실행 가능한 테스트 환경     | 실패 근거, 최소 구현, AC 검증, 리팩터·보안 결과 | 대화형 단계별 승인 또는 명시된 제한적 위임 |
| 기능 검증            | 기능 이슈 통합 결과, PRD 사용자 여정    | E2E 시나리오·실행·실패 복구 기록                | 기능 여정 검토                             |
| 전달                 | 검증 증거, PR 초안, 브랜치 정책         | PR, CI 결과, 리뷰, 머지 기록                    | 외부 변경 및 최종 머지 승인                |

재사용할 핵심은 도구 이름보다 **입력과 검증 결과를 다음 단계에 넘기는 계약**이다. 각 단계는 앞 단계의 파일 경로·버전·승인 근거를 참조하고, AI가 제안한 내용과 사용자가 확정한 내용을 섞지 않는다.

## 최소한의 E2E로 연결 검증

### 계층과 비용

함수가 각각 통과해도 연결이 끊기면 앱은 동작하지 않는다. 작은 규칙·경계는 단위 테스트로 빠르게 확인하고, 핵심 전체 여정은 적은 수의 E2E로 확인한다.

| 계층 | 검증 예시                                   | 비용·안정성                                                         | 구분 기준                                                      |
| ---- | ------------------------------------------- | ------------------------------------------------------------------- | -------------------------------------------------------------- |
| 단위 | `addTag()`가 올바른 객체를 반환             | 밀리초, 환경 의존 없음, 함수 단위 추적, flaky 거의 없음             | 작은 동작의 규칙·예외·경계값; 시간과 외부 상태를 통제해야 함   |
| 통합 | Context와 API 함수가 연결되어 동작          | 모듈 사이 연결 검증                                                 | 모듈 계약과 데이터 전달 검증; 사용자 전체 여정과 동일하지 않음 |
| E2E  | `react` 입력 후 Enter를 눌러 chip 표시 확인 | 초-분, 브라우저·서버·DB 필요, 원인 추적이 넓고 네트워크·타이밍 영향 | 사용자가 관찰하는 전체 경로; 실제 연결과 대체한 경계를 명시    |

위 속도와 환경 의존성은 상대적인 비교이지 모든 테스트의 보장값이 아니다. 단위 테스트도 전역 상태나 시간을 통제하지 않으면 불안정할 수 있다. E2E라는 파일명만으로 서버·DB까지 연결되었다고 판단하지 않는다. 로컬 `npm run check`를 이 표의 통합 테스트로 분류하면 안 된다.

### 시점, 원칙, 도구

- 전달 순서: TDD·보안 완료 → `/e2e-write` → `/create-pr` → CI → main 머지.
- 기능의 모든 이슈가 머지된 뒤 E2E를 한 번 작성하고, 이후 새 이슈의 PR 전에는 기존 전체 E2E를 회귀 실행한다. 첫 기능에서는 이슈를 **기능 통합 브랜치**에 모은 뒤 최종 main PR 전에 작성하는 흐름이다.
- 네 원칙: 완결된 사용자 여정, 단위 테스트 중복 금지, 정상 흐름 중심(예외·경계는 단위 담당), 구체적 행동과 결과. 추상적인 “태그가 잘 동작” 대신 “Enter → chip 표시”를 쓴다.
- 도구 구성: Playwright를 Vitest와 분리해 사용, `webServer`를 통한 서버 실행, 시맨틱 셀렉터, Trace Viewer의 스크린샷·네트워크·콘솔 기록을 소개한다.
- 셀렉터 우선순위는 `getByRole → getByText → getByPlaceholder → getByTestId`. 마지막 것은 다른 방법이 안 될 때 사용하며 `data-testid` 남용을 경계한다.
- 데이터 정리: 생성한 note ID를 보관했다가 `afterEach`에서 각각 API DELETE로 정리하고 ID 배열을 비운다. 실행 순서에 무관한 독립성을 목표로 한다.
- 실행 모드: headless는 기본 자동 실행, headed는 브라우저 창을 보며 디버깅·시연하는 모드로 설명한다. 같은 테스트의 모드 차이지 서로 다른 테스트 계층이 아니다.

정상 흐름을 우선하는 것은 최소 E2E 전략이다. 후속 앱에서 로그인 실패·권한 차단 등 사용자 수준 위험이 핵심이면 승인된 위험 분석으로 E2E 범위를 보강한다. 모든 제품의 예외 E2E를 금지하는 보편 규칙으로 만들지 않는다. headed/headless 결과가 다르면 환경 차이를 조사하지, 모드 차이를 무시해 같다고 보고하지 않는다.

### 재사용 절차: E2E 작성과 실행

입력: 승인 PRD의 사용자 스토리, 통합된 기능, 기존 단위·통합 테스트, 실행 URL, 테스트 계정, 격리 데이터 정책, 설치된 러너/브라우저, 변경 승인 범위.

1. 기능 통합 완료 여부와 앱 실행 가능성을 확인한다. 미구현 여정을 실패 버그로 등록하지 않고 선행 구현 누락으로 분리한다.
2. 사용자 시작 상태부터 최종 관찰 결과까지 여정을 펼친다. 내부 함수의 세부 분기는 단위·통합으로 보내고 핵심 정상 경로를 선택한다.
3. 화면의 실제 role·이름·텍스트를 확인해 locator 후보를 정한다. 셀렉터 우선순위와 선택 이유를 기록한다. 존재하지 않는 UI나 selector를 추정하지 않는다.
4. 생성할 데이터에 테스트 소유권을 표시하고 생성 ID를 수집한다. 삭제 대상은 이 실행에서 만든 테스트 데이터로 한정한다. 운영 URL이면 실행을 중단한다.
5. 승인된 시나리오에 따라 테스트를 작성한다. 서버 시작 방법, 데이터 초기화/정리, 실패 증거 수집 설정을 별도로 확인한다.
6. 관련 시나리오를 실행하고 결과를 읽는다. headless 보고서와 실제 화면 검토를 구분한다. 화면 확인이 필요한 실패는 headed 또는 이용 가능한 브라우저 도구로 관찰한다.
7. 실패 원인을 해결한 뒤 관련 테스트를 재실행하고, 최종 전달 시 승인된 전체 회귀 검사를 수행한다. 변경·실패 없이 같은 검사만 반복하지 않는다.

산출물: 시나리오 목록, 테스트 파일, 실행 명령·종료 코드, 대상 버전, 보고서/trace 경로, 정리 결과, 남은 실패와 승인 기록. 이 문서에서는 템플릿만 제공한다.

```text
E2E 시나리오 ID / PRD 스토리 / 관련 이슈:
기능 통합 상태 / 대상 코드 버전:
사용자 / 시작 상태 / 테스트 URL:
Given: 테스트 소유 데이터와 초기 화면
When: 입력, 클릭, 키 동작의 구체적 순서
Then: 화면에 보여야 할 결과와 검증 지점
locator 후보와 선택 이유:
단위·통합에서 이미 검증한 내용 / 중복 제외 이유:
생성 데이터 ID 수집 / 정리 방법 / 정리 실패 처리:
실행 모드 / 명령 / 종료 코드 / 통과·실패·건너뜀 수:
화면 직접 검토 여부 / 보고서·trace 경로:
실패 계층 / 회귀 테스트 / 재실행 결과:
검토자 / 승인 범위 / 미결 사항:
```

### 실패 복구

E2E 실패 → API·렌더링·로직 등 고장 계층 식별 → 적합한 단위·통합 테스트에 회귀 사례 추가(Red) → 프로덕션 코드 수정(Green) → E2E 재실행 순서로 복구한다. 통과시키기 위한 E2E 기준 약화는 금지한다.

먼저 제품 버그, 잘못 작성된 테스트, 환경 장애, 데이터 오염을 구별한다. 제품 버그를 assertion 완화나 skip으로 숨기지 않는다. 테스트 자체가 승인 요구사항과 어긋났다면 근거와 변경 이유를 별도 검토받아 수정할 수 있다. 모듈 연결 결함은 적합한 통합 회귀 테스트도 추가한다. 정리 실패는 성공에 묻지 말고 데이터 ID와 소유 범위를 남긴다. trace의 자격증명·개인정보는 외부 공유하지 않는다.

## PR, CI, 보호 규칙, 최종 머지

### 검증 순서

`create-pr`는 **PR 초안 생성 → 개발자 승인 → E2E → 실패 시 PR 생성 중단 / 성공 시 push → PR 생성**이다. 승인 전에 외부 PR부터 만드는 흐름이 아니다.

검증 체인은 코드 스타일(Husky+lint-staged), 커밋 메시지(commitlint), 보안, E2E, 클린 환경 CI로 누적한다. 로컬 성공만으로 누락 의존성·환경변수·캐시·머신 차이까지 검증되지는 않는다.

CI는 저장소 정책에 맞는 대상 브랜치의 PR에서 클린 체크아웃 → 런타임 준비 → 잠금 파일 설치(`npm ci`) → lint → 타입 → 의존성 감사 → 테스트를 실행하도록 구성한다. 예를 들어 `verify` job을 두되 action 버전과 운영체제·런타임은 대상 환경에서 검증하고 고정한다. Playwright가 있다면 브라우저·서버·DB 준비와 실패 보고서·trace 보관을 별도로 구성한다. `npm test`가 모든 계층을 실행한다고 가정하지 않고 scripts를 확인한다.

브랜치 보호에는 PR 필수와 상태 검사 필수를 연결하고 직접 push·미통과 머지 차단이 실제 적용되는지 확인한다. 가능한 한 첫 머지 전 보호·리뷰 조건을 준비한다. 보호가 나중에 적용됐다면 이전 머지도 보호됐다고 보고하지 않는다. 이슈별 이력 보존이 요구되면 squash 대신 승인된 merge 전략을 사용한다. CI 성공은 구성된 환경의 증거이지 모든 환경의 보장은 아니다.

### 재사용 절차: 전달 후보 준비부터 머지 확인

입력: 승인된 변경 범위, 이슈 AC, 보안 결과, E2E 증거, 현재 head/base, PR 초안, CI 정의와 필수 검사 이름, 리뷰 정책, 외부 작업 승인.

1. 작업 트리와 변경 소유권을 읽고 해당 이슈 diff만 확인한다. 다른 작업자의 변경을 커밋·stash·reset하지 않는다.
2. PR 제목, 목적, 변경 파일, AC별 근거, 테스트 결과, 위험, 복구 계획을 초안으로 작성한다. head와 base를 명시하고 리뷰를 받는다.
3. 승인 범위 내 관련 검사와 기존 E2E를 실행한다. 실패하면 push/PR 생성 경로를 닫고 E2E 실패 복구 절차로 되돌아간다.
4. 커밋·push·외부 PR 생성 각각이 사용자 요청에 포함되는지 확인한다. 스킬 이름이나 로컬 검사 통과만으로 권한을 추정하지 않는다.
5. 후속 실행에서만 실제 PR을 만들고, CI가 대상 head의 올바른 검사들을 완료했는지 결과를 확인한다. queued, skipped, cancelled, 검사 없음은 통과로 바꾸지 않는다.
6. 필수 검사 이름이 CI job과 연결되는지, 대상 브랜치 보호와 리뷰 조건이 충족되는지 확인한다. main에만 걸린 CI가 feature 대상 이슈 PR에도 실행된다고 가정하지 않는다.
7. 최종 머지 승인 후에만 승인된 merge 전략을 사용한다. branch 이름·PR 번호·head 변경 여부를 직전에 확인한다. 승인된 이력 보존 정책을 임의 squash로 바꾸지 않는다.
8. 머지 결과와 대상 커밋을 확인하고 운영 설명서를 실제 코드와 맞춘다. main 머지와 서비스 배포/운영 정상은 별도의 결과로 기록한다.

```text
전달/PR 초안
이슈 / 목적 / 승인된 범위:
head / base / 검증 대상 커밋:
변경 파일 / 다른 작업자 변경 제외 내역:
AC별 구현·테스트 근거:
단위 / 통합 / E2E / 타입 / lint / 보안: 실행·미실행·실패 구분
실제 명령 / 종료 코드 / 보고서:
Closes #N 사용 여부와 대상 이슈:
CI 필수 검사 이름 / 실행 URL / 대상 head / 결과:
리뷰 결과 / 알려진 위험 / 복구 계획:
커밋·push·PR 생성 승인 / 머지 승인: 각각 범위와 근거
merge 전략 / 결과 커밋 / 배포 검증은 별도:
```

실패 복구: CI 실패 로그에서 첫 실제 실패를 분류한다. 환경 문제는 런타임·잠금 파일·변수·서비스 차이를 확인하고, 제품 결함은 회귀 테스트로 재현한다. 충돌이나 head 변경이 있으면 이전 테스트 결과를 그대로 재사용하지 않는다. 머지 후 문제는 검토 가능한 되돌리기 계획을 준비하되 강제 push나 무단 revert로 복구하지 않는다.

### 문서 보존

README·운영 가이드·구조도를 실제 상태와 맞춘다. ADR의 결정 이유와 spec·이슈의 승인 근거는 보존한다. 장기 활용 여부와 프로젝트 보존 정책을 확인하고, 별도 승인 없는 삭제·이동은 하지 않는다. 이 문서는 정리 실행 권한을 부여하지 않는다.

## tdd-loop는 순서 자동화, 승인은 유지

### 실제 이름과 0+7 단계

`/tdd-loop`는 새로운 구현 알고리즘이 아니라 기존 스킬·에이전트를 순서대로 호출하는 컨테이너/메타 스킬이다. 명령 7번을 한 번으로 줄이고 누락·실패 위치를 관리하지만 판단과 승인을 우회하지 않는다. “7단계”에 사전 점검 0번이 추가되어 실제 표기는 0-7이다.

| 단계 | 호출/역할          | 입력과 수행                            | 산출물·검증·게이트                                             |
| ---- | ------------------ | -------------------------------------- | -------------------------------------------------------------- |
| 0    | 사전 점검          | 이슈·AC, base 확인, `feat/<slug>` 분기 | 브랜치 계획, 허용 변경, 실행 환경; 생성 승인 없으면 계획만     |
| 1    | `/test-scenarios`  | 시그니처·시나리오 설계                 | 정상·예외·경계 사례와 기대값; 시그니처·시나리오 사용자 승인    |
| 2    | `/tdd-red`         | 승인 시나리오로 실패 테스트 작성       | 기대 동작 미구현 때문에 실패한 로그; import/설정 오류와 구분   |
| 3    | `/tdd-green`       | 최소 구현, 내부 회귀 감시              | 테스트를 바꾸지 않은 최소 diff, 관련 테스트 결과               |
| 4    | `@ac-verifier`     | AC 충족 독립 검증                      | AC별 실제 근거와 미충족 목록; 구현자 자기 선언만으로 통과 금지 |
| 5    | `/tdd-refactor`    | 동작 보존 리팩터링                     | 변경 이유, 테스트 재검증, 과잉 추상화 여부                     |
| 6    | `/security-review` | 보안 점검                              | 발견 사항·심각도·수정·재검사·미해결 위험                       |
| 7    | `/create-pr`       | commitlint, `Closes #N`, PR 생성       | 승인된 PR 초안, E2E 결과, 외부 작업 승인, 실제 생성 결과       |

4번은 구현자와 분리된 AC 판단 역할이다. `ac-verifier` 스킬에 검증 계약을 두고 실제 독립 실행을 확인한다. 대화형 tdd-loop와 자동 모드의 수치 STOP 정책을 혼동하지 않는다.

### 브랜치 흐름과 종료점

기능 통합 중의 브랜치 예:

```text
main
  feature/<feature>              기능 통합 브랜치
    feat/<issue-1> -> PR -> feature/<feature>
    feat/<issue-2> -> PR -> feature/<feature>
    ...
  feature/<feature> -> 최종 PR -> main  (최종 전달 절차)
```

“PR 생성”과 “이슈 머지”를 별도 완료 상태로 기록하고 머지 권한을 확인한다. 이슈 PR이 기능 통합 브랜치에 머지되어도 자동 main 머지 권한은 생기지 않는다.

기능 전체를 main에 넣은 이후의 독립 수정은 main에서 분기할 수 있다. 모든 이슈 PR의 base를 무조건 기능 통합 브랜치 또는 main으로 하드코딩하지 않는다. 기능 통합 중인지 통합 후 독립 변경인지 입력으로 확정한다.

### 정지, 재개, 승인 계약

단계 실패 위치를 명확히 보고하고 시그니처·시나리오·구현 등 사용자 승인 게이트를 유지한다.

1. 최초 호출 시 이슈, AC, head/base, 허용 파일, 승인된 명령 범위를 확인한다.
2. 각 하위 단계 결과를 기록한 후 다음 단계의 입력이 충분한지 확인한다. 미승인 시나리오로 Red에 넘어가지 않는다.
3. 테스트 실패가 예상된 Red인지, 비정상 도구 실패인지 구분한다. 후자는 Green 진입 조건이 아니다.
4. AC 미충족, 보안 미해결, 테스트 실패, 승인 누락, 범위 변경, 외부 도구 부재 시 해당 위치에서 멈춘다. 완료를 선언하지 않는다.
5. 승인 대기와 기술 실패를 구별한다. 승인이 필요한 단계는 산출물과 질문을 제시하고, 실패는 로그·원인·복구안을 남긴다.
6. 재개 시 작업 트리·브랜치·입력 버전을 다시 확인한다. 유효한 이전 승인까지 반복해서 묻지 않되 범위가 달라졌다면 변경분을 확인한다.

```text
TDD 실행 원장
이슈 / 승인 AC / 기획 승인 근거:
base / head / 대상 버전 / 변경 허용 파일:
단계 0-7 각각: 상태, 입력, 산출물 경로, 명령, 종료 코드, 증거
상태 값: 준비 / 실행 / 승인 대기 / 실패 / 통과 / 미실행
마지막 통과 단계 / 현재 실패·대기 단계:
승인자 / 승인 범위 / 변경된 전제:
PR 생성 여부 / feature 머지 여부 / main 머지는 별도:
복구 작업 / 재개 조건 / 재검증 필요 범위:
```

## tdd-auto-loop의 자체 승인과 객관 STOP

### 컨테이너와 다른 점

`/tdd-auto-loop`를 순서뿐 아니라 의사결정까지 자동화하는 자율 루프로 정의한다. 각 단계는 격리된 subagent가 실행하고 종료 시 컨텍스트를 해제한다. 메인은 코드 본문 대신 결과 JSON을 누적·검사한다. 명시적으로 위임된 구현 범위 안의 하위 승인 게이트만 자체 판정하며, Green 직후 별도 `ac-verifier`가 검증한다.

STOP은 “계속할까요?”라고 세션을 매달아 두는 방식이 아니다. 사유 로그를 남기고, 외부 쓰기가 승인된 경우에만 이슈 코멘트를 게시한 뒤 종료한다. 이후 사용자가 보강하여 재실행한다. 자동 실행 후 사람의 역할은 **PR 리뷰 한 번**이다. 자동 실행의 종료점은 PR 준비 또는 승인된 생성까지이며 main 머지는 별도 승인이다.

### 필수 STOP 조건 전체

다음은 자동 모드의 필수 STOP 조건이다. 임의로 완화하지 않는다.

| 단계                | 필수 STOP 조건                      | 남길 근거와 복구                                                                         |
| ------------------- | ----------------------------------- | ---------------------------------------------------------------------------------------- |
| 0 사전 점검         | AC 누락 / uncommitted / 잘못된 base | 누락 AC, 작업 트리 상태, 기대·실제 base; 다른 사람 변경을 커밋·삭제해 조건을 맞추지 않음 |
| 1 시나리오          | 시나리오 5개 미만 / 경계값 누락     | 사례 목록과 AC 대응; 중복 사례로 숫자만 채우지 않고 승인 범위에서 보강                   |
| 2 Red               | 잘못된 이유로 실패(import 에러)     | 실제 stderr와 예상 실패 차이; 러너·경로를 수정하고 Red 증거 재수집                       |
| 3 Green (×3)        | 3회 실패 / 테스트 수정 시도         | 시도별 diff·실패 로그, 테스트 변경 감지; 네 번째 자동 시도 금지                          |
| 4 AC 검증           | `ac_passed=false`                   | AC별 미충족 증거; 기준 완화 대신 입력·구현 보강 후 새 실행                               |
| 5 Refactor          | `npm test` 미통과                   | 동작 회귀 위치; 해당 실행의 변경만 검토해 복구                                           |
| 6 Security + 재스캔 | 재스캔 후 high 이상                 | scanner·대상·결과와 잔여 심각도; 수정 후 재검사, 무근거 면제 금지                        |
| 7 PR 생성           | commitlint 실패                     | 메시지 규칙과 실제 오류; 훅 우회 금지, 통과 시 PR URL 기록                               |

Green 실행 시도를 1–3으로 기록하며 세 번째 실패 후 네 번째 자동 시도는 금지한다. 시나리오 수 5개는 사례의 질을 대신하지 않는다. 각 결과의 버전·증거·상태를 함께 검증한다.

CI에서 `moderate` 이상 감사를 차단하도록 구성했다면 자동 모드 재스캔의 `high 이상` STOP과 별도 게이트다. high가 없다는 이유로 moderate CI 실패를 통과로 바꾸지 않는다.

### 자동 승인에 대한 필수 제한

프로젝트 지침과 위임 범위가 우선한다:

- 자체 승인을 그대로 전역 권한으로 해석하지 않는다. 요구사항·아키텍처·범위·이슈 목록의 사용자 승인 경계는 유지한다.
- 후속 사용자가 자율 실행을 명시적으로 위임한 경우에만, 이미 승인한 입력 안의 가역적 구현·검증 판단을 자체 처리하는 후보가 된다. 위임 범위 밖의 새 의존성·요구사항 변경·데이터 삭제·외부 전송은 기술 성공 여부와 별개다.
- 커밋·push·PR·이슈 코멘트·머지를 묶어 승인된 것으로 추정하지 않는다. 외부 코멘트가 금지/미승인이면 STOP 보고를 로컬 산출물로 남기며, 코멘트를 게시했다고 쓰지 않는다.
- 실제 subagent 실행 도구와 격리 범위를 실행 시 확인한다. 문서에 역할을 나눴다고 컨텍스트/파일시스템 격리가 구현되었다고 보고하지 않는다. 불가능하면 수동 인계 또는 명시된 대체 검증으로 기록한다.
- 메인은 단계별 결과 JSON의 필수 필드, 증거 경로, 코드 버전 일치, 실제 테스트 결과를 검증한다. 생성자가 적은 `passed=true`만으로 성공 판정하지 않는다. 코드 직접 검토가 필요하면 추가 검토 범위를 기록한다.
- AC 검증은 구현자와 분리하고 승인 AC를 수정할 수 없도록 한다. Refactor 이후 동작/계약이 바뀌었다면 기존 Green 직후 AC 검증만으로 종료하지 않는다.
- 인프라 부재, 권한 범위 초과, 증거 누락, 결과 파싱 실패, 사용자 중단은 실행 안전 STOP이다.

### 재사용 절차와 결과 JSON 템플릿

입력: 승인 이슈·AC, 자율 위임 범위, 실행 환경, base/head, 하위 단계 계약, 검사 도구, 반복 예산, 외부 작업 허용 여부.

1. 사전 점검 결과와 허용 작업을 고정한다. 앱 부재·미승인 구현이면 실행하지 않는다.
2. 단계별 담당자에게 필요한 입력과 허용 파일만 전달한다. 같은 파일을 병렬 수정하도록 무작정 배분하지 않는다.
3. 단계 종료 결과를 구조화해 수집한다. 이전 단계 통과 근거와 다음 입력을 연결한다.
4. 필수 STOP 및 실행 안전 STOP을 분리해서 검사한다. STOP이면 후속 단계와 외부 작업을 수행하지 않는다.
5. Green은 제한 횟수 내에서만 시도하고 별도 AC 검증을 호출한다. 보안 수정 뒤 재스캔과 관련 회귀 검사를 한다.
6. 모두 통과해도 외부 생성 권한이 없으면 PR 초안과 증거만 인계한다. 권한이 있을 때만 실제 PR URL로 생성 결과를 증명한다.
7. 사람의 PR 리뷰와 별도 머지 조건을 남긴다. 재실행은 사용자가 입력을 보강하거나 원인이 해결된 뒤 새 상태 점검부터 시작한다.

다음 결과 JSON 템플릿에 실행 단계와 증거를 기록한다. `ac_passed`는 독립 검증 결과이며 누락·파싱 실패를 true로 간주하지 않는다.

```json
{
  "issue": "<approved-issue>",
  "stage": "ac-verification",
  "status": "stopped",
  "base": "<approved-base>",
  "head": "<issue-branch>",
  "revision": "<verified-revision>",
  "attempt": 1,
  "ac_passed": false,
  "evidence": ["<local-log-or-report-path>"],
  "stop_source": "harness-auto-loop",
  "stop_reason": "<unmet-AC-and-observed-result>",
  "changed_files": [],
  "external_actions_performed": [],
  "resume_condition": "<required-correction-and-verification>"
}
```

```text
STOP 보고
실행 ID / 이슈 / 대상 버전:
중단 단계 / 필수 STOP 또는 실행 안전 STOP:
조건의 기대값 / 실제값 / 로그·증거 경로:
완료 단계 / 미실행 단계 / 변경 파일:
시도 횟수 / 잔여 위험 / 데이터 정리 상태:
외부 변경: 없음 또는 승인 근거와 실제 결과
다음 사람이 보강할 입력 / 재실행 전 확인사항:
```

## 실행 스킬과 검증 명령

실제 등록·호출 여부는 런타임과 등록 목록에서 확인한다. 스킬 이름은 독립 에이전트·파일시스템 격리가 자동 제공된다는 뜻이 아니다.

| 스킬·역할                          | 필수 계약                                                        |
| ---------------------------------- | ---------------------------------------------------------------- |
| `e2e-write`                        | PRD 여정, locator, 데이터 격리, 실행·보고서·정리                 |
| `create-pr`                        | 초안 승인, E2E 실패 차단, 승인된 push/PR, base/head·CI·머지 구분 |
| `tdd-loop`                         | 사전 점검+7단계, 하위 승인 유지, 실패 위치와 재개                |
| `tdd-auto-loop`                    | 격리 단계, 결과 JSON, 필수·안전 STOP, 독립 AC, PR 리뷰           |
| `test-scenarios`                   | 시그니처·시나리오 승인, 자동 모드의 최소 5개·경계값              |
| `tdd-red` / `tdd-green`            | 올바른 실패 증거, 최소 구현·회귀, 자동 모드 최대 3회·테스트 동결 |
| `ac-verifier`                      | 구현자와 분리한 AC 검증과 `ac_passed` 근거                       |
| `tdd-refactor` / `security-review` | 동작 보존·회귀, 보안 수정·재스캔·잔여 위험                       |
| `feature-planner`                  | 앞단 기획·네 승인 게이트, [상세 기획 계약](planning.md)          |

명령은 실제 설치 버전·도움말·프로젝트 scripts로 먼저 확인한다. 아래 예시는 실행 권한을 부여하지 않는다.

| 명령·구성                                                          | 실행 전 확인                                  |
| ------------------------------------------------------------------ | --------------------------------------------- |
| `npx playwright test`, `--headed`                                  | 로컬 러너·브라우저·서버·실행 URL              |
| `npm run test:e2e`                                                 | script 존재와 실제 포함 범위                  |
| `npx playwright show-report`                                       | HTML 보고서 존재; trace 준비·열기는 별도 확인 |
| `webServer`, role/text/placeholder/testid locator                  | 실제 접근성 이름·중복·설치 버전 API           |
| `npm ci`, `npm run lint`                                           | 잠금 파일·런타임·실제 lint 범위               |
| `npx tsc --noEmit`, `npm audit --audit-level=moderate`, `npm test` | 타입 구성·감사 정책·테스트 층                 |
| `gh pr create --base "$BASE" --head "$HEAD" --title "$TITLE"`      | 인증·저장소·대상·외부 생성 승인               |
| `gh pr merge "$PR" --merge`                                        | 정확한 PR·리뷰·보호·CI·별도 머지 승인         |
| `gh issue create`                                                  | 외부 이슈 생성 요청과 중복 여부               |

## 최종 점검

- 요구사항·아키텍처·범위·이슈 목록 승인과 유한한 실행 대상·반복 상한이 있는가?
- 앱과 러너·명령을 실제 확인하고 단위·통합·E2E·로컬 품질·원격 CI를 구분했는가?
- Red가 올바른 이유로 실패하고 Green의 테스트 동결과 독립 AC 검증을 지켰는가?
- Refactor 후 회귀, 보안 수정 후 재스캔, E2E 데이터 정리 증거가 있는가?
- 대화형 승인 대기와 자동 모드 STOP 종료를 혼동하지 않았는가?
- 이슈 PR·기능 통합·main 머지·배포·사람 수락을 별도로 보고했는가?
- PR 승인·검사 성공·외부 작업·리뷰·머지 승인 및 head 일치가 확인됐는가?
- 보호 문서와 다른 작업자의 변경을 보존하고 미실행·실패·재개 조건을 명시했는가?
