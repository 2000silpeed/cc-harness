# 디자인 시스템 작성과 검사

새 기준을 만들 때 [문서 작성 방법론·템플릿·검토 기준](../design-system/authoring-guide.md)을 함께 사용한다. 화면 정의 → 공통 기준 → 재사용 스킬 → 자동 검사로 연결한다.

이 문서의 구조도 경로·npm 명령·검사 종료 코드·훅 동작은 원본 하네스의 구성 사례다. 이식 스크립트는 해당 화면·검사기·package·훅을 복사하지 않는다. 새 제품에서는 승인된 화면과 실제 런타임에 맞게 구성한 뒤 아래 절차를 적용한다. 특히 이벤트 이름과 도구 매칭은 현재 설치된 Codex에서 지원 여부를 확인한다.

이미지만 주면 구현마다 색상·간격·폰트가 달라질 수 있다. design.md는 화면 구성과 상태를 텍스트로 고정하고, 공통 규칙은 colors·typography·spacing·components로 분리한다. 스킬은 작업 전에 읽을 절차, 훅은 작업 후 기준 이탈을 알리는 장치다. 기능 테스트와 디자인 검사는 역할이 다르며, 어느 한쪽이 다른 쪽을 대체하지 않는다.

## 파일별 역할 — 없으면 어떻게 되는가?

| 파일                                    | 역할 / 없을 때                                                         |
| --------------------------------------- | ---------------------------------------------------------------------- |
| `docs/architecture/design.md`           | 이 화면의 구성·출처·범위. 없으면 공통 규칙만 있고 화면별 의도가 사라짐 |
| `docs/design-system/colors.md`          | 색상과 테두리의 허용 값. 없으면 색상 기준을 읽거나 검사할 수 없음      |
| `docs/design-system/typography.md`      | 글꼴·크기·굵기·행간. 없으면 텍스트 스타일이 제각각이 됨                |
| `docs/design-system/spacing.md`         | 간격·너비·배치 값. 없으면 레이아웃 수치를 매번 추정함                  |
| `docs/design-system/components.md`      | 구성·상태·접근성 기준. 없으면 상태별 표현을 빠뜨리기 쉬움              |
| `.agents/skills/design-system/SKILL.md` | Codex의 작업 절차. 없으면 매번 읽을 문서와 검증 순서를 설명해야 함     |
| `scripts/check-design-system.mjs`       | CSS 선언을 문서의 JSON 기준과 비교. 없으면 자동 판정이 없음            |
| `.codex/hooks.json`                     | 도구 실행 후 검사 연결. 없으면 수동 명령이나 통합 검사 때만 발견       |
| `AGENTS.md`                             | 프로젝트에서 스킬·기준을 찾아갈 안내                                   |
| `package.json`                          | design:check 및 기존 통합 검사에 실행 명령 연결                        |

## 검사 연결과 신뢰

프로젝트 훅은 `.codex/hooks.json`에서 관리한다. 실행 시점의 로컬 런타임에서 이벤트·도구 매칭과 신뢰 상태를 확인한다. 프로젝트 신뢰와 훅 정의 승인은 별개이며 설정 파일 작성만으로 활성화를 보고하지 않는다.

## 사용하는 순서

1. 프로젝트 루트에서 `npm run design:check`를 실행한다.
2. Codex에서 `$design-system 구조도 화면의 디자인 기준을 점검해줘`라고 요청한다.
3. 새 Codex CLI 세션을 이 프로젝트에서 시작하고 `/hooks`를 연다. 프로젝트 훅의 실행 명령과 스크립트를 검토한 뒤 신뢰를 승인한다. 프로젝트 자체가 미신뢰라면 먼저 프로젝트 신뢰 상태를 확인한다.
4. 이후 apply_patch 또는 Bash 도구 실행이 끝나면 구조도 전체 스타일을 검사한다. 읽기 명령 뒤에도 실행되지만 파일을 수정하지 않는 가벼운 검사다.
5. 위반이 나오면 변경 의도와 문서를 비교해 수정한다. 훅은 변경을 되돌리거나 디자인을 자동으로 고치지 않는다. 검사기 위반은 수동 실행에서 exit 1, 훅 모드에서 exit 2로 전달된다.
6. 마무리는 `npm run check`. 실제 포함 검사는 package.json에서 확인하고 원격 CI와 구분한다.

이 작업에서는 사용자 훅 신뢰를 대신 승인하거나 우회하지 않는다. 따라서 **설정·검사기 검증과 실제 Codex 이벤트 발화 검증은 별개**이며, 후자는 신뢰 승인 후 확인해야 한다. 수동 검사는 승인 전에도 실행 가능하다.

## 검사기가 보장하는 것과 한계

- 색상·타이포그래피·간격 문서의 첫 JSON 블록이 허용 값의 단일 기준이다. 검사 코드에 동일한 값을 복제하지 않는다.
- 기본 대상은 `docs/architecture/index.html`의 모든 정적 style 블록. CSS 속성과 정규화된 값이 허용 목록에 있는지 확인한다.
- 기준 파일 누락·형식 오류·중복 속성·style 부재·인라인 style 속성·외부 스타일시트 연결은 오류로 처리한다.
- CSS 파서나 보안 경계가 아닌, 현재 단순 CSS에 맞춘 제한적 검사다. 선택자·미디어쿼리·값의 의미상 조합·동적 JavaScript 삽입·Mermaid 생성 SVG·CSS 전체 문법은 검증하지 않는다.
- 허용된 24px을 엉뚱한 선택자에 써도 통과할 수 있다. 새 화면·CSS 구문·외부 파일은 검사 범위를 확장하고 실제 브라우저에서 확인한다.
- 실패를 없애려고 허용 목록만 늘리지 않는다. 의도한 디자인 변경이면 근거와 해당 화면을 함께 갱신한다.

## 재사용 프롬프트

```text
$design-system
기존 인터뷰와 승인 상태는 그대로 둬.
대상 화면의 design.md와 공통 디자인 기준을 읽고 변경 범위를 설명해.
기준을 재사용해서 요청한 부분만 변경하고 design:check를 실행해.
화면을 바꾸면 좁은 화면·상태·키보드 포커스를 확인하고,
정적 검사 결과와 실제 화면 확인 결과를 따로 보고해.
```

## 검증 기록

검증 결과는 설정 작업의 최종 보고와 함께 확인한다. 재현 명령:

```sh
npm run design:check
node scripts/check-design-system.mjs --hook
npm run check
```

신뢰 승인 뒤 실제 도구 호출에서 훅 상태 메시지가 나오는지 별도로 확인한다. 정적 검사만으로 대상 앱의 디자인 승인, 이미지 기반 시안 추출, 앱 구현 또는 시각 회귀 검증까지 완료했다고 보고하지 않는다.

## 화면별 범위 선택

루트 `docs/design-system/`은 구조도 기준이다. 앱 화면에는 대상 기능의 `AGENTS.md`, `design.md`, `design-system/`을 먼저 적용한다. 기존 화면 CSS에서 기준을 추출한 것과 새 참고 이미지에서 시안을 만든 것을 구분한다. 새 화면·상태·반응형 크기·키보드 포커스를 실제 브라우저에서 검토하며, 기존 인터뷰와 디자인 승인 상태를 임의 변경하지 않는다.
