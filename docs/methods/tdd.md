# TDD: 이슈 하나를 검증된 코드로 바꾸기

이 문서는 승인된 이슈 하나를 검증된 코드로 바꾸는 절차를 설명합니다. 계약·시나리오 → Red → Green → 독립 인수 조건(AC) 검증 → Refactor → 보안 검토 순서로 구현합니다. 인수 조건은 기능이 요구대로 완성됐는지 판단하는 조건입니다. 특정 언어나 테스트 실행기를 강제하지 않으며 실제 프로젝트의 도구와 승인 범위를 따릅니다. 자동 모드의 추가 중단(STOP) 조건은 [전달·자동화](delivery-automation.md)에 정의합니다.

## 계약과 시나리오를 먼저

입력은 승인된 제품 요구사항 문서(PRD), 이슈 AC, 기존 코드와 테스트 방식입니다. 출력은 `docs/features/{feature}/tests/{issue}-scenarios.md`입니다.

1. 이슈에서 사용자가 관찰할 수 있는 결과와 선행 의존성을 읽습니다.
2. 함수·API의 이름, 입력·출력 타입, 동기·비동기 여부, 오류 계약을 먼저 고정합니다. 이 단계에서는 구현 코드를 작성하지 않습니다.
3. AC마다 정상, 경계, 예외 사례를 도출합니다. 최솟값과 최댓값의 직전·정확한 경계·직후, 빈 값, 중복, 실패 가운데 대상 영역에 맞는 사례를 선택합니다.
4. `should [결과] when [조건]` 형식의 이름과 Given–When–Then을 적고 AC ID를 연결합니다.
5. 인터페이스와 시나리오를 사용자가 검토한 뒤 Red로 넘어갑니다. 정하지 않은 동작을 AI가 스스로 확정하지 않습니다.

```markdown
# 이슈 [ID] 시나리오

- 근거 PRD·AC·대상 코드:
- 계약: 함수/API, 입력, 출력, 오류, 부작용
- 검토 상태·사용자 결정 근거:

| ID  | AC  | 분류 | Given | When | Then | 테스트 층 | 격리할 의존성 |
| --- | --- | ---- | ----- | ---- | ---- | --------- | ------------- |

## 미정·제외

## 실행할 테스트 명령
```

AI가 구현과 기대값을 동시에 조정하면 잘못된 동작도 테스트를 통과할 수 있습니다. 따라서 테스트 통과와 요구사항 충족을 따로 판단합니다. 테스트하기 쉽도록 만들라는 원칙은 외부 의존성을 경계에서 분리할 단서이며, 추상화를 무조건 늘리라는 뜻은 아닙니다.

## Red는 실패 종류를 증명하는 단계

입력은 검토된 계약과 시나리오입니다. 출력은 테스트 코드, 필요한 최소 스텁(stub), 실제 실패 로그입니다.

1. 기존 테스트 실행기를 사용합니다. 실행기가 없다면 설치, 스크립트, 테스트 위치를 준비하는 작업을 먼저 별도로 구분합니다.
2. 시나리오를 테스트 이름과 검증문(assertion)으로 옮깁니다. 사용자 인터페이스(UI)는 내부 상태보다 사용자가 보는 텍스트, 역할, 동작을 검증합니다.
3. 모듈을 불러오기 위해 필요하다면 계약을 그대로 드러내는 최소 스텁만 추가합니다. 비즈니스 동작은 구현하지 않습니다.
4. 테스트가 정상적으로 수집·실행되고, 기대 동작을 아직 구현하지 않았기 때문에 실패하는지 확인합니다.
5. 문법, import, 환경, 연결 오류는 비정상 실패(Broken)로 분류해 먼저 해결합니다. 대상 테스트 수와 실패 이유를 기록합니다.

기존 코드가 이미 필요한 동작을 제공한다면 테스트가 처음부터 통과할 수 있습니다. 억지로 실패를 만들거나 기존 동작을 훼손하지 말고, 현재 동작을 기록하는 특성화 테스트인지 새로 구현할 동작인지 판별합니다. 일부 예외 테스트는 스텁의 일반 오류만으로 통과할 수 있으므로 오류 종류, 메시지, 상태까지 계약과 맞는지 검토합니다. 신규 테스트의 실패 수와 기존 회귀 테스트의 통과 수를 나누어 기록하며, 전체 저장소를 일부러 실패시키지 않습니다.

## Green은 테스트를 바꾸지 않는 최소 구현

1. 실제 Red 증거를 확인하고 해결할 실패 하나를 선택합니다.
2. 그 기대 동작에 필요한 코드만 추가합니다. 새로운 편의 기능, 미래 확장, 불필요한 추상화는 추가하지 않습니다.
3. UI라면 design.md와 공통 디자인 기준을 함께 적용합니다. 동작 테스트 통과가 외형의 일치까지 보증하지는 않습니다.
4. 관련 테스트를 실행하고 기존에 통과하던 테스트가 깨지지 않았는지 확인합니다. 작은 저장소에서는 전체 테스트를 매번 실행하고, 큰 저장소에서는 관련 회귀 묶음을 반복한 뒤 단계가 끝날 때 전체 검사를 실행합니다. 프로젝트에 반복 검사 정책이 있다면 그 주기와 종료 검사를 따릅니다.
5. 남은 실패를 차례로 줄입니다. 검증문 삭제, 테스트 건너뛰기(skip), 기대값 완화, 계약 변경으로 통과 상태를 만들지 않습니다.
6. 코드 실행 범위(coverage)가 설정되어 있다면 실행되지 않은 분기를 누락된 시나리오의 후보로 검토합니다. 수치만 높이기 위한 의미 없는 테스트는 추가하지 않습니다.
7. 별도의 AC 검증자가 승인된 이슈와 구현·증거를 비교합니다. 빠진 AC가 발견되면 시나리오와 Red 단계로 돌아갑니다.

코드 실행 범위(Coverage)는 함수(Function), 문장(Statement), 분기(Branch), 줄(Line)을 구분하고 `if`의 반대 경로처럼 빠뜨리기 쉬운 분기를 살핍니다. V8 등 실제 계측 도구의 결과를 사용합니다. 도구마다 집계 방식이 다르므로 분기 100%가 모든 환경의 다른 지표나 제품 정확성까지 보장한다고 일반화하지 않습니다. 실행된 코드의 비율과 의미 있는 결과를 검증했다는 사실은 서로 다릅니다.

### AC 검증 기록

```markdown
# AC 검증 — 이슈 [ID]

- 검토 대상 변경·버전:
- 검증자: 독립 에이전트 / 동일 에이전트 재검토
  | AC  | 구현 근거 | 실행·관찰 근거 | 판정 | 누락·다음 행동 |
  | --- | --------- | -------------- | ---- | -------------- |
- 판정: pass / fail / unverified
```

AC 검증자는 절차를 반복 실행하는 스킬과 구별되는 판단 역할입니다. `ac-verifier` 스킬의 계약에 따라 구현자와 다른 검증자가 검토하게 합니다. 독립 실행 도구가 없다면 같은 에이전트가 다시 검토했다는 사실을 명시하고, 독립 검증이 끝났다고 보고하지 않습니다.

## Refactor와 보안은 다른 검사

### Refactor

전제는 Green과 AC 검증이 여전히 유효하다는 것입니다. 중복, 이름의 명확성, 단일 책임, 불필요한 복잡도, AGENTS 규칙의 다섯 기준으로 검토합니다. 작은 변경 하나를 마칠 때마다 관련 테스트를 실행합니다. 실패하면 **자신의 마지막 변경만** 되돌리거나 수정하며, 사용자의 변경을 reset이나 checkout으로 지우지 않습니다. 새 기능이나 동작을 바꾸는 버그 수정은 별도의 Red가 필요한 변경으로 다룹니다. 개선할 필요가 없다면 억지로 리팩터링하지 않습니다.

### 보안·품질

1. 동작 테스트와 별도로 대상 기술 스택의 타입 검사를 실행합니다. TypeScript가 없다면 tsc를 설치하지 않고 해당 없음으로 기록합니다.
2. 사용 중인 패키지 관리자의 의존성 검사를 확인합니다. 네트워크 감사는 패키지 정보를 외부로 보내므로 대상 정책에 맞게 실행합니다.
3. 입력 검증, 인증, 권한, 출력 처리, 민감정보, 환경변수, 로그, 설정 변경을 실제 변경 범위 안에서 검토합니다.
4. 발견한 항목마다 영향, 근거, 심각도, 도달 가능성, 수정안, 결정자를 남깁니다. 즉시 조치, 권장 조치, 근거가 있는 예외를 구분합니다.
5. `audit fix --force` 같은 강제 업데이트는 실행하지 않습니다. 수정한 뒤 테스트와 필요한 검사를 다시 수행합니다.

심각도가 낮다고 자동으로 무시하지 않습니다. 개발 의존성도 빌드 환경에 영향을 줄 수 있습니다. 실제로 노출된 비밀 값은 로그에 다시 출력하지 않고 교체나 폐기 같은 조치를 사용자에게 알립니다. 타입 검사와 감사가 모두 통과해도 제품 전체가 안전하다는 뜻은 아닙니다.

```markdown
# 보안·품질 검토 — 이슈 [ID]

| 항목 | 근거 | 영향·심각도 | 조치 또는 예외 이유 | 책임자·재검토 | 결과 |
| ---- | ---- | ----------- | ------------------- | ------------- | ---- |

- 실행 명령·작업 경로·종료 코드·증거:
- 미실행 검사와 이유:
- 머지 차단 항목:
```

## 이슈마다 같은 사이클

각 이슈에서 `test-scenarios → tdd-red → tdd-green → ac-verifier → tdd-refactor → security-review → 승인된 이슈 PR`을 의존성 순서로 반복합니다. 기능 전체 E2E와 main 병합은 준비된 모든 수직 조각이 통합된 뒤 별도로 수행합니다. 이슈 완료를 main 배포 완료와 혼동하지 않습니다.

이슈마다 시나리오, 테스트, 검증, PR 증거를 연결해 다음 작업으로 인계합니다. `feature/<feature>` 같은 브랜치 이름과 이슈 번호는 대상에 맞게 정합니다. 실제 저장소, 기준 브랜치(base), 작업 브랜치(head), 승인 범위를 확인합니다. 커밋, 브랜치 생성, PR, 이슈 종료는 해당 작업에 대한 별도 요청이나 명시적인 사전 승인 범위 안에서만 수행합니다.
