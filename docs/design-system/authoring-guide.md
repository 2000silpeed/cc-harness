# 디자인 시스템 작성 방법 — 새 프로젝트에 재사용하기

이 문서는 새 프로젝트에서 화면 정의 → 공통 기준 → 스킬 → 검사·훅 순서로 디자인 시스템을 만드는 실무 방법을 제공합니다. 템플릿과 판단 기준은 대상의 실제 자료, 기술 환경, 승인 범위에 맞게 적용합니다.

## 1. 무엇을 재사용하는가

재사용할 대상은 **작성·검토·검사 절차**입니다. 이 저장소의 어두운 색상과 구조도 화면을 새 제품의 디자인 기준으로 그대로 복사해서는 안 됩니다.

| 재사용 가능                                 | 대상 프로젝트에 맞게 다시 결정                 |
| ------------------------------------------- | ---------------------------------------------- |
| 이 가이드, 스킬의 작업 순서, 승인·검증 원칙 | 제품 목적·사용자·화면·상태                     |
| 문서의 항목과 표 구조                       | 색상·폰트·간격·컴포넌트 값                     |
| 읽기 전용 검사 → 피드백이라는 연결 방식     | 검사 파일 범위·CSS 방식·도구 명칭·실행 환경    |
| 기존 품질 도구 활용 원칙                    | 대상 프로젝트에 이미 있는 npm 명령·훅과의 병합 |

처음부터 모든 파일을 복사하지 않습니다. 대상 저장소의 지침과 기존 디자인 시스템을 먼저 확인하고, 이미 있는 문서를 재사용하거나 필요한 부분만 보완합니다. 기존 설정을 통째로 덮어쓰지 않습니다.

## 2. 시작 전에 받을 자료

| 입력      | 확인할 내용                                  | 없을 때                                          |
| --------- | -------------------------------------------- | ------------------------------------------------ |
| 기능 정의 | 사용자·목적·주요 작업·범위                   | 기능을 임의로 확정하지 말고 필요한 질문 하나     |
| 참고 화면 | Figma 프레임, 이미지 파일, 기존 구현 경로    | 기존 코드 기준으로 할지, 새 시안을 정할지 확인   |
| 화면 상태 | 기본·빈 결과·로딩·오류·비활성 등             | 이미지에 없다는 이유로 없는 상태로 단정하지 않음 |
| 기술 환경 | 일반 CSS, CSS modules, Tailwind 등 실제 설정 | 프레임워크를 임의 설치하지 않고 조사             |
| 제약      | 브라우저·화면 크기·접근성·브랜드·다국어      | 필요한 것만 질문하고 나머지는 미정으로 기록      |

외부 업로드나 계정 연결 없이 접근할 수 있는 자료부터 사용합니다. 참고 화면이 승인된 디자인인지, 단순한 취향 예시인지도 구분합니다.

### 관찰과 제안을 구분하는 기록

| 항목                   | 관찰 값   | 출처                       | 확실성        | 결정 상태                    |
| ---------------------- | --------- | -------------------------- | ------------- | ---------------------------- |
| 예: 카드 내부 여백     | 24px      | 기존 CSS의 section padding | 코드에서 확인 | 현행 값, 새 제품 채택은 미정 |
| 예: 이미지의 본문 폰트 | 식별 불가 | reference.png의 본문       | 불확실        | 폰트 후보 제안 필요          |

스크린샷의 색상과 치수는 압축, 배율, 렌더링 때문에 추정값일 수 있습니다. 정확한 스타일 값이 있다면 그 근거를 먼저 확인합니다. 자료가 서로 다르면 새 값으로 조용히 통일하지 말고 차이와 선택 이유를 남깁니다.

## 3. 작성 순서와 승인 지점

1. 자료 조사 → 출처와 미정 항목 목록 작성.
2. 화면별 design.md 초안 → 화면 구성·상태·반응형을 구체화.
3. 공통 값 후보 추출 → colors·typography·spacing 작성.
4. 반복 UI의 구조·상태 정리 → components 작성.
5. 화면 문서의 중복 값을 공통 기준 참조로 바꾸고 양쪽 일치 확인.
6. 미정 항목 중 구현에 영향을 주는 결정만 사용자에게 확인. 이미 확정된 인터뷰는 반복하지 않음.
7. 확정된 기준을 사용하는 스킬과 검사기를 대상 환경에 연결.
8. 정상·위반 사례 검사 → 실제 화면 확인 → README와 흐름 화면에 현재 상태 반영.

처음부터 모든 공통 규칙을 정할 필요는 없습니다. 화면 하나에서 시작할 수 있지만, 한 화면에서 우연히 사용한 값을 곧바로 제품 전체의 표준으로 선언해서는 안 됩니다. 문서 작성 완료, 디자인 승인, 구현 완료, 검증 완료는 서로 다른 상태입니다.

## 4. design.md — 화면을 재현할 수 있는 명세

### 만드는 방법

1. 화면을 큰 영역부터 나눈다: 헤더, 탐색, 본문, 보조 영역 등 실제 있는 것만.
2. 영역의 순서·정렬·너비·스크롤 소유자를 기록합니다.
3. 각 영역에서 사용하는 컴포넌트와 사용자 동작을 연결합니다.
4. 기본 상태 외에 긴 텍스트·빈 데이터·로딩·실패·비활성 상태의 화면 변화를 정의합니다.
5. 화면 폭이 줄 때 무엇이 접히고 줄바꿈되고 스크롤되는지 적습니다. 이미지 한 장에서 모바일 동작을 확정하지 않습니다.
6. 공통 수치는 해당 공통 문서의 이름을 참조합니다. 화면 고유의 예외만 이곳에 둡니다.

### 작성 템플릿

```markdown
# [화면명] 디자인 정의

## 상태·범위

- 상태: 초안 / 검토 중 / 승인됨
- 연결 요구사항: [경로와 항목]
- 적용 화면·제외 범위: [...]
- 출처: [파일·프레임·코드 경로, 확인 일자]
- 관찰 사실 / 제안 / 미정: [분리해서 기록]

## 화면 구성

| 영역 | 내용·사용자 동작 | 배치·스크롤 | 공통 기준 참조 |
| ---- | ---------------- | ----------- | -------------- |

## 상태

| 발생 조건 | 보여줄 내용 | 가능한 동작·복구 | 상태 전달 방식 |
| --------- | ----------- | ---------------- | -------------- |

## 반응형·접근성

- 좁은 화면에서 바뀌는 배치와 기준 폭:
- 긴 문구·확대·키보드·포커스 처리:

## 구현 연결

- 대상 파일·선택자 또는 컴포넌트:
- 실제 스타일 방식과 토큰 연결:
- 예외와 이유:

## 확인 항목

- [ ] 기본·빈 데이터·오류 등 필요한 상태가 빠지지 않음
- [ ] 넓은 화면과 좁은 화면에서 읽고 조작 가능
- [ ] 미정 항목을 구현 완료로 표기하지 않음
```

일반적인 경로는 `docs/features/[feature]/design.md`입니다. 현재 저장소의 `docs/architecture/design.md`는 문서 화면에 적용한 사례입니다. Tailwind를 사용한다면 실제 클래스와 토큰을 연결하고, 사용하지 않는다면 CSS 속성과 선택자로 적습니다.

## 5. colors.md — 색을 역할로 정의

### 만드는 방법

1. 참고 자료의 색을 수집하고 배경·본문·테두리·강조·상태 역할로 분류합니다.
2. 같은 값이라도 역할이 다르면 역할 이름을 분리할지 검토합니다. 값이 비슷하다고 자동 병합하지 않습니다.
3. 글자색은 배경과 한 쌍으로 검토합니다. 성공·오류는 색 외에 문구나 아이콘도 정합니다.
4. hover·focus·disabled 등 필요한 상태의 색을 매핑합니다. 없는 상태는 제안 또는 해당 없음으로 표시합니다.
5. 실제 스타일 토큰 또는 CSS 값과 연결합니다. 접근성 목표는 대상 프로젝트에서 정하고 실제 대비 검사 결과를 별도로 남깁니다.

### 작성 템플릿

```markdown
# 색상

- 출처·적용 테마·승인 상태:

| 역할 이름 | 값 또는 토큰 | 쓰는 곳 | 배경·전경 조합 | 출처·상태 |
| --------- | ------------ | ------- | -------------- | --------- |

## 상태별 매핑

| 요소·상태 | 배경 | 글자 | 테두리 | 색 외 전달 방식 |
| --------- | ---- | ---- | ------ | --------------- |

## 사용 금지·예외

- 임의 색 추가, 상태를 색으로만 전달하는 사용 등 대상별 규칙:

## 검증

- 대비 검사 대상·방법·결과 / 미검증:
```

완료 기준은 구현자가 회색을 임의로 고르지 않고 역할에 맞는 색을 찾을 수 있으며, 실제 사용 값마다 출처가 있는 상태입니다.

## 6. typography.md — 글자의 정보 위계를 정의

### 만드는 방법

1. 제목, 본문, 설명, 라벨, 코드 등 실제 텍스트 역할을 나눕니다.
2. 글꼴, 대체 글꼴, 크기, 굵기, 행간, 자간을 역할별로 묶습니다.
3. 한글·영문·숫자·긴 제목에서 읽히는지 확인합니다. 폰트 파일이 없는 상태에서 특정 폰트가 표시된다고 주장하지 않습니다.
4. 줄바꿈·말줄임·최대 줄 수와 전체 내용 접근 방법을 정합니다.
5. 반응형 크기와 확대 시 동작을 연결합니다. 시스템 폰트라면 별도 다운로드가 필요 없음을 명시합니다.

### 작성 템플릿

```markdown
# 타이포그래피

- 글꼴 출처·로드 방식·대체 글꼴:

| 역할 | font-family | 크기 | 굵기 | 행간 | 자간 | 적용 위치 |
| ---- | ----------- | ---- | ---- | ---- | ---- | --------- |

## 줄바꿈·반응형

| 텍스트 종류 | 긴 내용 처리 | 좁은 화면 처리 | 전체 내용 확인 |
| ----------- | ------------ | -------------- | -------------- |

## 검증

- 한글·영문·숫자·긴 문장·확대 확인 결과:
```

완료 기준은 같은 역할의 텍스트 규칙을 화면마다 다시 정할 필요가 없고, 글꼴을 불러오지 못했을 때 사용할 대체 경로가 있는 상태입니다.

## 7. spacing.md — 간격과 배치의 반복 규칙

### 만드는 방법

1. 요소 내부 padding, 요소 사이 gap, 영역 사이 margin을 구분해 측정합니다.
2. 반복 값에서 간격 체계 후보를 만듭니다. 기존 화면을 보존하는 작업이라면 예쁜 배수로 임의 반올림하지 않습니다.
3. 콘텐츠 최대 폭, 페이지 여백, 모서리, 테두리 두께 등 배치 관련 기준을 명시합니다.
4. 좁은 화면에서 바뀌는 값과 유지되는 값을 나눕니다.
5. 화면별 조합은 design.md에, 공통 값과 용도는 이 문서에 둡니다.

### 작성 템플릿

```markdown
# 간격·레이아웃

- 단위·출처·기준:

| 이름 | 값  | 용도 | 금지하거나 주의할 사용 |
| ---- | --- | ---- | ---------------------- |

| 영역 | 넓은 화면 | 좁은 화면 | 전환 기준·이유 |
| ---- | --------- | --------- | -------------- |

## 크기·넘침

- 콘텐츠 폭·스크롤 영역·긴 내용 처리:
- 모서리·테두리 등 부가 규칙:

## 예외

| 화면·요소 | 예외 값 | 이유 | 검토 상태 |
| --------- | ------- | ---- | --------- |
```

완료 기준은 내부 여백(padding)과 요소 사이 간격(gap)의 용도가 구분되고, 값 목록뿐 아니라 각 값을 어디에 쓰는지 설명한 상태입니다.

## 8. components.md — 반복 UI의 계약

### 만드는 방법

1. 화면에서 반복되거나 독립적으로 조작하는 UI를 찾습니다. 아직 없는 범용 컴포넌트 라이브러리를 상상해서 만들지 않습니다.
2. 각 요소의 구조, 입력 내용, 사용자 동작, 크기·변형을 정리합니다.
3. 상태표를 만듭니다. hover·focus·disabled·loading·error는 필요한 요소에만 적용합니다.
4. 색·폰트·간격은 공통 기준 이름으로 연결합니다.
5. 키보드 조작, 의미 있는 이름, 오류 복구와 긴 내용 처리를 정의합니다.

### 컴포넌트마다 반복할 템플릿

```markdown
## [컴포넌트 이름]

- 목적·사용 화면:
- 구조·필수 내용·사용자 동작:
- 변형·크기:

| 상태 | 진입 조건 | 표현·토큰 참조 | 허용 동작 | 복구·다음 상태 |
| ---- | --------- | -------------- | --------- | -------------- |

- 키보드·포커스·접근 가능한 이름:
- 긴 내용·빈 값·좁은 화면:
- 구현 파일·예외:
- 수동 확인·자동 검사 항목:
```

예: 현재 구조도의 배지는 버튼이 아니므로 disabled 동작을 만들지 않습니다. 로딩 상태 문구는 기본·성공·실패와 대체 원문 안내가 필요합니다. 이 예를 새 제품의 모든 배지와 상태에 강제하지 않습니다.

## 9. 문서와 기계 검사 기준을 연결하는 방법

### 단일 기준을 선택한다

- 이미 CSS 변수·디자인 토큰 파일이 있다면 그것을 실행 기준으로 활용하고 문서는 역할과 사용법을 설명합니다.
- 현재 저장소처럼 간단한 CSS라면 문서의 JSON을 검사 기준으로 사용할 수 있습니다.
- 두 방식을 무계획하게 병행하지 않습니다. 값을 바꾸는 원본과 참조하는 쪽을 명확히 정합니다.

현재 검사기는 colors, typography, spacing 문서의 **첫 JSON 블록**을 읽습니다. 형식은 `CSS 속성: 문자열 배열`이며 속성은 세 문서 사이에서 중복되면 안 됩니다. 아래 값은 구조를 설명하는 예시일 뿐 채택된 디자인 값이 아닙니다.

```json
{
  "color": ["#111111", "#ffffff"]
}
```

현재 구조에서는 문서 설명, JSON, 실제 CSS가 서로 일치하는지 검토합니다. components와 `design.md`는 선택자, 상태, 의미를 설명하지만 검사기가 이 내용을 자동으로 판정하지는 않습니다.

### 검사기를 만드는 순서

1. 대상 파일과 스타일 형식을 명시합니다. 모든 프레임워크를 지원한다고 선언하지 않습니다.
2. 규칙 원본을 읽고 필수 기준 누락이나 형식 오류를 실패로 처리합니다.
3. 검사 대상에서 해당 스타일을 추출합니다. 복잡한 CSS·TSX는 기존 파서·린터 활용을 먼저 검토합니다.
4. 위반 위치·속성·값과 수정 방향을 출력합니다. 읽기 전용을 기본으로 합니다.
5. 정상 사례, 잘못된 색·폰트·간격, 빈 대상, 기준 누락, 지원하지 않는 스타일 형식을 검증합니다.
6. 수동 명령이 정확히 동작한 뒤 기존 통합 검사에 추가하고 마지막으로 훅에 연결합니다.

**현재 검사기는 모든 프로젝트에 쓸 수 있는 범용 검사기가 아닙니다.** 기본 경로는 `docs/architecture/index.html`입니다. 다른 HTML 경로를 인자로 넘겨도 기준 문서는 여전히 이 저장소의 문서를 읽습니다. 따라서 명령의 경로만 바꿔서는 새 프로젝트로 디자인 시스템이 이식되지 않습니다. 토큰 원본, 지원 문법, 대상 탐색, 패키지 명령을 함께 조정해야 합니다.

## 10. SKILL.md와 훅을 만드는 방법

### 스킬

1. 이름과 description에 언제 사용할지 적는다: 새 디자인 기준 작성인지, 기존 기준 적용인지.
2. 처음에 실제 대상·참고 자료·기존 규칙을 읽게 합니다.
3. 기준이 없으면 이 가이드로 문서를 작성하고 미정을 확인하게 합니다. 있으면 재작성하지 않고 적용합니다.
4. 대상별 경로와 검사 명령을 확인하게 합니다. 이 저장소의 경로를 모든 프로젝트의 기본값으로 강제하지 않습니다.
5. 긴 작성법은 가이드로 연결하고 스킬 본문은 짧게 유지합니다.
6. 형식 검사와 실제 요청 처리 검증을 구분합니다. 스킬이 발견된 것만으로 작업 품질을 보장하지 않습니다.

### 훅

1. 대상 Codex 버전과 공식 문서에서 이벤트·매칭 이름·입출력 규약을 확인합니다.
2. 현재 프로젝트의 기존 훅과 병합하되 중복 실행 여부를 확인합니다.
3. 스크립트 경로가 하위 작업 디렉터리에서도 해석되는지, Node와 Git 전제가 맞는지 검사합니다.
4. 검사 스크립트 직접 실행 → 설정의 명령 수동 실행 → 사용자 신뢰 승인 → 실제 도구 이벤트 순서로 확인합니다.
5. 성공과 실패 피드백을 각각 확인합니다. 도구 실행 후 훅은 이미 일어난 변경을 취소하지 못합니다.

현행 훅 설정과 수동 실행법은 [디자인 시스템 방법론](../methods/design-system.md)에 설명되어 있습니다. 새 환경에서 명령을 검증하기 전에는 활성화가 완료됐다고 보고하지 않습니다.

## 11. 새 프로젝트 시작용 요청문

```text
이 프로젝트의 디자인 시스템 작성 절차를 재사용해줘.
대상 프로젝트: [경로]
대상 기능·화면: [이름]
참고 자료: [Figma/이미지/기존 코드 경로 또는 없음]
변경 범위: [문서만 / 승인된 디자인의 구현 포함]

먼저 대상 지침과 기존 디자인·기술 구성을 조사해.
authoring-guide.md에 따라 design.md와 네 공통 문서를 작성하되,
관찰 사실·AI 제안·사용자 승인·미정을 구분해.
막히는 결정은 한 번에 하나씩 질문하고 기존 인터뷰는 반복하지 마.
현재 구조도의 값을 새 제품의 확정 기준으로 복사하지 마.
실제 스타일 방식에 맞는 검사 범위를 정하고 정상·위반 사례를 확인해.
문서·구현·수동 검사·훅 실제 발화의 완료 여부를 따로 보고해.
마지막에 README와 하네스 흐름 화면의 현재 상태를 맞춰줘.
```

## 12. 인계 전 체크리스트

- [ ] 처음 보는 사람이 출처와 확정·미정 항목을 구분할 수 있습니다.
- [ ] design.md만 읽고 화면 순서·상태·반응형을 설명할 수 있습니다.
- [ ] 네 공통 문서가 값뿐 아니라 역할·용도·예외를 설명합니다.
- [ ] 공통 기준과 화면별 예외가 중복되거나 충돌하지 않습니다.
- [ ] 실제 없는 입력·버튼·상태·앱을 구현된 것으로 기록하지 않았습니다.
- [ ] 문서 템플릿의 빈칸은 채우거나 미정 이유를 기록했습니다.
- [ ] 정상·위반 검사 결과와 검사하지 못하는 범위가 명확합니다.
- [ ] 새 프로젝트의 경로·스타일 방식·검사 명령으로 연결했습니다.
- [ ] 수동 검증과 훅 신뢰·실제 작동, 시각 검증을 구분했습니다.
- [ ] 화면을 변경했다면 실제 확인 결과를 남겼습니다. 미실행이면 그렇게 밝혔습니다.
- [ ] README와 흐름 화면은 현 상태와 일치하며 승인된 인터뷰는 보존했습니다.

## 13. 이후 변경할 때

새 화면을 추가할 때는 먼저 기존 기준에서 적용할 규칙을 찾습니다. 맞는 규칙이 없다면 화면에만 적용할 예외인지 공통 기준을 바꿀 사안인지 결정하고, 영향을 받는 화면을 목록으로 남깁니다. 공통 기준을 바꿀 때는 이유와 검토 상태를 기록하고 관련 화면을 다시 확인합니다. 이력이 필요하면 실제 변경과 함께 Git으로 관리하되 커밋은 사용자 요청에 따릅니다. 검사 실패를 없애려고 허용 목록만 늘리는 일은 디자인 결정으로 볼 수 없습니다.
