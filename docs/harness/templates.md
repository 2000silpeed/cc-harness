# 전 사이클 산출물 작성 템플릿

새 대상의 `docs/features/{feature}/`에 필요한 템플릿만 사용한다. 빈 문서를 대량 생성하지 않는다. 대괄호는 작성 시 교체하고 확정하지 못한 항목은 미정 이유·결정자를 적는다. 기존 PM 인터뷰에 이 템플릿을 덮어쓰지 않는다.

## 원문·인터뷰·요구사항

```markdown
# spec-original.md

## 최초 요청

[사용자의 요청을 의미 변경 없이 보존]

## 제공 자료

[파일·링크·명시한 제약]
```

```markdown
# interview.md

| 질문 ID | 질문·AI 추천과 이유 | 사용자 답변·결정 이유 | 반영 요구사항 |
| ------- | ------------------- | --------------------- | ------------- |

## 회고

- AI 추천과 다르게 선택한 내용:
- 새로 발견한 경계·예외:
- 다시 시작한다면 바꿀 접근:
```

```markdown
# spec-fixed.md

- 상태·승인 근거:

## 목적·주 사용자

## 기본 사용 시나리오

## 요구사항

| ID  | 동작·제약 | 결정 근거 | 확인 방법 |
| --- | --------- | --------- | --------- |

## 용어 정의

## 오류·경계·저장·성능

## 미정·제외 범위
```

작성 방법: 실제 코드 패턴을 먼저 조사하고 primary user, 최소 동작, 저장 관계, 경계, 실패 표시, UI 일관성, 성능, 확장을 확인한다. 질문은 하나씩, 이미 알려진 답은 반복하지 않는다. 확장은 이번 범위를 넓히는 허가가 아니라 결정 영향 검토다.

## 디자인

[디자인 작성 가이드](../design-system/authoring-guide.md)의 design.md·colors·typography·spacing·components 템플릿을 사용한다. 요구사항을 시각 명세로 바꾸되 관찰·추정·승인을 구분한다. UI가 없으면 이유를 남기고 생략한다.

## PRD와 ADR

```markdown
# prd.md

- 상태·요구사항 승인 근거·디자인 참조:

## 개요

## 사용자 스토리와 요구사항 ID

## 기술 대안 비교

| 기준               | 안 A | 안 B | 안 C |
| ------------------ | ---- | ---- | ---- |
| 데이터 구조        |      |      |      |
| API 변경 지점      |      |      |      |
| 상태관리 변경 지점 |      |      |      |
| 핵심 동작          |      |      |      |
| 컴포넌트 구조      |      |      |      |
| 기존 패턴 일관성   |      |      |      |
| 테스트 용이성      |      |      |      |

## 기술 결정: [제목]

- Context:
- Decision: [사용자 선택 근거]
- Alternatives: [각 대안과 각각의 거부 이유]
- Consequences: [장점·단점·부담]

## Out of Scope

## 용어 정의

## 검증·위험·미정
```

작성 순서: 기술 결정은 처음에 미정으로 둔다 → 실제 구조와 맞는 최소 세 안을 비교한다 → 사용자가 선택한다 → ADR 네 요소를 작성한다 → 하지 않을 일을 구체화하고 승인받는다. 의미 없는 대안으로 선택을 유도하지 않는다. PRD는 결정의 기준점이고 디자인 값의 중복 저장소가 아니다.

## 이슈

```markdown
# issues.md

- PRD·범위 승인 근거:
  | ID  | 사용자에게 보이는 결과 | 선행 이슈 | 크기 판단 | 상태 | 외부 URL |
  | --- | ---------------------- | --------- | --------- | ---- | -------- |

## [ID] [행동 중심 제목]

### 목적·범위·PRD 요구사항

### Acceptance Criteria

- [ ] AC-01: Given [...], When [...], Then [...]

### 의존성

### 테스트 접근·예상 변경 범위

### 제외 범위·위험

### 등록 결과

- 저장소·issue URL·보드 item·상태:
```

한 이슈만으로 사용자 동작을 보여줄 수 있는지 검토한다. API→상태→UI만으로 수평 분할하지 않는다. 반나절~하루는 강의의 크기 판단 기준이며 실제 작업 시간 보장은 아니다. GitHub는 이슈 목록 승인 후 대상 저장소/보드/권한을 확인해 등록한다. 일부 성공 시 이미 생성한 URL을 기록해 중복 재등록하지 않는다.

## 테스트·검증

[9–13강 문서](../lessons/09-13-tdd.md)의 시나리오·AC·보안 템플릿을 이슈별 `tests/`와 `reviews/`에 사용한다. 요구사항 ID → AC → 시나리오 ID → 테스트 코드 → 실행 증거의 연결이 끊기지 않아야 한다.

## 진행·재개

```markdown
# progress.md

- 대상 프로젝트 절대 경로:
- feature·현재 이슈·현재 단계:
- 구현/외부 작업 승인 범위:
- 대상 변경 식별자: [커밋 또는 검사 파일 해시]

| 게이트 | 대상 문서·버전 | 상태 | 사용자 승인·위임 근거 |
| ------ | -------------- | ---- | --------------------- |

| 단계 | 명령·cwd | 결과·종료 코드 | 증거 경로 | 다음 행동 |
| ---- | -------- | -------------- | --------- | --------- |

## 남은 문제·미실행 검사

## 재개 조건
```

명령을 실행하지 않았다면 planned/unverified로 적는다. 목표 스킬 이름을 나열했다고 실행 완료로 바꾸지 않는다.

## PR·CI·머지 기록

```markdown
# delivery.md

- 원격 저장소·base·head·대상 커밋:
- 관련 이슈·요구사항:

## 변경 요약

## 실제 검사

| 검사 | 명령/CI 이름 | 대상 변경 | 결과 | 로그 |
| ---- | ------------ | --------- | ---- | ---- |

## 리뷰·미해결 의견

## 승인

- PR 생성 / 머지 / 브랜치 정리 / 이슈 종료 각각의 범위:

## 머지 결과 또는 미실행 이유

## 회고와 다음 기능에 재사용할 규칙
```

테스트 명령은 대상의 실제 package/CI에서 얻는다. GitHub Actions YAML이 존재하는 것과 원격 실행 성공은 다르다. 아직 CI가 없으면 초안을 만들 수 있지만 검증 상태를 pending으로 둔다.

## 배포·운영 인계 — 강의 밖 보강

```markdown
# release-checklist.md

- 배포 대상·환경·담당자·비용 승인:
- 배포할 버전·검사 증거:
- 비밀 관리: [값이 아닌 저장 위치·주입 방식]
- 마이그레이션·백업·복구 조건:
- 실행 절차·롤백 절차:
- smoke test·관측할 로그·알림:
- 사용자 승인과 실제 실행 결과:
- 남은 운영 작업·책임자:
```

플랫폼이 정해지지 않으면 일반 템플릿을 실행 가능한 배포 스크립트로 주장하지 않는다.
