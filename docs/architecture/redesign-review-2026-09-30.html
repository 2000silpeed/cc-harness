기준선 재현과 기존 안전장치

sequence 1에 비범위 승인 old-approval.md와 필수·valid 증거 old-evidence.json을 넣고, sequence 2에서 둘 다 누락해도 evidence_validity: valid이면 prepare 종료 코드 0, decide는 ROLLOVER_READY였습니다. 과거 참조는 기록에서 사라졌습니다. 반면 참조를 유지한 채 실제 파일을 바꾸면 STOP_EVIDENCE_STALE가 반환됐습니다. 이는 임시 재현이며 당시 코드의 동작입니다. 인계 스크립트

선택된 v2 계약

후속 기록은 predecessor_handoff_id로 직전 인계를 잇고, retired_refs에 이전 승인·증거의 kind, path, sha256, 유효성, 은퇴 원인과 출처 ID를 누적합니다. 이전 활성 참조는 그대로 활성으로 남거나 정확히 한 번 은퇴해야 하며, 과거 또는 같은 전환에서 은퇴한 동일 kind/path/sha 조합은 다시 활성화할 수 없습니다. 잘못된 계보는 prepare에서 거부되어 기존 기록을 보존합니다. v2 계보 검사

검사 경계readiness와 파일 해시 검사는 현재 활성 참조만 대상으로 하며 은퇴 metadata의 원본 파일을 다시 읽지 않습니다. 원본 승인·증거 바이트를 보관하거나 복원할 수 있다는 보장은 없습니다. 기존 실패가 참조하는 증거는 은퇴·변경할 수 없고, STOP 해제에는 별도의 새 승인·증거 경로가 계속 필요합니다.

구현자 검사 · 당시 작업 트리

같은 prepare 전환의 참조 탈락·재활성화 2건이 Red로 실패했습니다. 이후 관련 Vitest 123/123이 Green으로 통과했고 대상 ESLint, Prettier, diff 검사도 통과했다고 구현자가 보고했습니다. Red는 독립 검증자가 다시 실행한 결과로 주장하지 않습니다. 이식 회귀 테스트

독립 검증과 통합 검사

독립 검증자는 lineage AC를 모두 PASS로 판정했습니다. 검증자 실행 node --check 종료 코드 0, 관련 Vitest 123/123 종료 코드 0입니다. 당시 코드·계약 변경 뒤 이 문서의 사실 수정 전, 검증자가 npm run check를 정확히 한 번 실행해 종료 코드 0을 확인했습니다. lint, 디자인 84개 선언, 하네스 15개 스킬·59개 등록 파일, 서식, Vitest 123/123, 타입 검사를 포함합니다. 이는 당시 작업 트리의 결과이며 이후 커밋 전 b30f72f에서 별도 통합 검사를 수행했습니다. git diff --check도 종료 코드 0이며, 당시 HTML의 href 59개 중 로컬 링크 41개가 모두 존재했습니다. 당시에는 미커밋이었고, 이후 f93bec9에 로컬 커밋했습니다. 푸시는 하지 않았습니다.

세 번째 가설: 승인 출처의 자기 선언

원본 저장소의 승인 기록을 바꾸지 않고 폐기 가능한 /tmp/approval-boundary.Sd9Cf6/repo에서 재현했습니다. 이 실험은 파일 해시가 맞아도 승인 주체의 진위가 자동으로 확인되지는 않는다는 경계를 보여줍니다.

입력과 관찰 결과

사용자 결정이 아니라고 명시된 self-approval.txt를 올바른 SHA와 함께 scope 및 stage:ac-verification의 approved 참조로 기록했습니다. 최초 작업자는 template·prepare의 종료 코드 0과 PREPARED를 보고했습니다. 독립 검증자는 같은 fixture에서 decide를 다시 실행해 종료 코드 0, PHASE_READY와 ac-verifier 라우팅을 확인했습니다. prepare의 독립 재실행은 수행하지 않았습니다.

현재 범위의 권고 A

CLI는 참조 형식·파일 해시 등 metadata 무결성을 검사합니다. 실제 승인 원문, 결정자, 범위는 별도 인간·세션 검토에서 대조해야 합니다. 이를 통과한 승인으로 자동 간주하지 않도록 인계와 독립 검토에 출처 확인 결과를 명시합니다. 서명 영수증을 도입하는 B안은 별도 설계와 승인이 필요하며 이번에 구현하지 않았습니다.

현재 아키텍처: 문서 계약이 실행을 이끈다

아래 연결은 파일·명령의 정적 관계를 요약합니다. 실제 모델 라우팅이나 훅 발화가 모두 검증됐다는 뜻이 아닙니다.

기획 G1–G5→이슈·시나리오→Red / Green→독립 AC→리팩터·보안→E2E·PR 인계

이 흐름의 설명은 planning, tdd-loop, delivery, 구조도에 분산되어 있습니다. 구조도의 그림과 정책 본문이 서로 다른 시점에 갱신될 수 있으므로 하나의 규범 출처와 나머지 파생 뷰를 지정해야 합니다.

근거와 위험: 확정 사실과 검증 가설을 분리

파일 링크는 이 보고서 위치에서 상대 경로로 열립니다. 정적 확인은 기준선 HEAD의 코드·기록 내용, 위험은 그 내용에서 도출한 전환 실패 가능성입니다.

승인 상태의 자기 선언 가능성

도구는 승인 참조의 모양과 파일 해시를 검사한 뒤 status === "approved"를 권한으로 해석합니다. 그 값이 실제 승인 주체에서 왔는지는 자동 증명하지 않습니다. 참조 검증 코드 · 판정 코드 · AI 자기 승인 금지

폐기 가능한 fixture에서 사용자 결정이 아닌 문서의 올바른 SHA와 approved metadata만으로 decide가 PHASE_READY를 반환함을 독립 재실행했습니다. 파일 무결성은 승인 출처의 진위를 보장하지 않으므로 승인 원문·결정자·범위 대조는 별도 인간·세션 검토로 유지합니다.

등록·복사·문서 절 추출 check-harness, install-harness, read-section가 이미 구현 기존 CLI 재사용. registry 원문을 매번 LLM 컨텍스트에 넣지 않음. 섹션 출력은 호출자가 상한 적용.
디자인 정적 검사 디자인 검사 가이드에 수동 검사·hook 모드·최종 검사; package scripts의 check가 디자인 검사를 다시 포함 관련 검사 1회와 최종 통합 1회. --hook 수동 실행은 훅 프로토콜 검증 때에 한정. 실제 화면 판단은 별도.
모든 Bash 뒤 CSS 재검사 Codex hook 설정, Claude hook 설정이 Bash를 포괄 읽기 전용 명령의 중복 검사를 줄일 변경 감지 방안 검토. 쓰기 명령 누락·훅 신뢰 상태는 별도로 확인.
이식 smoke test 수동 dry-run/apply/reapply 일부가 이식 회귀 테스트에서 회귀 검사됨 일반 변경은 관련 Vitest와 통합 검사. 배포 목록·설치 코드 변경이나 실제 대상 이식 때 수동 검증.
승인·AC·증거의 의미 승인 주체와 독립 AC 계약 명령·해시·형식은 스크립트, 승인 출처·실제 결과·사용자 가치 판정은 독립 검토.

목표 계층: 정책을 한 번 정의하고 여러 진입점에서 사용

객체지향은 클래스를 늘리는 목표가 아닙니다. 변경되는 상태와 그 상태를 보호하는 규칙을 같은 경계에 묶고, 파일·Git·CLI는 바깥으로 밀어내는 설계 선택입니다.

핵심 객체와 불변식 제안

  • ApprovalDecision: 주체, 원문 참조, 범위, 유효성의 계보를 가진 값. 파일 해시만으로 승인 확정하지 않음.
  • HandoffRecord: STOP 이유·해제 조건, 예산·실패·참조의 단조로운 전환을 보호.
  • EvidenceManifest: 명령·환경·입력 해시·결과·실제 로그의 관계를 표현. historical/current 판정을 분리.
  • GateDecision: 기계적 충족, 독립 검토, 사용자 승인 출처를 별도 상태로 기록.

포트와 어댑터 제안

  • 포트: 파일 해시, Git snapshot, 증거 읽기, 승인 조회, 결과 기록.
  • CLI 어댑터: 기존 session-handoff, 설치·검사 명령 유지.
  • 문서 어댑터: lifecycle 하나를 규범 출처로 정하고 스킬·구조도는 단계별 진입 요약으로 유지.
  • 평가 어댑터: 로컬 fixture 기반 오프라인 회귀; 실제 운영 피드백은 명시적으로 승인된 범위에서만.
로컬 평가 순환 · 제안기존 trace: 명령·로그·버전→dataset: 익명화한 실패 fixture→evaluation: 결정론적 검사와 독립 AC→feedback: 실패 ID·수정 후보→다음 로컬 fixture각 연결에는 당시 입력 해시와 현재 재검증 결과를 따로 남깁니다. 외부 동기화와 자동 승인 없이 현재 파일 기반 증거에서 시작합니다.
Fowler의 리팩터링 원칙을 적용하는 방식기존 동작을 작은 단계로 보존하면서 분리·이름 변경·책임 이동을 수행하고 매 단계 검사합니다. 아래 5단계는 이 저장소를 위한 제안 순서이며 Fowler 책의 목차나 공식 단계가 아닙니다. Refactoring 소개 · 리팩터링 카탈로그

서로 다른 3안 · planning의 동일 7기준

비교 기준은 기획 계약의 7항목을 그대로 사용했습니다. 표는 설계 판단이며 실측 성능·비용 수치가 아닙니다.

고정 기준 A · 문서 중심 유지 B · 상태 코어 + 기존 어댑터 추천 C · 이벤트 로그 기반 재구축
1. 데이터 구조 현행 JSON·Markdown과 규칙 분산 유지 현행 파일 형식을 보존하고 내부에 승인·STOP·증거 값 객체 도입 append-only 이벤트에서 현재 상태 투영; 마이그레이션 필요
2. API 레이어 변경지점 CLI 조건문에 검사 추가 현행 CLI 인터페이스 유지, 내부 판정을 코어 호출로 교체 새 이벤트/투영 API와 CLI 전면 교체
3. 상태관리 변경지점 handoff JSON에 필드 추가 전환 함수가 불변식 적용; 저장 형식은 호환 상태를 이벤트 재생으로 구성, 운영·복구 경계 추가
4. 핵심 동작 에이전트가 문서·로그 대조 정적 규칙 선판정 → 독립 증거 검토 → 승인된 단계 전환 모든 행위를 이벤트화하고 정책 엔진에서 투영·판정
5. 컴포넌트 구조 현재 스크립트·스킬에 기능 추가 작은 도메인 코어, CLI/파일/Git 어댑터, 기존 스킬 이벤트 저장소, 스키마 버전, 투영기, 감사 UI 필요
6. 기존 패턴과 일관성 높음, 중복과 암묵 규칙 지속 높음, 기존 명령과 배포 구조를 점진 보존 낮음, 독립형 파일 하네스와 큰 차이
7. 테스트 용이성 CLI·파일 fixture 반복 순수 전환 단위 테스트 + 현행 이식 회귀 + 수동 AC 이벤트 재생·호환·복구 테스트 비용 큼

A의 이점과 비용

가장 작은 초기 변경. 그러나 승인·증거 계보가 문서와 CLI 조건문 사이에 계속 흩어집니다.

B의 이점과 비용

기존 진입점과 증거를 보존하면서 불변식을 테스트하기 쉽습니다. 초기에 객체 경계와 파일 호환성 설계가 필요합니다.

C의 이점과 비용

감사 가능한 장기 이력에 유리합니다. 현재 독립 하네스 규모에는 데이터 이전·운영 부담이 큽니다.

ADR 초안 · 추천 B · 결정 상태: 제안, 미승인Context 승인·STOP·증거 규칙이 문서와 CLI에 분산됨. Decision 현행 파일/CLI 호환을 유지한 작은 상태 코어를 단계적으로 도입. Alternatives A는 계보 공백의 반복을 허용하고 C는 운영 복잡도가 큼. Consequences 새 내부 경계·호환 테스트·마이그레이션 비용이 생기며 사용자 승인과 독립 AC 판단은 자동화되지 않음. 이 ADR은 선택 요청을 위한 초안이며 G2 승인 기록이 아닙니다.

제안하는 5단계 전환

각 단계는 별도 승인 범위와 작은 변경 묶음으로 계획합니다. 선행 단계의 Green이 전체 제품 완료를 뜻하지 않습니다.

기준선 고정과 증거 분류

현재 계약·AC·명령·환경과 과거 manifest를 연결하고, 오래된 해시와 검토 회수의 시점을 바로잡습니다. 역사적 로그는 수정하지 않고 당시 버전으로 표시합니다.

통과 조건: 승인 원문·현재 해시·historical/current 구분·미검증 항목이 서로 모순 없이 조회 가능.

전환 불변식의 순수 함수화

STOP 이유, 승인·증거 계보, 예산, dirty 상태의 전환 규칙을 fixture와 함께 분리합니다. 기존 CLI의 외부 동작과 저장 형식을 우선 보존합니다.

통과 조건: 정상·경계·실패 사례가 Red→Green으로 검증되고 기존 인계 회귀가 통과. 승인 자기 선언을 통과로 오인하지 않음.

검사 파이프라인 정리

등록 링크의 앵커 검증, 중복 디자인 검사, Bash 훅의 불필요한 반복, 수동 이식 검증 트리거를 명시합니다. 자동화의 범위를 넓힐 때 신뢰와 실제 발화는 따로 검증합니다.

통과 조건: 관련 검사 1회와 최종 npm run check 1회; 훅 smoke test·브라우저 확인의 결과를 별도 기록.

증거 평가 루프

대표 fixture를 로컬 오프라인 평가 세트로 쓰고 구조·종료 코드·버전의 결정론적 검사를 자동화합니다. 독립 검증자는 실제 로그와 AC 결과를 검토하고 실패 사례를 다음 fixture 후보로 남깁니다.

통과 조건: 이전 버전과 현재 버전의 동일 입력 비교 및 실패 식별 정보 보존. 운영 trace·유료 LLM judge는 범위 밖.

문서·스킬·구조도 일치시키기

한 규범 출처에서 단계 이름·권한·STOP을 유지하고 스킬은 필요한 절로 연결합니다. 구조도는 사람을 위한 뷰로 갱신하며 브라우저 렌더링도 확인합니다.

통과 조건: 문서 링크·명령·검사 범위와 화면 설명이 일치하고 독립 AC 검토가 통과. PR·배포는 별도 권한.

검증 게이트와 이번 보고서의 한계

구현 시 필요한 게이트

  1. 현재 HEAD·dirty 및 승인 범위 재확인
  2. 관련 fixture로 실패를 관찰하고 최소 구현
  3. 관련 검사 재실행 후 npm run check 한 번
  4. 구현자와 분리된 AC·승인 출처 검토
  5. 구조도 변경이면 실제 브라우저 렌더링 확인
  6. Git·PR·외부 서비스는 별도 권한 확인
