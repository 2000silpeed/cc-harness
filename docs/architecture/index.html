CC-HARNESS / IDEA TO PROJECT

아이디어에서 프로젝트까지

무엇을 정하고, 어떤 스킬을 쓰고, 무엇을 확인한 뒤 다음으로 가는가.

00 · 시작 01 · 기반 02 · 요구사항과 디자인 03 · 설계와 작업 분해 04 · 이슈마다 반복 05 · 기능 완성

18개 자료 · 224쪽 분석 / 스킬셋 등록. 실제 제품 구현·머지·배포는 별도 실행 단계입니다.

00 · 시작 / 소개 · 전체 사이클 진입

아이디어와 대상부터 정한다

누가 어떤 문제를 해결하는지, 어느 프로젝트에서 어디까지 진행할지 확인합니다.

$harness-cycle

다음 단계로 넘기는 것: 최초 요청 · 대상 경로 · 현재 단계

01 · 기반 / 2–3강

같은 규칙으로 작업하고 자동으로 검사한다

기존 도구를 조사한 뒤 협업 지침과 코드·커밋 검사를 연결합니다.

$project-bootstrap · $mermaid-diagram

다음 단계로 넘기는 것: AGENTS · 실제 검사 명령 · Git 훅

02 · 요구사항과 디자인 / 4–5강

무엇을 만들고 어떻게 보일지 정한다

한 번에 하나씩 질문해 결정을 남기고, 참고 화면에서 공통 디자인 기준을 만듭니다.

$feature-planner · $design-system

다음 단계로 넘기는 것: spec-fixed · design.md · 공통 디자인 기준

사람이 결정하는 지점

요구사항과 필요한 디자인 결정을 확정합니다. AI의 추천을 사용자 승인으로 기록하지 않습니다.

03 · 설계와 작업 분해 / 6–8강

기술 선택의 이유를 남기고 작은 동작으로 나눈다

기술안 세 가지를 비교하고, 범위를 확정한 뒤 AC와 의존성이 있는 수직 이슈를 만듭니다.

$feature-planner

다음 단계로 넘기는 것: PRD · ADR · Out of Scope · 이슈와 AC

사람이 결정하는 지점

기술안 선택 → 제외 범위 → 이슈 목록. 실제 GitHub 등록은 별도 승인 범위에서만 수행합니다.

04 · 이슈마다 반복 / 9–13강 · 테스트 특강

실패 테스트에서 검증된 구현으로 간다

시나리오 → Red → Green → 독립 AC 검증 → Refactor → 보안. 누락된 AC는 다시 Red로 돌아갑니다.

$test-scenarios · $tdd-red · $tdd-green · $ac-verifier · $tdd-refactor · $security-review

다음 단계로 넘기는 것: 테스트 · 최소 구현 · AC 근거 · 보안 결과

반복하는 방법 선택 / 16–17강

$tdd-loop: 한 이슈의 순서를 묶고 단계별 확인을 유지합니다.

$tdd-auto-loop: 사전 위임된 범위에서 격리된 단계·결과 JSON·객관 STOP으로 PR까지 진행합니다. 무한 반복이나 자동 머지가 아닙니다.

16·17강은 이 사이클을 감싸는 실행 방식입니다. 프로젝트가 끝난 뒤 추가하는 단계가 아닙니다.

05 · 기능 완성 / 14–15강

실제 사용자 흐름과 CI를 확인한 뒤 통합한다

기능 이슈를 모아 E2E로 연결을 확인하고, PR 초안·필수 검사·리뷰·승인을 거쳐 main에 통합합니다.

$e2e-write · $create-pr

다음 단계로 넘기는 것: E2E 증거 · PR · CI · 승인된 머지

main 이후 / 강의 밖 보완

배포 대상·비용·데이터·백업·롤백을 정하고 승인받습니다. 실제 배포 후 smoke test와 운영 인계를 확인합니다. main 머지만으로 배포 완료를 선언하지 않습니다.

전체 흐름을 도식으로 보기

도식을 불러오는 중입니다.

실선은 진행 순서, 점선은 재작업입니다. 각 단계의 승인은 별도로 유지합니다.

  tdd --> review["AC · Refactor · 보안 / 11–13강"]

  review --> e2e["기능 E2E / 14강"]
  e2e --> delivery["PR · CI · 승인된 머지 / 15강"]
  delivery --> release["배포 · 운영 인계 / 보강"]
