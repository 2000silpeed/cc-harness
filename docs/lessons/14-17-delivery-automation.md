### 현재 레포와 금지 경계

로컬 `AGENTS.md`, `package.json`, 파일 목록을 확인했다. 현재 앱 소스, React/TypeScript 앱 구성, 앱 테스트·빌드 및 원격 CI 구성이 없다. `npm run check`는 ESLint, 디자인 기준, Prettier를 실행하는 **로컬 통합 품질 검사**이지 단위·통합·E2E 앱 테스트나 원격 CI가 아니다.

분석 시작 시 프로젝트 스킬은 design-system과 mermaid-diagram이었다. 이후 통합 작업에서 강의 스킬을 실제 작성했다. 최종 등록 목록과 검증 상태는 `docs/harness/registry.json` 및 `docs/harness/verification.md`를 기준으로 본다. 강의에서 이름을 읽은 것과 스킬 등록·제품 실행은 별개다.

이 문서는 14–17강 분석 담당자의 산출물이다. 전체 하네스 통합에서 별도로 등록한 스킬은 `docs/harness/registry.json`을 기준으로 확인한다. 원본 PDF, `feature-planning-workflow.md`, `docs/features/pm-program-tracker`의 보호 대상 3파일은 수정하지 않는다. 앱 개발, 새 의존성, 커밋, 브랜치 생성, 푸시, 외부 등록, 전역 설정 변경은 하지 않았다. PDF 렌더는 지정된 임시 경로의 판독용 산출물이다.

## 2. 아이디어부터 전달까지 연결하는 입력 계약

**강의 사실**: 15:p13의 전체 흐름은 `spec 한 줄 → AI 인터뷰 → PRD/ADR → 이슈 분해 → Red/Green/Refactor → Security → E2E → CI/브랜치 보호 → main 머지`다. 16:p5는 `/feature-planner`가 `spec → 인터뷰 → 디자인 → PRD → 이슈 분해`를 묶고 승인 게이트를 유지하는 패턴이라고 설명한다.

**보강 방법론**: 이 네 강의는 앞단 기획을 대신하지 않는다. 후속 프로젝트에서 다음 입력을 받았을 때만 구현 절차로 넘어간다. 이 레포에서는 설명서 인계까지이며 지금 이 표를 채워 앱 개발을 시작하지 않는다.

| 단계                 | 필수 입력                               | 수행과 산출물                                   | 다음 단계 승인                                  |
| -------------------- | --------------------------------------- | ----------------------------------------------- | ----------------------------------------------- |
| 아이디어/인터뷰 인계 | 최초 요청, 사용자 문제, 용어, 제외 범위 | 원문과 확정 결정 분리, 미결 질문 목록           | 요구사항 승인                                   |
| 아키텍처 인계        | 확정 요구사항, 실제 레포, 제약          | PRD, ADR, 디자인 근거, 기술 결정과 이유         | 아키텍처 승인                                   |
| 구현 범위 인계       | 기능 우선순위, 예산, 데이터 경계        | 포함/제외 범위와 변경 허용 파일                 | 범위 승인                                       |
| 이슈 인계            | 승인 범위, 의존 순서                    | 이슈별 AC, 시그니처, 검증 계층, base/head 계획  | 이슈 목록 승인                                  |
| TDD 사이클           | 승인 이슈와 실행 가능한 테스트 환경     | 실패 근거, 최소 구현, AC 검증, 리팩터·보안 결과 | 16강 방식의 단계별 승인 또는 명시된 제한적 위임 |
| 기능 검증            | 기능 이슈 통합 결과, PRD 사용자 여정    | E2E 시나리오·실행·실패 복구 기록                | 기능 여정 검토                                  |
| 전달                 | 검증 증거, PR 초안, 브랜치 정책         | PR, CI 결과, 리뷰, 머지 기록                    | 외부 변경 및 최종 머지 승인                     |

재사용할 핵심은 도구 이름보다 **입력과 검증 결과를 다음 단계에 넘기는 계약**이다. 각 단계는 앞 단계의 파일 경로·버전·승인 근거를 참조하고, AI가 제안한 내용과 사용자가 확정한 내용을 섞지 않는다.

## 3. 14강: 최소한의 E2E로 연결 검증

### 3.1 강의 사실: 계층과 비용

14:p4의 문제는 함수들이 각각 통과해도 연결이 끊기면 앱은 동작하지 않는다는 것이다. 14:p5의 피라미드는 아래의 단위 테스트를 많이, 위의 E2E를 적게 둔다. 슬라이드는 Mike Cohn의 2009년 책을 출처로 적지만 이 문서에서는 해당 책을 별도로 검증하지 않았다.

| 계층 | 강의의 검증 예시(14:p7)                     | 비용·안정성 설명(14:p5-6)                                           | 보강: 구분 기준                                                |
| ---- | ------------------------------------------- | ------------------------------------------------------------------- | -------------------------------------------------------------- |
| 단위 | `addTag()`가 올바른 객체를 반환             | 밀리초, 환경 의존 없음, 함수 단위 추적, flaky 거의 없음             | 작은 동작의 규칙·예외·경계값; 시간과 외부 상태를 통제해야 함   |
| 통합 | Context와 API 함수가 연결되어 동작          | 모듈 사이 연결 검증                                                 | 모듈 계약과 데이터 전달 검증; 사용자 전체 여정과 동일하지 않음 |
| E2E  | `react` 입력 후 Enter를 눌러 chip 표시 확인 | 초-분, 브라우저·서버·DB 필요, 원인 추적이 넓고 네트워크·타이밍 영향 | 사용자가 관찰하는 전체 경로; 실제 연결과 대체한 경계를 명시    |

보강: 위 속도와 환경 의존성은 강의의 단순 비교이지 모든 테스트의 보장값이 아니다. 단위 테스트도 전역 상태나 시간을 통제하지 않으면 불안정할 수 있다. E2E라는 파일명만으로 서버·DB까지 연결되었다고 판단하지 않는다. 로컬 `npm run check`를 이 표의 통합 테스트로 분류하면 안 된다.

### 3.2 강의 사실: 시점, 원칙, 도구

- 14:p2 도식: TDD·보안 완료 → `/e2e-write` → `/create-pr` → CI → main 머지.
- 14:p9: 기능의 모든 이슈가 머지된 뒤 E2E를 한 번 작성하고, 이후 새 이슈의 PR 전에는 기존 전체 E2E를 회귀 실행한다. 16:p8과 연결하면 첫 기능에서는 이슈를 **기능 통합 브랜치**에 모은 뒤 최종 main PR 전에 작성하는 흐름이다.
- 14:p12의 네 원칙: 완결된 사용자 여정, 단위 테스트 중복 금지, 정상 흐름 중심(예외·경계는 단위 담당), 구체적 행동과 결과. 추상적인 “태그가 잘 동작” 대신 “Enter → chip 표시”를 쓴다.
- 14:p10: Playwright를 Vitest와 분리해 사용, `webServer`를 통한 서버 실행, 시맨틱 셀렉터, Trace Viewer의 스크린샷·네트워크·콘솔 기록을 소개한다.
- 14:p11: 강의 셀렉터 우선순위는 `getByRole → getByText → getByPlaceholder → getByTestId`. 마지막 것은 다른 방법이 안 될 때 사용하며 `data-testid` 남용을 경계한다.
- 14:p13: 생성한 note ID를 보관했다가 `afterEach`에서 각각 API DELETE로 정리하고 ID 배열을 비운다. 실행 순서에 무관한 독립성을 목표로 한다.
- 14:p14: headless는 기본 자동 실행, headed는 브라우저 창을 보며 디버깅·시연하는 모드로 설명한다. 같은 테스트의 모드 차이지 서로 다른 테스트 계층이 아니다.

**보강 방법론**: “정상 흐름만”은 이 강의의 최소 E2E 전략이다. 후속 앱에서 로그인 실패·권한 차단 등 사용자 수준 위험이 핵심이면 승인된 위험 분석으로 E2E 범위를 보강한다. 모든 제품의 예외 E2E를 금지하는 보편 규칙으로 만들지 않는다. headed/headless 결과가 다르면 환경 차이를 조사하지, 강의 문구를 근거로 같다고 보고하지 않는다.

### 3.3 재사용 절차: E2E 작성과 실행

입력: 승인 PRD의 사용자 스토리, 통합된 기능, 기존 단위·통합 테스트, 실행 URL, 테스트 계정, 격리 데이터 정책, 설치된 러너/브라우저, 변경 승인 범위.

1. 기능 통합 완료 여부와 앱 실행 가능성을 확인한다. 미구현 여정을 실패 버그로 등록하지 않고 선행 구현 누락으로 분리한다. 현재 레포에는 앱이 없어 실행 단계로 진행하지 않는다.
2. 사용자 시작 상태부터 최종 관찰 결과까지 여정을 펼친다. 내부 함수의 세부 분기는 단위·통합으로 보내고 핵심 정상 경로를 선택한다.
3. 화면의 실제 role·이름·텍스트를 확인해 locator 후보를 정한다. 강의 우선순위와 선택 이유를 기록한다. 존재하지 않는 UI나 selector를 추정하지 않는다.
4. 생성할 데이터에 테스트 소유권을 표시하고 생성 ID를 수집한다. 삭제 대상은 이 실행에서 만든 테스트 데이터로 한정한다. 운영 URL이면 실행을 중단한다.
5. 승인된 시나리오에 따라 테스트를 작성한다. 서버 시작 방법, 데이터 초기화/정리, 실패 증거 수집 설정을 별도로 확인한다.
6. 관련 시나리오를 실행하고 결과를 읽는다. headless 보고서와 실제 화면 검토를 구분한다. 화면 확인이 필요한 실패는 headed 또는 이용 가능한 브라우저 도구로 관찰한다.
7. 실패 원인을 해결한 뒤 관련 테스트를 재실행하고, 최종 전달 시 승인된 전체 회귀 검사를 수행한다. 변경·실패 없이 같은 검사만 반복하지 않는다.

산출물: 시나리오 목록, 테스트 파일, 실행 명령·종료 코드, 대상 버전, 보고서/trace 경로, 정리 결과, 남은 실패와 승인 기록. 이 문서에서는 템플릿만 제공한다.

```text
E2E 시나리오 ID / PRD 스토리 / 관련 이슈:
기능 통합 상태 / 대상 코드 버전:
사용자 / 시작 상태 / 테스트 URL:
Given: 테스트 소유 데이터와 초기 화면
When: 입력, 클릭, 키 동작의 구체적 순서
Then: 화면에 보여야 할 결과와 검증 지점
locator 후보와 선택 이유:
단위·통합에서 이미 검증한 내용 / 중복 제외 이유:
생성 데이터 ID 수집 / 정리 방법 / 정리 실패 처리:
실행 모드 / 명령 / 종료 코드 / 통과·실패·건너뜀 수:
화면 직접 검토 여부 / 보고서·trace 경로:
실패 계층 / 회귀 테스트 / 재실행 결과:
검토자 / 승인 범위 / 미결 사항:
```

### 3.4 실패 복구

**강의 사실(14:p8, 15:p5)**: E2E 실패 → API·렌더링·로직 등 고장 계층 식별 → 해당 단위 테스트에 회귀 사례 추가(Red) → 프로덕션 코드 수정(Green) → E2E 재실행. 15:p5는 통과시키려고 E2E 코드를 고치는 것을 금지한다.

**보강 방법론**: 먼저 제품 버그, 잘못 작성된 테스트, 환경 장애, 데이터 오염을 구별한다. 제품 버그를 assertion 완화나 skip으로 숨기지 않는다. 테스트 자체가 승인 요구사항과 어긋났다면 근거와 변경 이유를 별도 검토받아 수정할 수 있다. 모듈 연결 결함은 적합한 통합 회귀 테스트도 추가한다. 정리 실패는 성공에 묻지 말고 데이터 ID와 소유 범위를 남긴다. trace의 자격증명·개인정보는 외부 공유하지 않는다.

## 4. 15강: PR, CI, 보호 규칙, 최종 머지

### 4.1 강의 사실과 순서상의 주의점

15:p4의 `/create-pr`는 **PR 초안 생성 → 개발자 승인 → E2E → 실패 시 PR 생성 중단 / 성공 시 push → PR 생성**이다. 승인 전에 외부 PR부터 만드는 흐름이 아니다.

15:p6은 검증 체인을 코드 스타일(Husky+lint-staged), 커밋 메시지(commitlint), 보안(`/security-review`), E2E(`/create-pr`), 클린 환경(GitHub Actions CI)으로 누적한다. 15:p7은 누락 의존성, 환경변수, 캐시, 머신 상태 때문에 로컬 성공만으로 충분하지 않다고 설명한다.

15:p8의 예제는 `.github/workflows/ci.yml`, `pull_request`의 `branches: [main]`, `verify` job, `ubuntu-latest`, `actions/checkout@v4`, `actions/setup-node@v4`, `npm ci`, lint, `tsc --noEmit`, moderate 이상 audit, `npm test` 순서다. 15:p9의 네 검사 목적은 스타일, 타입, 의존성 취약점, 동작 검증이다.

**보강 방법론**: 이 YAML은 강의 예시이며 최신 권장 버전이나 이 레포에 바로 적용 가능한 완성본이 아니다. 예제에는 Playwright 브라우저 설치·서버/DB 준비·trace 보관 설정이 보이지 않는다. `npm test`가 단위·통합·E2E를 모두 실행한다는 슬라이드 설명은 대상 앱의 scripts를 확인해야 성립한다. CI 통과는 구성된 환경의 증거이지 모든 머신과 모든 동작을 보장하지 않는다.

15:p10은 PR 필수와 상태 검사 필수를 설정해 main 직접 push와 미통과 머지를 차단하도록 설명한다. 15:p11은 `feature/tag-spec → main` PR과 **squash가 아닌 merge 방식**으로 이슈별 이력을 보존한다.

순서 차이를 보존해야 한다. 15:p2의 개념 도식은 CI → 브랜치 보호 → main 머지이나, 15:p16의 실습은 CI 파일 추가·첫 main 통합 PR·검증·머지 뒤 보호 규칙을 추가해 **다음 PR부터** 강제한다. 보강 시에는 가능한 한 첫 머지 전에도 보호·리뷰 조건을 확인하되, 실습 슬라이드가 처음부터 보호되었다고 바꾸어 쓰지 않는다.

### 4.2 재사용 절차: 전달 후보 준비부터 머지 확인

입력: 승인된 변경 범위, 이슈 AC, 보안 결과, E2E 증거, 현재 head/base, PR 초안, CI 정의와 필수 검사 이름, 리뷰 정책, 외부 작업 승인.

1. 작업 트리와 변경 소유권을 읽고 해당 이슈 diff만 확인한다. 다른 작업자의 변경을 커밋·stash·reset하지 않는다.
2. PR 제목, 목적, 변경 파일, AC별 근거, 테스트 결과, 위험, 복구 계획을 초안으로 작성한다. head와 base를 명시하고 리뷰를 받는다.
3. 승인 범위 내 관련 검사와 기존 E2E를 실행한다. 실패하면 push/PR 생성 경로를 닫고 3.4절의 복구로 되돌아간다.
4. 커밋·push·외부 PR 생성 각각이 사용자 요청에 포함되는지 확인한다. 강의 스킬 이름이나 로컬 검사 통과만으로 권한을 추정하지 않는다. 이 작업에서는 모두 금지다.
5. 후속 실행에서만 실제 PR을 만들고, CI가 대상 head의 올바른 검사들을 완료했는지 결과를 확인한다. queued, skipped, cancelled, 검사 없음은 통과로 바꾸지 않는다.
6. 필수 검사 이름이 CI job과 연결되는지, 대상 브랜치 보호와 리뷰 조건이 충족되는지 확인한다. main에만 걸린 CI가 feature 대상 이슈 PR에도 실행된다고 가정하지 않는다.
7. 최종 머지 승인 후에만 승인된 merge 전략을 사용한다. branch 이름·PR 번호·head 변경 여부를 직전에 확인한다. 이력 보존이 필요하다는 강의 의도를 임의 squash로 바꾸지 않는다.
8. 머지 결과와 대상 커밋을 확인하고 운영 설명서를 실제 코드와 맞춘다. main 머지와 서비스 배포/운영 정상은 별도의 결과로 기록한다.

```text
전달/PR 초안
이슈 / 목적 / 승인된 범위:
head / base / 검증 대상 커밋:
변경 파일 / 다른 작업자 변경 제외 내역:
AC별 구현·테스트 근거:
단위 / 통합 / E2E / 타입 / lint / 보안: 실행·미실행·실패 구분
실제 명령 / 종료 코드 / 보고서:
Closes #N 사용 여부와 대상 이슈:
CI 필수 검사 이름 / 실행 URL / 대상 head / 결과:
리뷰 결과 / 알려진 위험 / 복구 계획:
커밋·push·PR 생성 승인 / 머지 승인: 각각 범위와 근거
merge 전략 / 결과 커밋 / 배포 검증은 별도:
```

실패 복구: CI 실패 로그에서 첫 실제 실패를 분류한다. 환경 문제는 런타임·잠금 파일·변수·서비스 차이를 확인하고, 제품 결함은 회귀 테스트로 재현한다. 충돌이나 head 변경이 있으면 이전 테스트 결과를 그대로 재사용하지 않는다. 머지 후 문제는 검토 가능한 되돌리기 계획을 준비하되 강제 push나 무단 revert로 복구하지 않는다.

### 4.3 문서 정리의 보존 예외

**강의 사실(15:p12)**: README·운영 가이드·다이어그램은 남기고 기능 단위 spec/PRD/ADR 및 이슈 분해 작업표는 정리 대상으로 제시한다. 판단 질문은 장기적으로 다시 볼 문서인지다.

**보강 방법론 및 현재 지침**: 이를 무조건 삭제 규칙으로 이식하지 않는다. ADR에는 결정 이유, spec에는 승인 근거가 남아 있으므로 후속 프로젝트의 보존 정책에 따라 유지·보관·삭제를 판단한다. 특히 이 작업의 보호 PDF, 원본 워크플로우, `docs/features/pm-program-tracker`의 보호 3파일은 삭제·이동·포맷하지 않는다. 이 문서는 정리 실행 권한을 부여하지 않는다.

15:p14-15의 재사용과 이슈당 5-10분 수치는 강의의 기대 설명이지 현재 레포에서 측정한 성능이 아니다. `/create-pr`의 자연어 자동 발동도 강의 설계이며 현재 Codex에서 확인한 동작이 아니다.

## 5. 16강: tdd-loop는 순서 자동화, 승인은 유지

### 5.1 실제 이름과 0+7 단계

**강의 사실(16:p3-7)**: `/tdd-loop`는 새로운 구현 알고리즘이 아니라 기존 스킬·에이전트를 순서대로 호출하는 컨테이너/메타 스킬이다. 명령 7번을 한 번으로 줄이고 누락·실패 위치를 관리하지만 판단과 승인을 우회하지 않는다. “7단계”에 사전 점검 0번이 추가되어 실제 표기는 0-7이다.

| 단계 | 원문 호출/역할     | 입력과 수행                            | 산출물·검증·게이트: 보강 인계 계약                             |
| ---- | ------------------ | -------------------------------------- | -------------------------------------------------------------- |
| 0    | 사전 점검          | 이슈·AC, base 확인, `feat/<slug>` 분기 | 브랜치 계획, 허용 변경, 실행 환경; 생성 승인 없으면 계획만     |
| 1    | `/test-scenarios`  | 시그니처·시나리오 설계                 | 정상·예외·경계 사례와 기대값; 시그니처·시나리오 사용자 승인    |
| 2    | `/tdd-red`         | 승인 시나리오로 실패 테스트 작성       | 기대 동작 미구현 때문에 실패한 로그; import/설정 오류와 구분   |
| 3    | `/tdd-green`       | 최소 구현, 내부 회귀 감시              | 테스트를 바꾸지 않은 최소 diff, 관련 테스트 결과               |
| 4    | `@ac-verifier`     | AC 충족 독립 검증                      | AC별 실제 근거와 미충족 목록; 구현자 자기 선언만으로 통과 금지 |
| 5    | `/tdd-refactor`    | 동작 보존 리팩터링                     | 변경 이유, 테스트 재검증, 과잉 추상화 여부                     |
| 6    | `/security-review` | 보안 점검                              | 발견 사항·심각도·수정·재검사·미해결 위험                       |
| 7    | `/create-pr`       | commitlint, `Closes #N`, PR 생성       | 승인된 PR 초안, E2E 결과, 외부 작업 승인, 실제 생성 결과       |

4번은 **에이전트 `@ac-verifier`**이지 `/ac-verifier`라는 스킬로 표기하면 안 된다. 16강은 Green 재시도 횟수나 시나리오 최소 5개를 수치로 규정하지 않는다. 그 수치는 17강 p7에 나온다.

### 5.2 브랜치 흐름과 종료점

**강의 사실(16:p8)**:

```text
main
  feature/tag-spec              기능 통합 브랜치
    feat/tag-1 -> PR -> feature/tag-spec
    feat/tag-2 -> PR -> feature/tag-spec
    ...
  feature/tag-spec -> 최종 PR -> main  (15강 절차)
```

16:p7은 7번을 PR 생성으로 끝내지만 16:p8의 설명은 `/tdd-loop` 범위를 **이슈 PR → feature/<spec> 머지까지**로 적는다. 따라서 “PR 생성”과 “이슈 머지”를 별도 완료 상태로 기록하고 머지 권한을 확인해야 한다. 어느 쪽도 자동 main 머지 권한이 아니다.

15:p15에는 기능 전체를 main에 넣은 이후의 새 수정/기능 브랜치를 main에서 분기하는 예도 있다. 따라서 모든 이슈 PR의 base를 무조건 `feature/tag-spec` 또는 무조건 main으로 하드코딩하지 않는다. 기능 통합 중인지, 통합 후의 독립 변경인지 입력으로 확정한다.

### 5.3 정지, 재개, 승인 계약

**강의 사실**: 16:p6은 단계 실패 위치를 명확히 보고하고 게이트를 유지한다. 17:p4의 회고도 16강에서는 시그니처·시나리오·구현 등 사용자 응답이 유지된다고 명시한다.

**보강 방법론**:

1. 최초 호출 시 이슈, AC, head/base, 허용 파일, 승인된 명령 범위를 확인한다.
2. 각 하위 단계 결과를 기록한 후 다음 단계의 입력이 충분한지 확인한다. 미승인 시나리오로 Red에 넘어가지 않는다.
3. 테스트 실패가 예상된 Red인지, 비정상 도구 실패인지 구분한다. 후자는 Green 진입 조건이 아니다.
4. AC 미충족, 보안 미해결, 테스트 실패, 승인 누락, 범위 변경, 외부 도구 부재 시 해당 위치에서 멈춘다. 완료를 선언하지 않는다.
5. 승인 대기와 기술 실패를 구별한다. 승인이 필요한 단계는 산출물과 질문을 제시하고, 실패는 로그·원인·복구안을 남긴다.
6. 재개 시 작업 트리·브랜치·입력 버전을 다시 확인한다. 유효한 이전 승인까지 반복해서 묻지 않되 범위가 달라졌다면 변경분을 확인한다.

```text
TDD 실행 원장
이슈 / AC 원문 / 기획 승인 근거:
base / head / 대상 버전 / 변경 허용 파일:
단계 0-7 각각: 상태, 입력, 산출물 경로, 명령, 종료 코드, 증거
상태 값: 준비 / 실행 / 승인 대기 / 실패 / 통과 / 미실행
마지막 통과 단계 / 현재 실패·대기 단계:
승인자 / 승인 범위 / 변경된 전제:
PR 생성 여부 / feature 머지 여부 / main 머지는 별도:
복구 작업 / 재개 조건 / 재검증 필요 범위:
```

## 6. 17강: tdd-auto-loop의 자체 승인과 객관 STOP

### 6.1 강의 사실: 컨테이너와 다른 점

17:p1-6은 `/tdd-auto-loop`를 순서뿐 아니라 의사결정까지 자동화하는 자율 루프로 정의한다. 각 단계는 격리된 subagent가 실행하고 종료 시 컨텍스트를 해제한다. 메인은 코드 본문 대신 결과 JSON을 누적·검사한다. 하위 스킬 사용자 승인 게이트는 자체 통과하며, Green 직후 별도 `ac-verifier`가 검증한다.

17:p8의 STOP은 “계속할까요?”라고 세션을 매달아 두는 방식이 아니다. 사유 로그와 이슈 코멘트를 남기고 종료한 뒤 사용자가 보강하여 재실행한다. 17:p9의 사람 역할은 **PR 리뷰 한 번**이다. 제목도 PR까지라고 명시하며 자동 main 머지를 설명하지 않는다.

### 6.2 원문 STOP 조건 전체

다음 수치와 조건은 **17:p7 원문**이다. 구현 시 임의로 낮추거나 “일반 권장값”으로 포장하지 않는다.

| 단계                | 원문 STOP 조건                      | 보강: 남길 근거와 복구                                                                   |
| ------------------- | ----------------------------------- | ---------------------------------------------------------------------------------------- |
| 0 사전 점검         | AC 누락 / uncommitted / 잘못된 base | 누락 AC, 작업 트리 상태, 기대·실제 base; 다른 사람 변경을 커밋·삭제해 조건을 맞추지 않음 |
| 1 시나리오          | 시나리오 5개 미만 / 경계값 누락     | 사례 목록과 AC 대응; 중복 사례로 숫자만 채우지 않고 승인 범위에서 보강                   |
| 2 Red               | 잘못된 이유로 실패(import 에러)     | 실제 stderr와 예상 실패 차이; 러너·경로를 수정하고 Red 증거 재수집                       |
| 3 Green (×3)        | 3회 실패 / 테스트 수정 시도         | 시도별 diff·실패 로그, 테스트 변경 감지; 네 번째 자동 시도 금지                          |
| 4 AC 검증           | `ac_passed=false`                   | AC별 미충족 증거; 기준 완화 대신 입력·구현 보강 후 새 실행                               |
| 5 Refactor          | `npm test` 미통과                   | 동작 회귀 위치; 해당 실행의 변경만 검토해 복구                                           |
| 6 Security + 재스캔 | 재스캔 후 high 이상                 | scanner·대상·결과와 잔여 심각도; 수정 후 재검사, 무근거 면제 금지                        |
| 7 PR 생성           | commitlint 실패                     | 메시지 규칙과 실제 오류; 훅 우회 금지, 통과 시 PR URL 기록                               |

17:p7은 Green “3회 실패”라고 적지만 시도 카운터의 상세 구현, JSON 전체 스키마, scanner 종류, 비용·시간 예산은 제공하지 않는다. 보강 설계에서는 Green 실행 시도를 1-3으로 명시하고 증거를 남겨 무한 반복을 막는다. 수치 5개는 사례의 질을 대신하지 않는다.

15:p8의 CI audit 차단 수준은 `moderate`, 17:p7의 재스캔 STOP은 `high 이상`이다. 둘은 다른 검사 게이트다. high가 없다는 이유로 moderate CI 실패를 통과로 바꾸지 않는다.

### 6.3 Codex 변환: 자동 승인에 대한 필수 제한

**보강 방법론 및 현재 지침 우선**:

- 원문의 자체 승인을 그대로 전역 권한으로 해석하지 않는다. 요구사항·아키텍처·범위·이슈 목록의 사용자 승인 경계는 유지한다. 이번 통합 요청은 문서·스킬 등록이며 실제 앱 구현·외부 등록 요청은 아니다.
- 후속 사용자가 자율 실행을 명시적으로 위임한 경우에만, 이미 승인한 입력 안의 가역적 구현·검증 판단을 자체 처리하는 후보가 된다. 위임 범위 밖의 새 의존성·요구사항 변경·데이터 삭제·외부 전송은 기술 성공 여부와 별개다.
- 커밋·push·PR·이슈 코멘트·머지를 묶어 승인된 것으로 추정하지 않는다. 외부 코멘트가 금지/미승인이면 STOP 보고를 로컬 산출물로 남기며, 코멘트를 게시했다고 쓰지 않는다.
- 실제 subagent 실행 도구와 격리 범위를 실행 시 확인한다. 문서에 역할을 나눴다고 컨텍스트/파일시스템 격리가 구현되었다고 보고하지 않는다. 불가능하면 수동 인계 또는 명시된 대체 검증으로 기록한다.
- 원문 메인은 JSON만 본다. 보강 설계의 메인은 JSON의 필수 필드, 증거 경로, 코드 버전 일치, 실제 테스트 결과를 검증한다. 생성자가 적은 `passed=true`만으로 성공 판정하지 않는다. 코드 직접 검토가 필요하면 그 사실과 원문 대비 변경을 밝힌다.
- AC 검증은 구현자와 분리하고 승인 AC를 수정할 수 없도록 한다. Refactor 이후 동작/계약이 바뀌었다면 기존 Green 직후 AC 검증만으로 종료하지 않는다.
- 인프라 부재, 권한 범위 초과, 증거 누락, 결과 파싱 실패, 사용자 중단은 보강 STOP이다. 이를 17강 원문 조건이라고 주장하지 않는다.

### 6.4 재사용 절차와 결과 JSON 템플릿

입력: 승인 이슈·AC, 자율 위임 범위, 실행 환경, base/head, 하위 단계 계약, 검사 도구, 반복 예산, 외부 작업 허용 여부.

1. 사전 점검 결과와 허용 작업을 고정한다. 앱 부재·미승인 구현이면 실행하지 않는다.
2. 단계별 담당자에게 필요한 입력과 허용 파일만 전달한다. 같은 파일을 병렬 수정하도록 무작정 배분하지 않는다.
3. 단계 종료 결과를 구조화해 수집한다. 이전 단계 통과 근거와 다음 입력을 연결한다.
4. 6.2절 원문 STOP 및 6.3절 보강 STOP을 분리해서 검사한다. STOP이면 후속 단계와 외부 작업을 수행하지 않는다.
5. Green은 제한 횟수 내에서만 시도하고 별도 AC 검증을 호출한다. 보안 수정 뒤 재스캔과 관련 회귀 검사를 한다.
6. 모두 통과해도 외부 생성 권한이 없으면 PR 초안과 증거만 인계한다. 권한이 있을 때만 실제 PR URL로 생성 결과를 증명한다.
7. 사람의 PR 리뷰와 별도 머지 조건을 남긴다. 재실행은 사용자가 입력을 보강하거나 원인이 해결된 뒤 새 상태 점검부터 시작한다.

아래는 **보강 템플릿**이며 강의의 실제 JSON 전문이 아니다. 원문에서 직접 확인한 키는 `ac_passed`다.

```json
{
  "issue": "<approved-issue>",
  "stage": "ac-verification",
  "status": "stopped",
  "base": "<approved-base>",
  "head": "<issue-branch>",

  "attempt": 1,
  "ac_passed": false,
  "evidence": ["<local-log-or-report-path>"],
  "stop_source": "lecture-17-p7",
  "stop_reason": "<unmet-AC-and-observed-result>",
  "changed_files": [],
  "external_actions_performed": [],

```
