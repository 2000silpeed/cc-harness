# 4강 · 요구사항 인터뷰 — Codex 적용 설명서

원본: 프로젝트 루트의 `04.요구사항 인터뷰_v1.pdf`, 총 11쪽. 텍스트 추출만으로 읽을 수 없는 자료여서 모든 페이지를 이미지로 렌더링해 확인했다.

이번 범위는 **강의 브리핑 → Codex 프로젝트 지침 적용 → 사용 설명서 작성 → 검증**이다. 기존 PM 도구의 인터뷰·최초 요청·요구사항 정의서와 승인 상태는 변경하지 않는다. 인터뷰를 다시 진행하거나 앱을 구현하는 작업이 아니다.

## 1. 핵심 브리핑

### 코딩 전에 결정할 것은 사람이 정한다

기능을 짧게 요청하면 AI가 저장 방식, 제한, 중복 처리 등 빈칸을 대신 채울 수 있다. 코드가 빠르게 만들어져도 그 전제가 틀리면 다시 고쳐야 한다. 따라서 먼저 **무엇을 만들고 어떤 조건을 만족해야 하는지**를 정한다. (3~4쪽, 7쪽)

- 기능 요구사항: 시스템이 해야 하는 동작.
- 비기능 요구사항: 성능·저장·복구·사용 환경 등 만족해야 하는 조건.
- 구현·아키텍처: 확정한 요구사항을 어떻게 실현할지 정하는 후속 작업.

### AI가 질문하고, 사용자가 결정한다

사용자가 모든 예외를 먼저 나열하는 대신 AI가 정의서와 실제 코드를 읽고 질문한다. 질문은 **한 번에 하나**, 필요한 경우 **추천과 이유**를 함께 제시한다. 추천은 결정의 근거이지 사용자의 결정을 대신하는 승인이 아니다. (8~9쪽)

### 원본과 확정본을 나눈다

- `spec-original.md`: 처음 받은 요청을 보존한다.
- `spec-fixed.md`: 인터뷰로 구체화하고 사용자가 확정한 요구사항을 기록한다.
- 결정 이유와 용어를 함께 남겨 나중에 “왜 이 규칙인가?”에 답할 수 있게 한다. (10~11쪽)

확정본이라는 파일명만 붙였다고 승인된 것은 아니다. 사용자가 검토·확정한 사실과 AI의 미확정 제안을 구분해야 한다.

### 강의의 강조 표현을 해석할 때

4쪽은 요구사항·설계·구현·테스트·배포 후 수정 비용을 각각 1배·5배·10배·15배·100배로 제시한다. **늦게 발견할수록 수정 부담이 커진다는 강의 설명**으로 읽는다. 슬라이드에 수치의 연구 출처가 표시되어 있지 않으므로 모든 프로젝트에 적용되는 실측 비율이나 시간 절감 보장으로 사용하지 않는다.

8쪽의 AI 학습 경험에 관한 설명도 AI가 항상 더 정확하다는 보장으로 해석하지 않는다. 실제 파일·사용자 답변·검증 결과가 판단 근거다.

**새 패키지·Git 훅·전역 설정은 필요하지 않다.** 3강과 달리 4강은 개발 도구를 추가 설치하는 강의가 아니라, 이미 준비한 환경에서 질문과 결정 절차를 적용하는 강의다.

Codex용 프로젝트 지침은 기존 `AGENTS.md`에 반영했다. Claude용 파일을 새 기준으로 삼거나 `feature-planner` 스킬을 설치한 것은 아니다. 강의 도식에 나온 `/test-scenarios`, `/tdd-red` 등의 후속 명령도 이번에 추가하지 않는다.

다음 파일은 이번 작업에서 수정·재작성·포맷·승인 상태 변경을 하지 않는다.

## 4. Codex에서 사용하는 절차

### 새 기능의 인터뷰를 요청할 때

새 기능의 초기 아이디어를 준비하고, 프로젝트의 새 Codex 세션에서 아래와 같이 요청한다. 경로는 실제 대상 기능의 파일로 바꾼다. **이 예시는 재사용 방법이며, 이번에 기존 인터뷰를 다시 실행하라는 뜻이 아니다.**

```text
AGENTS.md와 docs/features/<기능명>/spec-original.md를 읽어줘.
먼저 실제 코드와 설정을 확인하고, 구현 전에 결정해야 할 내용을 질문해줘.
앱 소스가 없다면 기존 앱이 있는 것으로 가정하지 마.

질문은 한 번에 하나씩 해줘.
판단이 필요한 질문에는 추천 방식과 이유도 포함해줘.
이미 확인한 사실은 반복해서 묻지 말고, 내 답변 없이 결정을 확정하지 마.

인터뷰가 끝나면 같은 폴더의 spec-fixed.md에 다음을 정리해줘.
- 목적과 사용자, 기능 및 비기능 요구사항
- 용어 정의, 경계 조건과 오류 처리
- 결정 사항과 이유, 이번에 하지 않을 것, 수락 기준
- 합의한 내용과 아직 확인이 필요한 제안의 구분

최초 요청은 보존하고, 다른 기능의 인터뷰 파일은 수정하지 마.
내가 정의서를 확정하기 전에는 구현하거나 커밋하지 마.
```

### 결과를 검토할 때

1. 원래 요청이 삭제되거나 다른 의미로 바뀌지 않았는지 확인한다.
2. 질문별 사용자 답변과 최종 규칙을 연결해 읽는다.
3. AI 추천을 그대로 채택한 부분과 사용자가 수정한 부분을 구분한다.
4. 빈 값·중복·실패·되돌리기 같은 예외가 어떻게 처리되는지 확인한다.
5. 코드·문서·대화에서 같은 용어가 같은 의미인지 확인한다.
6. 확인하지 않은 성능 수치나 기술 선택이 확정 사실로 섞이지 않았는지 확인한다.
7. 사용자가 최종 확정한 뒤에만 문서 상태를 확정으로 바꾼다. 이후 요구사항 변경은 이유와 함께 기록한다.

문서 커밋이 필요하면 변경 내용을 먼저 검토하고 명시적으로 요청한다. 메시지 예시는 `docs(requirements): 기능 요구사항 인터뷰 정리`이며, 이번 작업에서는 커밋·푸시하지 않는다.

## 5. 검증 방법과 범위

- PDF 11쪽 전체의 시각적 확인과 페이지별 대응표를 점검한다.
- 새 인터뷰 지침이 Codex의 모델 입력에 포함되는지 비생성 진단으로 확인한다. 이는 새 인터뷰를 실행하는 테스트가 아니다.
- 기존 인터뷰 3개 파일과 원본 자료의 작업 전후 SHA-256을 비교한다.
- 수정한 문서만 서식을 정리한 뒤 `npm run check`로 기존 ESLint·Prettier 검사를 수행한다.
- 앱 테스트·배포·PRD·디자인 시스템·새 인터뷰의 완료를 주장하지 않는다.

이번 4강 적용의 결과는 **재사용할 협업 지침과 설명서**다. 특정 기능의 인터뷰 답변이나 요구사항을 다시 결정한 결과가 아니다.
