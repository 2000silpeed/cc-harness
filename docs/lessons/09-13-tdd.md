# 9–13강 · 이슈 하나를 검증된 코드로 바꾸기

## 원문 확인과 적용 경계

9강 12쪽, 10강 10쪽, 11강 16쪽, 12강 14쪽, 13강 5쪽을 렌더링해 전부 확인했다. 아래는 강의 내용의 구조화와 Codex용 실행 방법론이다. 태그·React·Vitest는 원문의 예시이며 모든 프로젝트의 의무 스택이 아니다. 현재 저장소에는 앱이나 앱 테스트가 없으므로 스킬 등록을 실제 앱 TDD 완료로 표현하지 않는다.

## 9강 — 계약과 시나리오를 먼저

입력: 승인된 PRD·이슈 AC·기존 코드와 테스트 방식. 출력: `docs/features/{feature}/tests/{issue}-scenarios.md`.

1. 이슈의 사용자 관찰 가능 결과와 선행 의존성을 읽는다.
2. 함수·API의 이름, 입력·출력 타입, 동기/비동기 여부, 오류 계약을 먼저 고정한다. 구현 코드는 작성하지 않는다.
3. AC마다 정상·경계·예외 사례를 도출한다. min/max의 직전·정확한 경계·직후, 빈 값·중복·실패를 대상 도메인에 맞게 선택한다.
4. `should [결과] when [조건]` 이름과 Given–When–Then을 적고 AC ID를 연결한다.
5. 인터페이스와 시나리오를 사용자에게 검토받은 뒤 Red로 간다. 미정 동작은 AI가 스스로 확정하지 않는다.

```markdown
# 이슈 [ID] 시나리오

- 근거 PRD·AC·대상 코드:
- 계약: 함수/API, 입력, 출력, 오류, 부작용
- 검토 상태·사용자 결정 근거:

| ID  | AC  | 분류 | Given | When | Then | 테스트 층 | 격리할 의존성 |
| --- | --- | ---- | ----- | ---- | ---- | --------- | ------------- |

## 미정·제외

## 실행할 테스트 명령
```

AI가 구현과 기대값을 동시에 맞추면 잘못된 동작도 함께 통과할 수 있다. 테스트 통과와 요구사항 충족은 별도 판단이다. 테스트 용이성은 외부 의존성을 경계로 분리할 단서이지 무조건 추상화를 늘리라는 뜻이 아니다.

## 10강 — Red는 실패 종류를 증명하는 단계

입력: 검토된 계약·시나리오. 출력: 테스트 코드, 필요한 최소 stub, 실제 실패 로그.

1. 기존 테스트 러너를 사용한다. 없는 경우 설치·스크립트·테스트 위치를 준비하는 작업을 먼저 구분한다.
2. 시나리오를 테스트 이름과 assertion으로 옮긴다. UI는 내부 state보다 사용자가 보는 텍스트·역할·동작을 검증한다.
3. 모듈 로딩이 필요하면 계약 그대로의 최소 stub만 추가한다. 비즈니스 동작은 구현하지 않는다.
4. 테스트가 수집·실행되고 기대 동작 미구현 때문에 실패하는지 읽는다.
5. 문법·import·환경·연결 오류는 Broken으로 분류해 먼저 해결한다. 대상 테스트 수와 실패 이유를 남긴다.

**보강:** 기존 코드가 이미 동작한다면 처음부터 통과할 수 있다. 억지 실패를 만들거나 기존 동작을 훼손하지 말고, 특성화 테스트인지 신규 미구현 동작인지 판별한다. 일부 예외 테스트는 stub의 일반 오류만으로 통과할 수 있으므로 오류 종류·메시지·상태까지 계약과 맞춰 검토한다. 원문의 `N failed, 0 passed`는 신규 예시의 출발점이지 모든 저장소 전체 테스트를 실패시키라는 지시가 아니다.

## 11강 — Green은 테스트를 바꾸지 않는 최소 구현

1. 실제 Red 증거를 확인하고 실패 하나를 선택한다.
2. 해당 기대 동작에 필요한 코드만 추가한다. 새 편의 기능·미래 확장·불필요한 추상화는 하지 않는다.
3. UI라면 design.md와 공통 디자인 기준을 함께 적용한다. 동작 테스트 통과가 외형 일치를 보증하지 않는다.
4. 관련 테스트를 실행하고 기존 통과 테스트가 깨지지 않았는지 확인한다. 작은 저장소에서는 전체 테스트를 매번, 큰 저장소에서는 관련 회귀 묶음을 반복하고 단계 종료 시 전체 검사를 한다. 이는 효율을 위한 적용 보강이다.
5. 남은 실패를 순차적으로 줄인다. assertion 삭제·skip·기대값 완화·계약 변경으로 초록색을 만들지 않는다.
6. 설정된 coverage가 있다면 미실행 분기를 누락 시나리오 후보로 검토한다. 수치를 높이기 위한 의미 없는 테스트는 추가하지 않는다.
7. 별도 AC 검증자가 이슈 원문과 구현·증거를 비교한다. 빠진 AC가 나오면 시나리오/Red로 돌아간다.

원문은 Function·Statement·Branch·Line 지표, V8 coverage 예, 분기 없는 듯 보이는 if의 반대 경로를 설명한다. 계측 도구별 집계 차이가 있으므로 Branch 100%가 모든 환경에서 다른 지표와 제품 정확성을 보장한다고 일반화하지 않는다. 실행한 코드 비율과 assert한 의미는 다르다.

### AC 검증 기록

```markdown
# AC 검증 — 이슈 [ID]

- 검토 대상 변경·버전:
- 검증자: 독립 에이전트 / 동일 에이전트 재검토
  | AC  | 구현 근거 | 실행·관찰 근거 | 판정 | 누락·다음 행동 |
  | --- | --------- | -------------- | ---- | -------------- |
- 판정: pass / fail / unverified
```

강의의 `@ac-verifier`는 절차를 반복하는 스킬과 구분되는 판단 역할이다. 여기서는 `ac-verifier` 스킬에 검증 계약을 두고, 허용된 독립 서브에이전트가 이 계약으로 검토하게 한다. 스킬 파일만 만들고 독립 에이전트가 설치·실행됐다고 주장하지 않는다.

## 12강 — Refactor와 보안은 다른 검사

### Refactor

전제: Green과 AC 검증이 유효함. 중복, 이름의 명확성, 단일 책임, 불필요한 복잡도, AGENTS 컨벤션의 다섯 기준으로 검토한다. 작은 변경 하나 뒤 관련 테스트를 실행한다. 실패하면 **자신의 마지막 변경만** 되돌리거나 수정하고, 사용자 변경을 reset/checkout으로 지우지 않는다. 새 기능과 동작을 바꾸는 버그 수정은 별도 Red가 필요한 변경으로 다룬다. 개선이 필요 없으면 억지 리팩터링하지 않는다.

### 보안·품질

1. 동작 테스트와 별도로 대상 스택의 타입 검사를 실행한다. TypeScript가 없으면 tsc 설치가 아니라 해당 없음으로 기록한다.
2. 사용 중인 패키지 매니저의 의존성 검사를 확인한다. 네트워크 감사는 패키지 정보를 외부로 보내므로 대상 정책에 맞게 실행한다.
3. 입력 검증·인증·권한·출력 처리·민감정보·환경변수·로그·설정 변경을 변경 범위에서 검토한다.
4. 각 발견에 영향·근거·심각도·도달 가능성·수정안·결정자를 남긴다. 즉시 조치/권장 조치/근거 있는 예외를 구분한다.
5. `audit fix --force` 같은 강제 업데이트는 하지 않는다. 수정 후 테스트와 필요한 검사를 다시 수행한다.

**보강:** 원문의 low 무시 가능은 자동 무시 규칙으로 옮기지 않는다. 개발 의존성도 빌드 환경에 영향을 줄 수 있다. 실제 노출된 비밀은 로그에 재출력하지 않고 교체·폐기 등의 조치를 사용자에게 알린다. 타입 검사·감사 모두 통과해도 안전한 제품 전체를 입증하지 않는다.

```markdown
# 보안·품질 검토 — 이슈 [ID]

| 항목 | 근거 | 영향·심각도 | 조치 또는 예외 이유 | 책임자·재검토 | 결과 |
| ---- | ---- | ----------- | ------------------- | ------------- | ---- |

- 실행 명령·작업 경로·종료 코드·증거:
- 미실행 검사와 이유:
- 머지 차단 항목:
```

## 13강 — 이슈마다 같은 사이클

`test-scenarios → tdd-red → tdd-green → ac-verifier → tdd-refactor → security-review → 승인된 이슈 PR`을 의존성 순서로 반복한다. 기능 전체 E2E와 main 머지는 모든 준비된 슬라이스가 통합된 뒤 별도 수행한다. 이슈 완료를 main 배포 완료와 혼동하지 않는다.

이슈마다 시나리오·테스트·검증·PR 증거를 연결하고 다음 작업으로 인계한다. 강의의 feature/tag-spec 등 브랜치 이름과 숫자 1은 예시일 뿐이다. 실제 저장소·base/head·승인 범위를 확인한다. 커밋·브랜치·PR·이슈 종료는 해당 작업의 별도 요청 또는 명시적 사전 승인 범위 안에서만 수행한다.
